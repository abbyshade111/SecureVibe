# ADR-068: An MCP link to a remote server over plain HTTP, found in the app's code (C10.3.1)

**Status:** proposed, 9 October 2026, with the backlog claim (0085, part 15); to be accepted in the pull request that
builds it. Asked for by the owner ("please continue to work through and pick up new items as you merge"). Written by
session paper-facts.

**Governs:** `crates/sv-check/src/launch.rs`, where the check this record adds, config.mcp-transport-unencrypted,
reads the same files as config.mcp-server-unpinned (ADR-049 governs the same file). A pull request that changes what
it says about this changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

AISVS C10.3.1 (level 1) reads: "Verify that authenticated, encrypted streamable HTTP is used for MCP transport for
remote services." Nothing in StackVet speaks to it. An app that is an MCP client writes the server's address in a
configuration file (`"url": "…"` in a server's entry) or opens a transport with it in code
(`StreamableHTTPClientTransport`, `streamablehttp_client`, `SSEClientTransport`, `sse_client`, and the like). An
address that starts `http://` and names another computer sends the tool calls, their results, and whatever token
the link carries, unencrypted.

## Decision

- **Where it looks:** the app's files that `config.mcp-server-unpinned` reads, configuration and code; not the AI
  coding tool's own files, which ADR-049 grades apart.
- **What it finds:** an `http://` address, as the `url` or `serverUrl` of an entry under `mcpServers` (or a key named
  for MCP), or as the first argument of a known MCP client transport.
- **Not this computer and not a private network:** `localhost`, loopback and private addresses, and a host name with
  no dot (a service on the same Docker network) are left out, since the link never leaves the machine or the
  network the app runs on.
- **Only ever a finding (medium):** an `https://` address shows neither that the link is authenticated nor that no
  other link is plain, so a clean run credits nothing, and the check is listed as one that only finds.

## Alternatives considered

- **Every `http://` string near the word MCP.** Rejected: documentation links and test fixtures would be found.
- **The old SSE transport as a finding.** Not here: it is deprecated, not unencrypted; over `https://` it is
  encrypted, so it does not fail C10.3.1's words.
- **Credit for an `https://` address.** Rejected for the reason above.
