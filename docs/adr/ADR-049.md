# ADR-049: `sv` reads the AI coding tool's own files in the project folder, apart from the app's grade

**Status:** accepted, 7 October 2026. The decisions are the owner's, of 7 October 2026 ("yes to 1 and 2, agree on
3"), on the three proposals in `docs/AGENTIC-SKILLS-TOP-10.md`. Proposed with the backlog claim, and built as proposed
(DESIGN, "The AI coding tool's own files, apart from the app").

**Governs:** `crates/sv-check/src/launch.rs`, which sets the AI coding tool's own files apart from the app's, and
`crates/sv-check/src/ai_tool.rs`, which reads them. A
pull request that changes what it says about them changes this record too, or says in its description why it does
not (`docs/adr/README.md`).

## Context

The person using `sv` builds with an AI coding tool, and that tool keeps its own files in the project folder:

- settings that run commands (Claude Code's hooks and helpers in `.claude/settings.json`);
- permission lists that let it act without asking;
- the MCP servers it starts (`.mcp.json`, `.cursor/mcp.json`);
- environment settings that send its traffic elsewhere;
- instruction files it reads as orders (`AGENTS.md`, `CLAUDE.md`, `SKILL.md`, `.cursor/rules/`).

OWASP's Agentic Skills Top 10 (read in `docs/AGENTIC-SKILLS-TOP-10.md`) names these as where skills go wrong:
- AST02: repository configuration files are executable code;
- AST03: over-broad permissions;
- AST04: instructions hidden with characters a reviewer cannot see;
- AST07: servers started unpinned.

Until now `sv` set these files aside on purpose (`developer_tool_config` in `launch.rs`), because they run on the
developer's computer and say nothing about the app, which is what ASVS and AISVS grade. Nothing read them at all.

## Decision

1. **The AI coding tool's own files are read, and reported in a section of their own, apart from the app's grade.**
   - **What is reported:** what they let the tool do, read from each tool's own documentation:
     - commands its settings run;
     - permissions that let it act without asking;
     - MCP servers it starts with no pinned version;
     - settings that send its traffic, or its keys, to another address.
   - **What each is:** a notice. The person may have chosen any of them on purpose, and none of them is about the
     app.
   - **What it cites:** no ASVS or AISVS requirement. Each notice cites none and credits nothing, so it changes no
     requirement's status.
   - **What it leaves out:** a setting the tool's documentation says has no effect from a project file is not reported.
     Claude Code's documentation says a `defaultMode` of `bypassPermissions` set in project settings does not take
     effect.
2. **Hidden characters in the instruction files committed in the folder are a finding.**
   - **What counts:** Unicode tag characters and the characters that override the direction of text, which a person
     reading the file cannot see and an AI tool reads.
   - **What is left out:** the zero-width joiner, which ordinary emoji use.
   - **Credit:** it is only ever a finding.
   - **Citation:** it cites no requirement, as `config.security-contact` cites none. Nothing in ASVS or AISVS asks
     this of a file in the folder.
3. **The Agentic Skills Top 10 is not adopted as a framework `sv` cites, for now.** It is a list of risks rather than
   requirements, its v1.0 is still in public review, and its own references to ASVS use 4.0's numbering. It is to be
   looked at again at its v1.0 release. Until then the new checks may say which of its risks they speak to, in their
   text, without citing it.

## Alternatives considered

- **Leave the developer's files out, as before.** Simpler, but the folder `sv` is given can run commands on the next
  computer that opens it, and nothing would say so.
- **Grade them with the app.** They are not the app; a hook on the developer's computer is not a failed ASVS
  requirement, and counting it as one would be a citation that is not a claim.

## Consequences

- A report gains a section about the AI coding tool. It is never counted in the app's requirement totals.
- Each tool's file format is read from that tool's own documentation and named in the code. A tool `sv` does not know
  is not read, and the section says which files it read. Cursor's documentation could not be reached when this was
  built, so its files are named as not read.

## Later, 9 October 2026: `sv`'s own marks named in the instruction files

The gap analysis of 7 October 2026, finding 22(e). An instruction file could tell the AI coding tool to write
`Written by: owner` under the security notes it drafts, or to add a `[[finding-review]]` for a finding it would rather
not fix, and this record read the instruction files only for hidden characters. Now every instruction file it already
names (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.cursorrules`, `.windsurfrules`, Copilot's, and the skill, command, and
agent folders) is also read for `sv`'s own marks: `Written by: owner`, `by = "owner"`, `[[finding-review]]`,
`not-the-app`, and `Sealed by sv review`, in any case and with Markdown's bold or italic markers set aside. A file that
names one gets one note in the report's section on the AI tool's files, naming every mark it names and quoting its
first such line, and is listed among the files read.

It is a note, not a finding, for the reason this record's other notes are: a line naming a mark may tell the tool to
write it, or just as well tell it never to, as `sv`'s own guidance does, and only a person reading it can tell. It
counts toward nothing. Since 4 October 2026 a mark the tool writes is not taken as the owner's without `sv review`'s
seal, so this does not decide what is credited; it shows the owner what the tool was told. The note cites AST03
(over-privileged skills: a tool acting on the owner's authority). Held by `crates/sv-check/tests/ai_tool_marks.rs`.
