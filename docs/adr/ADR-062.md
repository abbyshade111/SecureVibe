# ADR-062: The product is StackVet; the command stays `sv`

**Status:** proposed, 8 October 2026, with the backlog claim; to be accepted in the pull request that builds it.
Asked for by the owner that day ("go ahead and draft the ADR - let's keep the command as sv for sure"), after a
brainstorm of names that keep the initials and a check of what the chosen one collides with. Written by session
securevibe-review.

**Governs:** `Dockerfile`, and the names module the build adds to the frameworks crate (every name the product carries,
in one place; this line names its path once the file exists). Not the documents that use the name, and not the paper. A pull request that changes one of
these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The product has been called SecureVibe since v1 (the `v1` branch, the tags `v1-paper` and `v1-final`, the Zenodo
DOI the paper cites). On 8 October 2026 a search found at least five other products with the same or a near name,
all in the same space: SecureVibes (an open-source scanner built on Claude), SecureVibe (an IDE extension),
SecVibe (a coding copilot), SecureVibing (a scanner for vibe-coded apps), and SecurVibe (an indie toolkit). A
security tool whose whole position is that its word can be trusted cannot share its name with five others that
say something else.

The command is `sv`, and so are the crate names (`sv-check`, `sv-run`, …), the environment variables (`SV_*`), the
Docker image's suffix, and the way every document, test, and the paper refer to the program. A new name that keeps
the initials keeps all of that.

**StackVet** was chosen from a list of names keeping the initials: "vet" is the right verb (to examine carefully
before accepting), `[stack]` is already the manifest's section for what the app is made of, and the person the
product is for understands it at once. Checked the same day: no software product by that name (the `.com` belongs
to a veterinary hospital in Syracuse, New York), and the name is free on crates.io, PyPI, and npm. The domains
`stackvet.dev` and `stackvet.app` were available; buying them, renaming the repository, and renaming the published
image are the owner's actions, since they cost money or change the repository's settings.

## Decision

1. **The product is StackVet. The command is `sv`, and stays `sv`.** So do the crate names, the `SV_*` environment
   variables, the binary's name in every document, and the `sv` prefix of the Docker image.

2. **Every name the product carries is read from one place**, `sv_frameworks::names`, so that this rename is the
   last one that touches every crate: the product name, the manifest's file name, the report folder, its marker and
   lock, the bundle's name, the config folder, the MCP server's name and its tools' prefix, the Docker labels, the
   coding-rules markers, and the signature namespace. Each has a `new` name and, where a user's files carry it, the
   `old` one beside it.

3. **A name a user's files carry is read under both names, for a window, and written under the new one.** These
   are the files `sv` wrote into someone's folder, or someone wrote for `sv`, and a rename must not strand them:
   - `securevibe.toml` → `stackvet.toml`. `sv init` writes the new name. Every command reads the new name first
     and the old one when the new is absent, and the report says it read the old name, so the owner can rename
     the file when they choose. A folder with both is refused with its reason: two manifests are two answers.
   - `securevibe-report/` → `stackvet-report/` as the default report folder, with the marker `.securevibe-report`
     → `.stackvet-report` and the lock `.securevibe-report.lock` → `.stackvet-report.lock`. An existing folder
     carrying the old marker is still `sv`'s own and is written to under its old name; a new report folder gets the
     new marker. The seal checks (ADR-034) read either marker.
   - `securevibe-bundle.zip` → `stackvet-bundle.zip` (the default name of a new bundle; a bundle's comment says
     "Made by StackVet (sv bundle)").
   - `~/.config/securevibe` → `~/.config/stackvet`. **The signing key is in that folder, and nothing moves it.** The
     new folder is read first; when it is absent and the old one holds a key, the old one is used, and `sv review`
     says so once per run and names the command to move it. A key moved by the owner keeps its fingerprint, since
     the key is the same bytes.
   - The coding-rules markers in `AGENTS.md` and `CLAUDE.md` (`<!-- securevibe:coding-rules:begin -->` and `end`)
     → `stackvet:coding-rules`. A block under the old markers is found and replaced, and rewritten under the new.

4. **The MCP server is `stackvet`, and its tools are `stackvet_*`.** The old `securevibe_*` names are answered too
   for the window, mapped to the same tools, and the catalog lists only the new names, so an AI coding tool that
   learned the old ones keeps working while the `AGENTS.md` it reads is rewritten by `sv init` with the new.

5. **The Docker labels** `org.securevibe.owner` and `org.securevibe.run`, and the volume label `securevibe.deps`
   → `org.stackvet.owner`, `org.stackvet.run`, `stackvet.deps`. The cleanup of leftovers (ADR-025) reads both for
   the window, so a container or volume left by the old name is still found and removed.

6. **The signature namespace `securevibe-review` does not change.** It is part of every seal `sv review` has
   written into owners' files (SSH signatures carry their namespace, and a signature verifies only under the
   namespace it was made with; ADR-043). Changing it would make every existing seal fail. It is a wire format now,
   named after the product that made it, as such things are.

7. **The window.** The old names are read until this record says otherwise, in a dated Later entry; not before
   1 January 2027. The report and `sv review` say, each time they read an old name, what to rename, so nobody is
   surprised when the window ends.

8. **What never changes.** The git history, the `v1` branch and its `ARCHIVED.md`, the tags, the Zenodo DOI, and
   the paper's text: the study was of a product called SecureVibe, and the paper says so. Earlier decision records
   and design entries keep their wording; they said what was true when they were written, and this record is where
   the rename is recorded. The old image name, `ghcr.io/abbyshade111/securevibe-sv`, is left as it is, with no
   further pushes; the README says where the image went.

9. **The owner's actions, not the build's:** buying the domains, renaming the repository (GitHub redirects the old
   name), and renaming or re-publishing the image under `ghcr.io/abbyshade111/stackvet-sv`. The build changes what
   the code and the documents say; the owner changes what the services say.

## Alternatives considered

- **A name that drops the initials** (Scrutable, Attested, Candor, Verity, Assay). Two were taken by security
  products, and all of them cost the `sv` command and every reference to it, in the paper included. Set aside.
- **Keeping SecureVibe and living with the neighbors.** The neighbors are in the same market, and one of them,
  SecureVibes, is an AI-driven scanner installed from PyPI under nearly the same command; a person searching for
  this tool finds that one. Set aside.
- **Renaming the command too** (`stackvet` as the binary, with `sv` kept as an alias). Every document, test, and
  the paper say `sv`; an alias would be the thing everybody uses, and the longer name would be the thing nobody
  types. The owner chose to keep `sv` outright.
- **No compatibility window: rename the files on first run.** `sv` never edits a user's own data except to repair
  it (CLAUDE.md), and renaming `securevibe.toml` under an AI coding tool that is reading it is a change the tool
  did not make and would not expect. Read both, write new, and say so.

## Consequences

- One pull request, or a short series, that touches nearly every crate once, to route every name through
  `names.rs`, and every document. After it, a name lives in one place.
- Until the window ends, the code reads two names for each file, which is a few lines per name and a test for
  each: the old name read, the new one written, both present refused.
- The paper and the archived v1 keep the old name, and this record is the bridge between them and the product.

## How it is held

To be filled in by the pull request that builds it: a test that every old name is read and the new one written;
that a folder with both manifests is refused; that the old config folder's key is used and said; that the old MCP
tool names answer; that the old Docker labels are cleaned up; and that the signature namespace is the one every
existing seal carries (the seal tests of ADR-043, unchanged).
