# ADR-038: The SQL injection probe only reads, only on `sv`'s own copy of the app, and only ever finds

**Status:** accepted. Decided by the owner on 4 October 2026, when the probe was proposed (#545); built the same day
(DESIGN, "SQL injection on the app's own reads"). Recorded on 6 October 2026, after the second weekly review of the
decision records found it had none and the owner chose it as one of the four most costly to lose.

**Governs:** `crates/sv-check/src/signed_in/sql.rs`. A pull request that changes it changes this record too, or says in
its description why it does not (`docs/adr/README.md`).

## Context

SQL injection is an app joining what a request sends into the text of a database query, so the sender can rewrite
the query. `ast.sql-built-by-hand` looks for it in the code; `probe.sql-injection` (V1.2.4, CWE-89, critical) asks
the running app, by adding a condition that is always true, and one that is always false, to a value the app reads.

Asking that way is not harmless. A condition that is always true, added to a request that changes data, can change
every row: `DELETE … WHERE id = 12 OR '1'='1'`. The same request against an app that is live, with real people's
data, is an attack on it.

## Decision

The probe is built, within three limits the owner set:

- **Only requests that read.** Every request it sends is a GET. It never adds a condition to a form, a JSON body, or
  any request that writes.
- **Only on the copy of the app `sv` starts itself,** with its throwaway data, inside the network fence (ADR-019).
  The check lives among the signed-in checks, which only `sv run` and `sv report --run` call; `sv probe`, which asks
  the owner's live site, never reaches it. So the limit holds by where the code is, not by a flag that could be
  turned off.
- **Only ever a finding.** Two conditions told apart is a finding. Nothing told apart is not credit, since a few
  values in a few addresses are not every query the app builds. `tools/coverage.py` lists the check in
  `RUST_FINDINGS_ONLY`, so the coverage counts and the census of credits hold it there.

A crash (5xx) or no answer raises nothing and is never read as an answer (ADR-021).

## Considered

- **Requests that change data,** where injection is often worse. Set aside by the owner: the cost of one wrong
  request is a damaged database, and a finding on reads already shows the app joins values into queries.
- **Asking the live site through `sv probe`.** Set aside: `sv probe` makes at most four read-only requests and never
  sends anything crafted (ADR-027).
- **Crediting V1.2.4 when nothing is told apart.** Set aside: it would credit an app for the queries the probe did
  not reach.

## Consequences

- An app that injects only through a form, a JSON body, or a header is not found by this probe; the code-reading
  rule and the outside tools still read for it.
- Loosening any of the three limits is a change to this record, made knowingly.

## How it is held

In `crates/sv-check/src/signed_in/sql.rs`: `a_correct_app_is_not_accused_and_nothing_is_credited`,
`a_value_joined_into_a_query_is_found_wherever_it_is`, `a_crash_or_no_answer_raises_nothing`,
`two_refusals_told_apart_are_not_a_finding`, and `spots_are_found_in_a_records_address_and_in_query_strings`. The
findings-only listing is held by the coverage document's own test and by the census of credits CI runs.

## Later, 6 October 2026: a review of this record, at the owner's asking

Read against the code and the backlog the same day. The decision and how it is held are as written; three things are
corrected here rather than in place.

- **Who gave which reason.** The owner's reason for limiting the probe to reads was "so an always-true condition can
  never reach a request that changes data" (BACKLOG, signed-in item 7, "The owner's decision, 4 October 2026").
  "A finding on reads already shows the app joins values into queries", under Considered, is this record's own
  reasoning, not the owner's.
- **Proposed and built.** #545 is the pull request that built the probe. It was proposed earlier, as BACKLOG's
  signed-in item 7, claimed and released on 3 October. Dates here are UTC: #545 merged on 4 October in UTC, the evening
  of 3 October in Eastern time, which is why the backlog's list of records owed says "3 October".
- **Where its limits are enforced.** Only `sql.rs` is governed. "Only ever a finding" is held by `RUST_FINDINGS_ONLY`
  in `tools/coverage.py`; "only on `sv`'s own copy" by the signed-in checks' only caller (`signed_in/mod.rs`, ADR-021)
  and the fence (`crates/sv-run/src/docker.rs`, ADR-019); the rule's citation and severity are in
  `signed_in/rules.rs`. `tools/coverage.py` and `signed_in/rules.rs` change with most new checks, so, as the owner
  decided on 6 October for the large shared files, they are not added to Governs; the weekly review is the safety net.
