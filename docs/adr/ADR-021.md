# ADR-021: A crash's or a rate limiter's answer is never read as the app refusing

**Status:** accepted. Built from 28 to 29 September 2026 in four pull requests (#412, #416, #418, #420), and written
down here on 4 October 2026, because the first weekly review of the decision records found it had no record
(BACKLOG, "Records owed", item 1). Its reasons are in DESIGN, "A rate limiter's answer is not the app's" and "A crash
is not a refusal", each with a later part.

**Governs:** `crates/sv-check/src/signed_in/mod.rs`, `crates/sv-check/src/signed_in/signin.rs`,
`crates/sv-check/src/signed_in/codes.rs`, `crates/sv-check/src/signed_in/once.rs`. A pull request that changes any of
these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

Many of `sv`'s checks on the running app give credit because the app said no: a private page refused to a stranger, a
signed-out session refused, another user's record refused. When these were written, any answer that was not a
success counted as that no.

Two kinds of answer are not the app saying no. A rate limiter's answer (HTTP 429, or a 503 that says when to come
back) means the request was stopped before it reached the check it was asking about. A crash (any other 5xx), or no
answer at all, means the app failed; it says nothing about whether the app would have let the request through. Read as
refusals, both turned into passes the app never earned.

It was found from a report by an agent in another project that was integrating `sv`: a critical finding it listed as
"F-0001" had got a 429 from the app's rate limiter. That report never reached this repository, and the owner closed
F-0001 without it on 30 September 2026. Looking for it turned up the opposite fault, a false pass:
`probe.private-page-anonymous` credited V8.2.1 ("refused to somebody not signed in") when the limiter had answered and
the page's own check never ran.

## Decision

Every request the signed-in checks send, and since 29 September the anonymous ones too, goes through one place
(`Patient` in `crates/sv-check/src/signed_in/mod.rs`; `ask_anonymously` for the anonymous probes), and that place
decides what the answer was.

- **A rate limiter is waited out once.** A 429, or a 503 with `Retry-After`, is the limiter (`rate_limited`). The
  request is sent again after the app's `Retry-After`, capped at 60 seconds, or after 5 when it gives none. All the
  waiting in one run is capped at 300 seconds (`MOST_WAITING`). Checks that want to see the limiter, such as those
  that guess passwords or send bursts, are not waited for.
- **A limiter that keeps answering credits nothing in the run.** Every pass in the run becomes not assessed, with
  advice to run again with the limiter relaxed or a longer wait. It is deliberately coarse, since no record says which
  conclusion rests on which request. Findings are kept, with a note that they may rest on the limiter: hiding a real
  finding is the worse fault.
- **A crash withholds only what rests on it.** A 5xx other than the limiter's, or a request with no answer, is recorded
  as a crash. A pass or a finding that rests on a request that crashed becomes not assessed, naming the requests and
  saying "Fix the error, and run it again." The others stand, because a crash is the app's answer to one request and
  says nothing of the rest. Which pass rests on which request is a table: `RESTS_ON_A_REFUSAL` for passes (29 rows when
  it was written, 36 on 4 October 2026) and `RAISED_ON_A_REFUSAL` for findings raised from a refusal.
- **An anonymous answer still from the limiter is left out** of what the probes read, and the report lists it as a
  gap.

## Alternatives considered

- **Fixing each check where it reads its answer.** Set aside: the same reading was in about thirty places, and "the
  fix is where every request passes, not at the thirty places".
- **The crash rule as broad as the limiter's.** Set aside on purpose: a limiter that keeps answering puts every request
  in doubt, a crash only the one it answered.
- Two sessions built the limiter rule in parallel (#411 and #412). The owner merged #412; the five-minute cap from
  the other was carried into #416.

## Consequences

- **Undoing it quietly brings back passes that rest on an answer the app never gave**: 29 when this was built, 36
  by the table today, each crediting a requirement because something was refused.
- A run behind a rate limiter takes longer: up to a minute per limited request, five minutes in all.
- An app that crashes, or whose limiter will not let up, gets not assessed where it once got a pass, with the reason.
  That is the intended cost.
- Not tested end to end against a real app behind a real limiter; the tests use the fake app's switches. The checks
  of the sign-in provider (`oidc.rs`) and of the app's own MCP server were not looked at for the limiter reading.

## How it is held

In `crates/sv-check/src/signed_in/mod.rs`: for the limiter, `a_limiter_that_answers_once_is_waited_out_and_the_refusal_is_the_apps`,

`a_limiter_asking_for_an_hour_is_waited_a_minute`, `a_real_finding_is_kept_through_a_persistent_limit_and_flagged`,

## Later, 5 October 2026: a delay counts as pushing back only when every attempt past the limit shows it

The password-guessing (V6.3.1) and code-guessing (V6.6.3) checks also count an attempt past the stated limit that
took markedly longer as the app pushing back. Until the deep review's H16 that was one time against one: the last
attempt against the first, each including the time `docker exec` takes to start the request, so one slow start
credited a limiter that was not there, and a slow first answer hid one that was. Built by session securevibe-e9 at
the owner's asking, in branch `claude/securevibe-e9-h16`.

- **The baseline is the quickest attempt within the limit,** since the container's time only ever adds.
- **Two attempts are made past the limit, and both must be markedly slower** (four times as long, and at least
  900ms longer). For passwords, the sign-in page fetched beside each must not be as slow, since no limit on wrong
  passwords slows it.
- **One slow and one not, or a slow page beside them, is not assessed, never a pass or a finding,** with the times.
  A different answer, or a refusal, still settles it as before.
- **Each check now makes the number allowed plus two attempts**, and the most it will make is 26.

Held by `a_delay_counts_only_when_every_attempt_past_the_limit_shows_it`,
`an_app_that_slows_every_attempt_past_the_limit_is_credited_and_one_slow_attempt_is_not`
(`crates/sv-check/src/signed_in/signin.rs`), and
`a_code_guessing_delay_counts_only_when_both_codes_past_the_limit_show_it` (`crates/sv-check/src/signed_in/codes.rs`).
The time is still measured from outside the container; timing the request inside it would take the container out
of the number altogether, and is not done.

## Later, 5 October 2026: nor is a refusal to somebody signed out, or without the page's token

`probe.action-done-twice` now sends its copies as two users (DESIGN, "Later, 5 October 2026: two users, not one"), and
credits the action when one user's copies go through and every copy from the other is refused. The crash sweep found
that a second user whose sign-in or token had silently failed was refused for that, and the refusal credited. The same
rule as this record's, one step further: a refusal counts only from somebody shown signed in, holding the token the
request asks for, and still signed in afterwards. Otherwise the check is not assessed, saying which was missing.

## Later, 5 October 2026: a sign-in the limiter refuses is named, and the credits stay withheld

When the limiter is still answering a request to the sign-in path after the wait, `Patient` notes it as a refused
sign-in, and the run adds one gap naming those sign-ins: the limit working, not the app failing the checks or
securevibe.toml being wrong, with what to change. A first user's sign-in refused this way no longer reads as a mistake
in securevibe.toml. This record's rule is unchanged: every credit is still withheld while the limiter answers
anything, because a refused sign-in can look exactly like a refusal a check is waiting for. DESIGN, "Later, 5 October
2026: a sign-in the app's limit refuses is named, and the spec says how many there are".

## Later, 7 October 2026: a page shell is neither the private page served nor refused

From the gap analysis (`docs/GAP-ANALYSIS.md`, 2.2; BACKLOG, item 8). A single-page app, the kind a React or Vite
build makes, sends everybody the same page for every address and draws it in the browser from what it fetches next.
So `/account` answered a stranger 200, and `probe.private-page-anonymous` reported a private page served to anyone,
high, when nothing private had been sent. Every check that needed the signed-in control then read "not assessed".

The same question as this record's: which answers are the app's answer to the question asked. Before the private
pages are asked, the front page (`/`) is asked once, as nobody. A private page whose answer to nobody is a success
with exactly the front page's body, short enough to have been kept whole (under `sv_check::probes::KEPT_CHARS`), is
the page shell: it is not judged, and every check after this one is given the private pages that are left. A body as
long as the kept part is never taken for a shell, because a server-rendered page may only begin as the front page does.

When every private page is a shell, V8.2.1 is not assessed, saying which pages and to list the addresses the page
fetches (`/api/me`) under `private` instead; the spec says the same. When some are left, the credit names the shells
as not judged. A finding is never turned into a credit by this: a shell is set aside, not counted as refused.
`crates/sv-check/src/signed_in/mod.rs` (`is_page_shell`, `page_shell_tests`); DESIGN, "A single-page app's page shell
is not its private page".
