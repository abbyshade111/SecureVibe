# ADR-025: `sv run` has an end

**Status:** accepted. Built on 28 September 2026 in #332 (time limits on Docker calls and on the app's tests, and Ctrl-C
that cleans up), #336 (a test limit `securevibe.toml` can set, and cleanup after a run killed outright), and #369 (a run
that fails still says what it removed). Written down here on 4 October 2026, because the first weekly review of the
decision records found it had no record (BACKLOG, "Records owed", item 5). Its reasons are in DESIGN, "A run has an
end, and Ctrl-C cleans up".

**Governs:** `crates/sv-run/src/lib.rs`, `crates/sv-run/src/cleanup.rs`, `crates/sv-run/tests/interrupt.rs`,
`crates/sv-run/tests/leftovers.rs`, `crates/sv-run/tests/limits.rs`. A pull request that changes any of these changes
this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv run` and `sv report --run` start the app in containers on a network with no way out (ADR-019), run its tests, and
ask it questions. The review of 27 September 2026 found that nothing bounded a run: "a suite that hung hung the whole
run", and Ctrl-C left the run's containers and network behind. No particular hung run is recorded; the fault was found
by reading.

## Decision

- **Every Docker call has a time limit**: 20 minutes (`DOCKER_CALL_LIMIT`, `crates/sv-run/src/lib.rs`), generous on
  purpose, since `docker run` may download an image: "the point is that a run never waits forever, not that it hurries".
  A call that runs out is stopped and reported as having failed, saying why. Calls that tear down have their own
  two-minute limit.
- **The app's tests have a time limit**: 10 minutes (`TEST_LIMIT`), which `[stack.run] test-time-limit` in
  `securevibe.toml` can change. A suite stopped at the limit is reported as stopped, not failed, and **credits
  nothing**, whatever it printed before it was stopped: what a run got to before it was cut short is not a report of
  the app.
- **Ctrl-C tears down.** The first Ctrl-C (or SIGTERM) stops the command in progress and starts no new one; the run then
  removes its containers and network as it would at its end, writes no report, and exits with status 130. A second one
  exits at once. Each command runs in its own process group, and stopping one stops the group: "Stopping only `sh -c`
  left its children running, still holding the output open, so the run waited for them anyway."
- **A run killed outright is cleaned up by the next.** Everything a run creates carries a label naming this computer
  and the run's process. The next run removes containers and networks with that computer's name whose process has
  ended, and nothing else: not another running `sv`, not one on another computer sharing the Docker service, and nothing
  unlabeled. When it cannot tell whether a process is alive, it treats it as alive, "so nothing is ever removed on a
  guess". What it removed is said on the terminal and in the report, also when the run then fails.

## Alternatives considered

- Nothing is written down as considered for the limits, the signal handling, or the process groups. In particular, no
  record says why a library for signal handling was not used in place of the C library calls below.

## Consequences

- **This is where all five of `sv`'s `unsafe` blocks came in** (ADR-020), each a direct call into the C library:
  installing the handler for Ctrl-C (`signal`), exiting from inside it (`_exit`, since only such calls are safe in a
  signal handler), stopping a process group (`kill`), asking whether a process is alive (`kill` with signal 0), and
  reading the computer's name (`gethostname`). The handler is needed because a signal ends a Rust program without
  unwinding, so no cleanup written as a `Drop` would run.
- **The cleanup relies on panics unwinding.** The containers are removed by `Teardown`'s `Drop`
  (`crates/sv-run/src/docker.rs`), which runs when a check panics only because the release build unwinds; ADR-019 says
  what that rules out.
- A test suite that legitimately needs longer than 10 minutes needs `test-time-limit`; until then it credits nothing.
- A run behind a slow image download can take up to 20 minutes per call before it says so.

## How it is held

`ctrl_c_ends_the_run_and_the_teardown_still_runs` (`crates/sv-run/tests/interrupt.rs`, a test program of its own
because a signal reaches the whole process), `a_suite_that_hangs_is_stopped_at_the_limit_and_the_run_still_cleans_up`
(`limits.rs`), and `a_run_first_removes_what_a_stopped_run_left_on_this_machine_and_nothing_else`,
`the_limit_securevibe_toml_sets_is_the_one_a_suite_is_stopped_at`, and
`a_run_that_fails_after_removing_leftovers_still_says_what_it_removed` (`leftovers.rs`), against real containers where
Docker is present. Unit tests in `crates/sv-run/src/lib.rs` and `cleanup.rs` hold the limits, the process groups, the
label, and which leftovers count as this computer's.

## Later, 4 October 2026: a run's output has an end too

A run had an end in time but not in size: every command `sv` ran was read to its end, so an app answering with
gigabytes, or a test suite printing without end, could fill this computer's memory before any time limit came
(the deep review, S9). The bounded runner in `crates/sv-run/src/lib.rs` now keeps at most 32 MB of each stream a
command prints, and reads and drops the rest, so the command is never left waiting on a full pipe. Output that was
cut says so. A Docker call whose output was cut is refused, as one that ran out of time is, so a check never judges
the app on the start of an answer. A test suite's output is shown cut and its exit code still counts. Held by
`output_past_the_limit_is_read_and_not_kept`. The limits on the containers themselves are ADR-019's.
