# ADR-056: An error answer is credited only when the app was made to give one, and it was clean

**Status:** accepted, 8 October 2026, in the pull request that builds it. Proposed the same day with the backlog
claim (BACKLOG, gap analysis item 3; `docs/GAP-ANALYSIS.md`, 1.6). Taken up by session securevibe-e9 at the owner's
"pick your next backlog item".

**Governs:** `crates/sv-check/src/probes.rs`, `crates/sv-cli/src/lib.rs` (the program's main.rs until 9 October 2026; see the Later
entry of that date). A pull request that changes either changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

`probe.error-detail-leak` asks the running app for a page that does not exist and looks for a stack trace in the
answer. When there is none it credits V16.5.1 (errors answered with a generic message) and V13.4.2 (debug mode off).
It credited both in 177 of about 190 trial builds that started. But frameworks show their traces when the app's code
fails, not when a page is missing: Flask's debugger, Django's yellow page, and Express's default error handler in
development all stay silent on a 404. A clean missing page shows neither requirement met.

## Decision

1. **The missing page still finds.** A trace on the 404 stays a finding, as now.
2. **The app is made to fail, without changing anything.** Signed out, `sv` sends a body that is not JSON, marked
   as JSON, to the routes securevibe.toml names that read a body (sign-in, sign-up, and `owned`'s create), and to the
   health path and the root. A body that does not parse cannot create anything, and signed out nothing is reached
   past the sign-in. A trace in any answer is a finding.
3. **Credit needs an error answer.** V16.5.1 is credited only when at least one of these answers was an error the
   app produced (400, 422, or 500 to 599 other than 501), and no answer to any of them, the missing page included,
   carried a trace. V13.4.2 is credited only when one was a server error (500 to 599 other than 501) and was clean:
   a debug page shows on a failure, and a framework's clean "bad request" says nothing about whether debug mode is on.
4. **No error, no credit.** When no request drew an error, both stay not assessed, and the report says the app was
   asked for a missing page and sent bodies that do not parse, and answered without failing.

## Alternatives considered

- **Keep crediting the 404.** What the gap analysis found wrong.
- **Guess routes and send ids that are not numbers.** Without the app's routes these are guesses; with `owned`'s read
  route the request is signed out and refused before the id is read. Left for later, signed in.
- **Credit V13.4.2 from any clean error.** Flask answers a body it cannot parse with a plain 400 whether debug mode is
  on or off.

## Consequences

Most apps lose both credits from the missing page alone. Apps whose code fails cleanly on a bad body keep V16.5.1,
and V13.4.2 when that failure is a server error. Apps that print a trace for a bad body, as Express does in
development, are now found.

## As built

- **The requests.** `requests` sends the body to the health path and the root (`bad_body_request`), and
  `error_requests` to the routes `sv-cli`'s `body_routes` takes from securevibe.toml: `signup`, `login`, and `owned`'s
  `create`, each with its own method. A route with a placeholder in its path (`{id}`) is left out. Each request's id
  is `bad-body` with its method and path, which the report quotes. `creates` is not used: they are sent signed in,
  and a body refused signed out shows nothing they do not.
- **A sign-in route counts one failed sign-in.** A body that does not parse, sent to a sign-in route, reaches the app
  as a sign-in with no user name. Counted against a rate limit by address it is one attempt, before the signed-in
  checks sign in; it names no account, so no account is locked by it.
- **What the report says.** When no answer was an error, "V16.5.1, V13.4.2" is a gap, naming the requests that were
  answered without one; when the only errors were refusals (400, 422), "V13.4.2" is (`error_answer_gap`). A trace in
  any answer to the body is its own finding, "An error answer shows how the app is built", naming each request.

## Later, 9 October 2026: the routes it sends to are read in the library

The first step of the library move (BACKLOG, "From the architecture assessment of 8 October 2026", item 12; design
entry "The report's assembly in a library under sv") took `body_routes` and `anonymous_requests`, which choose the
routes the unreadable bodies are sent to, from `crates/sv-cli/src/main.rs` to `crates/sv-cli/src/lib.rs`, unchanged.
The Governs line follows them. What is sent, and what is credited, are as decided above.
