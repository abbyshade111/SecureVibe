# ADR-034: A report is offered as `sv`'s only when its seal shows `sv` wrote it

**Status:** accepted. Built on 5 October 2026 by the cato-pipeline session, at the owner's asking, for the deep
review's R9 (medium, reproduced), and accepted by the owner the same day when asked, knowing its cost: reports
written before it, or on another computer, by CI, or in a container now gone, are no longer offered over MCP until
they are written again; they stay readable on disk. The owner kept the key the test runs had made on their computer.

**Governs:** `crates/sv-cli/src/report_seal.rs`. A pull request that changes it changes this record too, or says in
its description why it does not (`docs/adr/README.md`).

## Context

`sv mcp` offers the reports below its root to the AI coding tool as resources, each described as "a report sv
wrote". It took any folder holding the marker `.securevibe-report` as one. Anything can write that marker, so the
review offered the tool a forged report, one that said whatever its writer liked, as `sv`'s own. H6 of the same
review had already made the walk of the app believe the marker only in a folder holding nothing but the files `sv`
writes, so a marker cannot hide code; a forged report is exactly such a folder, so that rule cannot tell it apart.
The run record #589 added to `report.json` (when the run started, the hash of the `securevibe.toml` it read) is
written in the open and proves nothing about who wrote it. The fix asked for "a marker that proves sv wrote it".
Nothing written in the open can prove that; a key kept outside the app can, as far as the review key already does
(ADR-026).

## Decision

- **`sv report` and `securevibe_write_report` seal what they wrote.** Once the five report files are written, while
  the run still holds the folder, the marker is written again with one more line, `seal: v1:<key id>:<mac>`: an
  HMAC-SHA-256, over each report file's name and SHA-256 in a fixed order, under this computer's report key.
- **The report key** is `report-key` beside the review key, in `~/.config/securevibe` (or under `XDG_CONFIG_HOME`),
  made with the review key's own care (32 bytes from the system's randomness, the folder private to its owner, never
  printed), the first time a report is written. `sv report` says on its error stream when it made it. It is a key of
  its own, not the review key, because the review key exists only where a person has run `sv review`, and on a
  computer with no review key a sealed entry counts unchecked (ADR-026): `sv report` making that key on CI would make
  every entry sealed on the owner's computer a proposal there. Its seals are made over a different domain string
  from the review key's, so neither can stand for the other.
- **The MCP server offers a report folder only when** it holds nothing but `sv`'s files (H6, `is_sv_output`), its
  marker holds a seal, this computer has a report key, the seal names that key, and it matches the files as they are
  now. A file is handed over only if what was read hashes to what was sealed. Any other folder is not listed, and
  reading a file in it is refused with why: "sv cannot show it wrote the report in that folder (…)".
- **A report that could not be sealed is still written and complete.** `sv report` says, and
  `securevibe_write_report`'s reply says, that it could not be sealed and so will not be offered as `sv`'s.
- **What humans read is unchanged.** The five report files are byte for byte what they were; only the marker, a
  hidden file, gains its line.

## Alternatives considered

- **H6's rule alone** (a folder of nothing but `sv`'s names). It is what the walk of the app uses, and it is kept
  here as the first condition, but a forged report meets it.
- **The run record**, or hashes of the files written into the marker without a key: anyone who writes the files can
  write those too.
- **Offering unproven reports with a warning in their description.** Set aside: the point of R9 is that the tool
  reads text it should not trust as if it could. A report `sv` cannot vouch for is better opened by the person.
- **The review key.** Set aside, as above, for what it would do to ADR-026 on CI.
- **Public-key signatures**, so a report could be checked on any computer: the same reason as ADR-026 gives.

## Consequences

- **Reports written before this change are not offered** until written again. One `securevibe_write_report` or `sv
  report` brings them back.
- **A report written on another computer, by CI, or in a container since gone, is not offered**: this computer
  cannot check its seal, and a made-up one would look the same. The person can still open it.
- **Any change to a report file**, or a file of anyone else's put in the folder, stops it being offered.
- **The seal stops the easy way, not every way.** Something running as the person could read the key and seal a
  forgery. What the seal stops is a report shipped in the app's own files, or written by anything that only writes
  into the app.
- **`sv report` writes one file outside the app, once per computer**: the key. That includes CI machines and the
  computer running `cargo test` for `sv`, whose tests run `sv report` (the MCP server's own tests keep their keys in
  a folder of their own).

## How it is held

In `crates/sv-cli/src/mcp/tests.rs`: `a_report_is_offered_as_svs_only_when_its_seal_shows_sv_wrote_it` (a real report
offered and read; an unsealed forgery, a forgery carrying the real report's own marker, a forgery sealed with another
key, and the real report with one file changed, each neither listed nor read, with why; a file put beside the real
report takes it off the list), `a_written_report_is_offered_as_resources_and_reads_back_as_written`, and
`nothing_but_the_files_of_a_report_sv_wrote_can_be_read_as_a_resource`. In `crates/sv-check/src/seal.rs`, the review
seal's own tests, unchanged.

## Later, 6 October 2026: the seal is of the bytes written

The review of 5 and 6 October (item 17) found the seal made from the report files read back after writing, so a file
changed between the writing and the sealing would have been sealed as `sv`'s, the very writer this record says the seal
stops. The seal is now made from the bytes `sv` wrote; the files are still read back and compared with it whenever a
report is offered, so such a change is found there. The decision stands.
