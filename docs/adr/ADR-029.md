# ADR-029: Exit codes: 2 only when a check could not run, 1 only when asked, 3 when `sv` failed

**Status:** accepted. Decided by the owner on 4 October 2026, after the deep review of `sv` at `eff3f17` found that
`sv check` and `sv report` exited 0 whatever happened (R6, high for CI users), and after measurements showed that the
review's suggested fix would fail every pipeline. Built the same day in branch `claude/r6-exit-codes`.

**Governs:** `crates/sv-cli/src/exit.rs`, `crates/sv-cli/tests/exit_codes.rs`. A pull request that changes either of
these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv audit` already had a status a CI job could act on: 0 when everything was compared and nothing matched, 1 for a
known vulnerability, 2 when the comparison did not cover the whole app. Its "not assessed" is narrow, so 0 is
reachable. Any error also exited 1, the same as a vulnerability. `sv check` and `sv report` exited 0 with findings,
with files they could not read, and on an empty folder.

The review suggested `sv audit`'s convention for both. Measured before building it, on the five apps in `examples/`
and on apps made with `sv init`, a plain static run would have exited nonzero on every one: `sv check` always finds
the low "There is no way to report a security problem" (1), and always has two to four "not assessed" checks that
need a Dockerfile, a git repository, a package manifest, or a `.gitignore` of the app's own (2). `sv report` always
has 121 to 230 requirements "not verified by anything" (2). A status that is never 0 says nothing.

## Decision

- **By default, `sv check` and `sv report` exit 0 when they finished, and 2 when a check could not run.** The list
  is exact (`exit::Gaps::of_files`): no file of the app read as text (apart from `securevibe.toml` and
  `security-notes.md`); a file or folder that could not be opened or read, or was too large to read even in pieces;
  a file in a language the code rules read that was not opened; a file the parser could not make sense of; a
  language present that nothing reads; a code rule whose query would not compile. For `sv report`, also `--run`
  given and the app could not be started, since every check of the running app was asked for and none ran.
- **Not on the list:** a file that was read and is not text, such as an image (every web app has one); a check that
  needs something the app does not have (a Dockerfile, a git repository, a manifest); requirements nothing verified;
  questions nobody answered.
- **`--fail-on WHAT`**, on both commands, opts in to more. `attention` exits 1 for a finding of low severity or worse,
  `attention:SEVERITY` for that severity or worse (critical, high, medium, low, info); `not-assessed` exits 2 also
  for a symbolic link not followed or an entry that is not an ordinary file, and in `sv report` for a `--tools` tool
  that did not run or ran only in part and an `--advisories` comparison that did not cover the app; `any` is both.
  Several are separated by commas. 1 outranks 2. Accepted risks still count, as they do everywhere else.
- **3 when `sv` itself failed**, from every command: no `securevibe.toml`, a manifest it cannot read, a folder that
  is not there, an advisory database it cannot open, an option it does not know. This moves `sv audit`'s errors from
  1 to 3, a deliberate small breaking change; its 0, 1, and 2 keep their meaning. Ctrl-C keeps 130.
- **The MCP tools are unchanged.** `securevibe_check` and `securevibe_write_report` return text and `isError`, which
  is set only when a call is refused; nothing in them is an exit status, so there is nothing for `--fail-on` to set.

## Alternatives considered

- **`sv audit`'s convention as written.** Every app measured would exit 1 or 2 on every run.
- **Nonzero only for findings.** Still 1 on every app, for the low security.txt finding, unless a threshold is set,
  and it leaves the review's empty-folder case at 0.
- **An opt-in flag for everything, 0 by default.** Leaves a run that read nothing looking like a clean one, which is
  what "Evidence is honest" forbids.

## Consequences

- On the apps measured on 4 October 2026, a default run exits 0 on all five examples and on four of five real apps
  with a manifest; the fifth exits 2 for a web page whose script could not be taken out to be read.
- A run whose file the parser could not read now exits 2, though its findings still stand: that is the price of
  H25 (one parse error silences every code rule), and the status says so rather than hiding it.
- A CI job that treated any nonzero `sv audit` status as "vulnerable" now sees 3 for a broken run, which it should
  treat as a failure too.

## Later, 6 October 2026: `sv run` exits 2 when the app could not be run

The documentation review of 6 October 2026 (item 4) found that `sv run` printed "Not assessed" and exited 0 when the
app could not be started or never answered, since this record covered only `sv check`, `sv report`, and `sv audit`. A
CI job read that as a run that went well. **The owner decided the same day** that `sv run` exits 2 then, as the other
commands do when a check could not run: nothing about the running app was checked, which is not a failure and not a
pass. It exits 3 when `sv` itself failed (no securevibe.toml, a manifest it cannot read, an option it does not know),
as every command does, and 0 when the app ran, whatever was found. `--fail-on` is not taken by `sv run`.

Held by `an_app_listening_on_loopback_is_warned_about_and_named_as_the_likely_cause` (exits 2, with a container
backend and without one) and `the_same_app_listening_on_every_address_answers_and_is_not_warned_about` (exits 0, its
control), both in `crates/sv-cli/tests/loopback_start.rs` and run against real containers.
