# ADR-015: What the owner says can add requirements and never remove one, and silence is not a "no"

**Status:** accepted. Decided with `sv`'s design (DESIGN, "Claims, and what corroborates them"), narrowed on
26 September 2026 (DESIGN, "Finding nothing does not answer for the owner"), written down here on
27 September 2026.

**Governs:** `crates/sv-frameworks/src/applicability.rs`, `crates/sv-frameworks/src/condition.rs`,
`data/tech-signatures.json`, `crates/sv-manifest/src/lib.rs`, `data/applicability-v2.json`,
`data/claim-corroborators.json`. A pull request that changes
any of these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

Which requirements apply to an app depends on about twenty-five yes-or-no facts about it: does it have
sign-in, take uploads, take payments, use AI, and so on. v1 learned these from its wizard. `sv` has no
wizard. The owner's AI coding tool writes them into `securevibe.toml`, and `sv` reads the code to check
them.

Getting one of these wrong in one direction is harmless: the owner is asked to meet a requirement they did
not need. Getting it wrong in the other direction is the failure that matters: a requirement the app needed
is reported as "not applicable", and nobody looks at it again.

## Decision

Each answer in `securevibe.toml` is a **claim**, and `sv-manifest::resolve` combines it with what the code
shows:

- **Either one saying yes is a yes.** A claim of "no" cannot switch off a requirement the code shows
  applies; the code wins, and the disagreement is a finding. A claim of "yes" is honored even when nothing in
  the code shows it.
- **A "no" needs the owner.** It takes effect only when the owner wrote it and nothing in the code
  contradicts it.
- **Silence stays silence.** When the owner has not answered, the requirements that turn on the answer are
  *not assessed*. This holds even when the scan looked and found nothing, because not finding a CI file in
  the copy `sv` read is not finding the pipeline absent.

There is one place where the scan's silence does remove requirements, and it is deliberate: the **derived**
conditions, which the owner is never asked, such as whether the app parses XML or serves GraphQL. The code
answers those, and when it finds nothing, the answer is "no". It is limited to technologies that always leave
a trace: a library in a manifest, or a standard-library import in the source. The matching is loose on
purpose (`data/tech-signatures.json`), because matching too much only ever adds requirements.

## Alternatives considered

- **Infer every answer from the code.** Sign-in can be written from a hash function and a database table and
  leave no library behind. Answering "no sign-in" because no sign-in library appears would switch off
  fifty-three ASVS requirements on the strength of a missing dependency.
- **Take the manifest's word.** A careless or over-confident manifest would then become an over-confident
  report.
- **Let a scan that found nothing answer for a silent owner.** This was the rule for `ci-cd` and `iac` until
  26 September 2026. On a manifest that answered nothing, it marked twelve requirements not applicable while
  the claim's own note said that finding nothing "is not the same as finding it absent".

## Consequences

- An owner who leaves a question unanswered sees requirements *not assessed* rather than excluded. The
  report looks less complete, and it is accurate.
- A wrong "yes" costs the owner work. A wrong "no" is caught whenever the code shows the capability, and is
  otherwise the owner's own statement, shown as theirs.
- The derived conditions are the exception, and they need watching. A technology added to the list has to
  be one that cannot be used without leaving a trace, or its "no" is a guess.
- Enforced by tests on `resolve` in `crates/sv-manifest/src/lib.rs`, and by one that runs `sv report` on a
  bare manifest. Putting the pre-26-September line back fails both.

## Later, 8 October 2026: `data/applicability-v2.json` is governed by this record

The backlog's gap analysis item 31 (`docs/GAP-ANALYSIS.md`, 7.3), taken by session securevibe-e9. The file holds the

## Later, 9 October 2026: infrastructure and CI files are looked for wherever an app keeps them

The gap analysis of 7 October 2026, finding 16 (`docs/GAP-ANALYSIS.md`, 3.8), the corroborators half, taken by session
securevibe-e2. `iac` and `ci-cd` are the only claims whose absence is an answer (`absenceIsEvidence` in
`data/claim-corroborators.json`), so the files they look for decide what "nothing found" means. `Dockerfile`, the
compose files, and `Chart.yaml` were looked for only at the root, and an app with its Dockerfile in `deploy/` was
answered "nothing found", which agreed with an owner who had said "no infrastructure configuration".

A file pattern `**/name` now matches a file or folder of exactly that name at any depth (`matching_path` in
`crates/sv-scan/src/lib.rs`); a name that merely ends in it does not match, and folders the scan does not enter, such
as `node_modules`, still count for nothing. `iac` uses it for `Dockerfile`, `Containerfile`, `docker-compose.yml`,
`docker-compose.yaml`, `compose.yaml`, `compose.yml`, and `Chart.yaml`, and adds `cdk.json`; `ci-cd` adds
`.travis.yml`, `cloudbuild.yaml`, `cloudbuild.yml`, and the `.buildkite` folder. The rule of this record is unchanged:
finding a file is a yes, and finding none still answers only an owner who said no. The change is in the direction this
record cares about: fewer apps are answered "nothing found" when they have the files. `data/claim-corroborators.json`
carries this record's rule and was governed by no record; it is added to the Governs list. Tests:
`crates/sv-scan/tests/corroborators_any_depth.rs`.
