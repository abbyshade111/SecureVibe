# ADR-023: False alarms and accepted risks a person records, and test code's findings listed apart

**Status:** accepted. Asked for by the owner on 27 September 2026, after an investigation of false alarms; built the
same day and the next in #297 (fewer false alarms reach the owner), #303 (a person's record that a finding is wrong,
or accepted, with the owner's five decisions), and #316 (findings in Rust test code listed apart). Written down here
on 4 October 2026, because the first weekly review of the decision records found it had no record (BACKLOG, "Records
owed", item 3). These change what the report counts, so the limits on them need their reasons.

**Governs:** `crates/sv-check/src/review.rs`, `crates/sv-check/src/finding.rs`, `crates/sv-check/src/bundled.rs`,
`crates/sv-report/src/sarif.rs`. A pull request that changes any of these changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

With an AI coding tool in the loop, a false alarm is not noise. In the owner's words that day, "the tool rewrites
correct code until the warning stops": two false alarms rated high had already changed correct code. The
investigation also found no way to set a finding aside, the same line reported twice by two tools, findings in test
code that looked like the app's own, and a confidence value no report showed. The v2 self-assessment found that 189 of
the 252 findings on `sv`'s own code were in its tests.

## Decision

A person can record, in `securevibe.toml`, that a finding is a false alarm or an accepted risk, and the report shows
both and credits neither.

- **The entry.** `[[finding-review]]` with `rule`, `file`, `fingerprint`, `verdict` (`false-alarm` or
  `accepted-risk`), and, for it to count, `why`, `by`, and `on` (`crates/sv-check/src/review.rs`).
- **A false alarm** leaves the list of things to fix for a section of its own, "Set aside by a person", with its
  reason. **An accepted risk** stays on the list, marked with who, when, and why.
- **Neither credits anything**: "a person's word that it was wrong does not show the protection is in place". When a
  false alarm was a requirement's only finding, the requirement shows whatever else is known about it, never *checked*.
- **Only a person's word counts.** An entry by the AI coding tool, or by nobody named, is listed as the tool's proposal,
  and the finding still counts. The reason, from `review.rs`: "a switch that makes a warning stop is the easiest rewrite
  of all." This follows ADR-022.
- **The limits.** A key or password can be a false alarm only with a reason of at least 80 characters, against 40 for
  anything else, and can never be an accepted risk: a real key is replaced and taken out of the code, and one that is
  not real is a false alarm. (That last rule was the building session's choice, beyond the owner's five decisions.) An
  entry matches by a fingerprint of the rule, the file, and the text of the flagged line, so moving the line keeps it
  and changing the line ends it; only the hash is kept, so the line a key was found on is never copied into
  `securevibe.toml`. An accepted risk lapses after 90 days, as does a false alarm about a finding with no line of code
  to watch. An entry that does not count (a proposal, no date, a date to come, a short reason, a lapsed one, one whose
  fingerprint no longer matches) is listed with why: "Nothing is dropped quietly."
- **Findings in test code are listed apart and still count.** Named by path, and in Rust by reading for `#[cfg(test)]`
  and `#[test]` modules. They come after the app's own: "a key in a test is still a leaked key and a pattern in a sample
  still gets copied. This moves findings down the page; it does not lower the bar."
- **In SARIF**, every result carries a fingerprint, a false alarm is marked suppressed so GitHub shows it dismissed,
  and an accepted risk is not suppressed.

## Alternatives considered

- **Leaving test code out of the scan.** Implicitly set aside: test code is "named, not skipped".
- Nothing else is written down as considered and rejected.

## Consequences

- **Trust rests on the name in `by`**, which `sv` cannot check (ADR-022).
- Any edit to a flagged line brings its false alarm back, to be looked at again.
- An accepted risk has to be dated again every 90 days to stay accepted.
- A false alarm can never lift a requirement to *checked*.
- Findings in test code still count against their requirements, so a report on an app whose only findings are in its
  tests does not read as clean.


## Later, 4 October 2026: an entry counts only when `sv review` recorded it

ADR-026 changes part of this record. "Only a person's word counts" now means an entry recorded through `sv review`,
which seals it: an entry written into `securevibe.toml` any other way, `by = "owner"` included, is a proposal and the
finding still counts. "Trust rests on the name in `by`" no longer holds on a computer with the review key; on one
without, such as CI, a sealed entry is taken on trust and the report says so. The section the report lists them in is
now "Set aside in securevibe.toml", not "Set aside by a person" (#578).

## Later, 5 October 2026: one entry names one finding, and says whether its rule looked

The deep review's A2 and R3 change "An entry matches by a fingerprint of the rule, the file, and the text of the
flagged line" and "one whose fingerprint no longer matches". The fingerprint, for a finding on a line of code, now
also reads the lines above that set a name the flagged line uses, and which of the lines with all of that the same
it is, so two identical lines each need their own entry, and a false alarm also ends when a line that sets a value
the flagged line uses changes. It starts `v2-`. An entry in the earlier form (sixteen hex characters) still matches
the finding it did when only one finding is on a line with that text, and when several are it matches none and says
so; nothing that held is dropped quietly, and seals are unchanged. An entry that matches no finding now says which of
three things happened: gone (its rule looked at its file), not looked for this time (with why), or unknown to this
version; only the first suggests removing it. DESIGN, "A review names one finding, and says whether its rule looked".

## Later, 5 October 2026: one entry answers for one finding

The deep review found that two entries for the same finding were each applied (R11): the same answer twice set the
finding aside twice, and opposite answers made it a false alarm and an accepted risk at once. Now each entry that
counts takes the first finding it matches that no earlier entry has taken, so two identical lines with an entry
each are both answered. An entry that counts and finds its findings already taken either repeats the earlier answer,
and does not count, saying it adds nothing, or contradicts it, and then neither counts and the finding stands until
one of them is removed. An entry that does not count takes no finding, so a sealed entry after an unsealed one still
answers. DESIGN, "One entry answers for one finding".

## Later, 5 October 2026: the fingerprint is of the line with the credential masked

"Only the hash is kept" did not keep the line secret. The report shows a credential's rule, its first four characters,
and its length, so the rest of a short one could be guessed and each guess hashed until one matched the fingerprint:
the deep review recovered a test password in 190 guesses (R4). The fingerprint is now the hash of the rule, the file,
and the line with every credential the secret rules find masked, as the report shows it, so it tells nothing the
report does not. A line with no credential reads the same masked, so its fingerprint and its entries are unchanged.
An entry recorded by an older `sv` for a line holding a credential no longer matches, and is listed as not counting,
saying so and to record it again with `sv review`. DESIGN, "A credential's fingerprint says nothing the report does
not".

## Later, 5 October 2026: an earlier fingerprint on identical lines answers for none of them

The owner's decision, the same day, on the one case where R11's rule above and A2's ("one entry names one finding,
and says whether its rule looked") disagreed: an entry whose fingerprint is in the form used before 5 October 2026,
which named a line by its text alone, and which matches findings on several lines that read the same, answers for
none of them and says so ("which one it means cannot be told"), rather than taking the first in order. Everything
else in R11's rule stands, for entries in either form: each entry that counts takes the first finding it matches that
no earlier entry has taken; a repeat adds nothing; a contradiction leaves the finding standing. For an entry in
today's form the taking rarely matters, since identical lines have fingerprints of their own. Held by
`an_entry_with_the_earlier_fingerprint_matches_its_one_finding_and_says_when_it_cannot_tell` and
`one_entry_answers_for_one_finding_and_a_pair_that_disagree_leaves_it_standing` (`crates/sv-check/src/review.rs`).

## Later, 5 October 2026: today's fingerprint and the earlier one given beside it are masked too

Merging A2 with R4: today's fingerprint (`v2-...`) reads the flagged line and the lines above it that set a name it
uses, and every one of them is masked as R4 masks a line before it is hashed, so a credential assigned on a line above
is protected as one on the flagged line is. `earlier_fingerprints`, given for a tracker to carry a finding over, is
only ever the masked earlier form, R4's; the form an `sv` before R4 gave a credential's line is never computed except
to tell an old entry that it must be recorded again, and never kept or shown; the note telling that entry so names it
by rule and file only, without the old hash it holds. DESIGN, "A review names one finding, and says whether its rule
looked".

## Later, 6 October 2026: a copy of another project's library is listed apart too

Semgrep follow-up 1 (BACKLOG). Of the 555 false alarms measured over 25 apps on 4 October 2026, 315 were in copies of
libraries kept inside the app (jQuery, Bootstrap, Moment.js in `public/`, `static/`, `assets/`), and none of the true
findings. Such a file is now listed apart from the app's own code, as test code is, and on the same terms: it still
counts toward its requirements, and nothing about it is hidden. Each of its findings names the library and, when the
file says, its version (`Finding::bundled_library`, `crates/sv-check/src/bundled.rs`), and says the fix is a newer copy
or loading it from its package, never an edit.

A copy is known by the library's own file, as retire.js knows one: a string only that library writes in its first
512 bytes, or the comment the file opens with naming a version (`/*! jQuery v3.6.1 | …`). Not by the file's name, and
not by long lines, which the app's own built code has too. An app's own bundle with a library further down is the
app's. Measured on 6 October 2026: of the real library files at hand (Debian's jQuery and Underscore, and the browser
builds in this repository's `node_modules`), every one with such a banner or string is named, and none of the 661
JavaScript, TypeScript, and CSS files of this repository and v1 is. The headings say "in test or sample code" as before
when no library is among them. DESIGN, "A copy of another project's library is listed apart".

## Later, 6 October 2026: one finding per line of code

The owner's decision, 6 October 2026 ("Yes, please go ahead with both of those"), asked whether to reverse the rule
that findings with no CWE in common on one line stay apart (Semgrep follow-up 3). The false-alarm measurement of 4
October found 309 of 868 findings on a line another rule had already named. Now, after what a person set aside is
applied, what is left on one line of one file is one finding (`finding::one_per_line`):

- The most severe leads, chosen as the merge of one weakness already chooses (then `sv`'s own rule, then the surer).
  It names every requirement and CWE of the others, so each still counts against what it is evidence about.
- Each other problem is kept whole in `Finding::also_on_this_line`, with its own rule, words, and fingerprint. The reports say
  each beside the line, with `sv`'s own rules' titles and fixes; an outside tool's rule is named, not quoted.
- Reviews stay per problem. They are applied before the gathering (`decisions_then_reviews`), so a false alarm or
  accepted risk recorded for one rule never sets aside another problem on the same line, and each can be set aside
  on its own by its fingerprint.
- SARIF keeps one result per problem, for the tools that read it.
- Findings without a line of code (the running app, settings, the test suite) are left as they are.

The merge of one weakness from two tools (`merge_same_place`) is unchanged and still runs first. DESIGN, "One finding
per line of code".
