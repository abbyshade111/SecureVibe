# ADR-030: A plan before any code

**Status:** proposed. The owner chose on 4 October 2026 to build all eight items of "Design-time help before any code"
(BACKLOG), and asked the same day for item 3, this one, to be claimed. Written with the claim, as `docs/adr/README.md`
asks for a substantial decision; the pull request that builds it makes it accepted and says where the build differs
from this plan.

**Governs:** `crates/sv-manifest/src/spec.rs`, until the plan is built: the spec is what tells the AI coding tool to
write the brief first, and will tell it to ask for the plan. The pull request that builds the plan replaces this list
with the plan's own files. A pull request that changes any of these changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

v1 knew the app before it was written, because it wrote it: the wizard's answers decided the template's features,
and the app came out able to be tested, so v1 could run its tests and probe it. That is the strong evidence the
comparison of the two versions found `sv` has never produced on record. `sv run` can produce it, but only for an app
that gives it what it needs: a start command, a way to make test users, the sign-in and sign-out forms, the pages only
a signed-in user or an admin should see. An app built without knowing that rarely has them.

ADR-028 made the design brief, `securevibe.toml` written before any code, the first step. What the brief decides
already shapes a report: run on a folder holding only the manifest, `sv report` gives the requirements that apply,
the threats, the tests worth writing, and what only the owner can check. But it says so as a check that failed ("not
assessed", exit status 2), mixed with what only makes sense once there is code, and it leaves out the two things a
builder most needs first: the decisions to make for each feature, and what the app must give `sv run`.

## Decision (proposed)

`sv plan [PATH]`, and the MCP tool `securevibe_plan`, turn the brief into a plan, before any code and at any time
after.

- **What it reads:** `securevibe.toml`, and `security-notes.md` when there is one. It needs no code, and reads none
  for the plan. It writes nothing: it prints, and the tool returns, the plan.
- **What it says, in the order a builder needs it:**
  1. the requirements that will apply, at the brief's level, grouped by the feature that brings them in;
  2. the decisions to make before writing each feature: the design questions and notes sections that apply, and the
     design-time prompt for each, marked as the library marks it (shown to work, or not tested);
  3. the tests worth writing, each named with its requirement's id, so that once written and passing they count as
     the app's own tests do;
  4. what the app must give `sv run` so it can be tested running: the `[stack.run]` and `[stack.run.users]` entries,
     worked out from the brief's capabilities (sign-in brings the sign-in and sign-out forms and the private pages;
     admin pages bring the admin account and pages; uploads bring the upload form; and so on);
  5. the threats the brief's answers raise, from the threat model the report already uses.
- **It is computed by the report's own code** for scope, threats, and tests, so that the plan and a later report
  cannot disagree about what applies.
- **It credits nothing**, says so, and never says "passed" (ADR-006, ADR-022). A plan is not evidence that anything
  was built.
- **It is not a failed check.** With no code, it does not exit as "not assessed"; that is what a report is for.

## Alternatives considered

- **`sv report` on an empty folder.** Already gives most of the parts, but as a check that found nothing to check, and
  without the decisions or what `sv run` needs.
- **Writing the plan into the app's folder.** A file the AI tool would read and could change; ADR-017 keeps what `sv`
  writes there to what the owner asks for. Printing it, and returning it over MCP, gives the tool the plan without a
  file to keep true. Whether a written copy is wanted is for the build to ask.
- **Starter code for the run entries** (a seed script, sign-in forms). ADR-017: `sv` never writes the app's code. The
  plan says what is needed; the AI tool writes it.

## Consequences

- **A plan is only as right as the brief.** A brief that over-claims gives a longer plan, which is the safe side; one
  that leaves a capability out gives a plan without it, which the report later catches when the code shows it.
- **The plan goes out of date** when the brief changes, so it is made fresh each time rather than kept.
- **The run entries it asks for are only useful if the app provides them.** Whether builds given the plan come out
  testable is item 7's question, the larger prompts trial, which spends the owner's AI credit and is asked for first.

## How it will be held

To be written with the build: tests that the plan needs no code, writes nothing, credits nothing, agrees with the
report about what applies, and asks for the run entries each capability needs.
