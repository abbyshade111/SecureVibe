# ADR-028: Decide before you build: the design comes first, and nothing is credited for it

**Status:** accepted. Decided by the owner on 4 October 2026 ("all eight, yes", BACKLOG, "Design-time help before any
code"), after comparing v1 and `sv` for the paper. Items 1, 2, and 8 built the same day, in the pull request that adds
this record. The claim (#614) merged at 17:29, four minutes before the rule that a substantial decision's record goes
into its claim as `proposed` (#613), so this record is written with the change instead.

**Governs:** `crates/sv-manifest/src/spec.rs`, `data/design-prompts.json`. A pull request that changes any of these
changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

v1 wrote the app, so its decisions came first by construction: the wizard, the design freeze, plan → approve →
build, and eight decision records for every app. `sv` writes no code (ADR-017), and until this change everything it
handed the AI coding tool was written for an app that already exists. The MCP server's instructions named the spec,
the coding rules, and the check, and never the design-time prompts. The spec told the tool to "describe the code that
is there", and that a payment flow "planned and never written" is false.

For a folder with no code yet, that rule makes every capability false: the one direction ADR-015 exists to guard
against, because a "no" is how a real requirement gets marked as not applying. The prompts trial of 4 October showed
the other side. When `securevibe.toml` already held the limits, builds given no prompt read them and enforced them.
A decision written down before the code steers whatever tool writes it.

## Decision

`sv` helps the person decide before the code is written, through the AI coding tool they already use, and credits
nothing for it.

- **The spec has two cases.** Before any code, `securevibe.toml` is written first, for the app as it will be, each
  answer decided with the person. It is the design brief, and what the app is built to and checked against. A
  capability the app is planned to have is true: rule 2, "if unsure, say true", applied to the plan. Once there is
  code, the file describes the code that is there. A capability planned and then dropped is false, and one still to
  be written stays true. The tool changes the file before adding a capability the plan does not have.
- **The MCP server's instructions put the decisions first.** For an app with no code yet: write the brief, then
  before building sign-in, anything people create or take, logging, or a call to anything outside the app, work
  through that feature's design-time prompt with the person and write down what was decided. For an app that
  already has code, the file is still written from the code.
- **The design-time prompts are MCP prompts as well as a tool.** `prompts/list` and `prompts/get` offer every prompt
  in `data/design-prompts.json`, in both the initializing and the stateless protocol. A client shows them for the
  person to choose (Claude Code documents showing them as slash commands; not yet tried here), so choosing one stays the person's decision rather
  than the model's. Every copy says whether it was shown to work, that a prompt is an instruction and not evidence,
  and carries the credit its license asks for. The coding prompts stay with `securevibe_prompts`.
- **Prompts no check can show working are offered, marked.** Eight more design-time prompts were written: the
  design brief, when to bring in a person, the app's data, everything it talks to, safe defaults, what to do if
  something goes wrong, the rules that might apply, and re-reading the decisions before a change. Each is marked
  not tried, names no ASVS requirement (none has a check, and `tools/coverage.py` refuses a requirement without one),
  and names a Secure by Design control only where the control's own statement fits. Two name none. Answers with a
  heading of their own in `security-notes.md` go there. The rest go in `design-decisions.md`, which `sv` does not
  read: a heading that is not one of `sv`'s ends no section in the notes (read in `read_answers`; not reproduced end
  to end), so the reader would take it as part of the answer above it. A test holds every prompt to the headings `sv` writes.
- **Nothing is credited.** ADR-006 and ADR-022 stand. A brief, a prompt given, or a decision written down changes
  no requirement's status. Only what the running app, the code, or the person's own recorded word shows does.

## Alternatives considered

- **Keep rule 3 and leave the design to the prompts.** An empty folder's manifest would still have said no to
  everything planned, and the prompts would have been working against the file they write into.
- **Offer the whole library as MCP prompts.** The coding prompts ask for how code is written, which the model can
  fetch for itself while it writes. A menu the person chooses from fits the decisions only the person can make.
  This can be revisited if trying the menu shows otherwise.
- **Have the server ask the person itself** (MCP elicitation), so the brief's answers would be the owner's word
  rather than the tool's. Item 6 of the backlog entry. Kept apart because client support varies and has to be tried
  first. `sv review` at a terminal stays the sure way to make an answer the owner's.

## Consequences

- **A brief written first can over-claim.** An early app is held to the requirements of everything planned, and
  reports more of them as not verified until each is built and checked. That is the safe side, and the cost the spec
  already names.
- **Drift between the plan and the code is caught only where the corroborators see it.** A capability built and never
  written into the file is still found when the code shows it. A decision in `security-notes.md` or
  `design-decisions.md` that the code ignores is not, until item 5 of the backlog entry ("decisions as planned, then
  held to") is built.
- **Which clients show MCP prompts has not been tried.** The protocol defines them, and the server answers them as
  the specification describes. Whether Claude Code, Cursor, and others list them for a person is to be tried before
  the walk-through says so, as was done for `AGENTS.md`.
- **None of the eight new prompts is shown to work,** and no check in `sv` could show one. They are offered because
  the owner asked for the useful ones to be kept, marked.

## Later, 5 October 2026: decisions in the brief are held to the code, for the design questions

The drift the consequences name is now caught for one kind of decision: the design questions. The spec offers
`planned` as an answer, with `where` naming the file it will be in, so a brief written before the code can record a
decision without claiming it is built. Once the app has code, a planned file that is not there is reported as
*decided, never built* (ADR-022, "Later, 5 October 2026"). Decisions written only in `security-notes.md` or
`design-decisions.md` are still not compared with the code; reading `design-decisions.md` is a separate backlog item,
by the owner's choice. The design-time prompts were not changed to ask for `planned`, because the third trial tested
their present wording.

## Later, 5 October 2026: two of the prompts' sections are read

`design-decisions.md` was written by the design-time prompts and read by nothing. Now the sections the incident-plan
and rules prompts write count toward SBD-MT-06 and SBD-AC-06 as written answers (ADR-022, "Later, 5 October 2026: the
decisions file's sections, read as the notes are"), and what the bring-in-a-person prompt writes is repeated in the
report. The prompts' words are unchanged; a test holds each heading `sv` reads to the words its prompt writes, so a
change to a prompt cannot quietly stop a section from being read. The prompts' notes in `design-prompts.json` say so.
"Safe defaults" is still read by nothing until the second part of the item.

## Later, 5 October 2026: the safe-defaults prompt writes three lines `sv` holds to the code

The second part of the decisions file's item. The safe-defaults prompt's words change, by the owner's choice: its
section now starts with three fixed lines (debug mode, cross-site access, default accounts), and each, decided the
safe way, is held to the check of the running app that sees it; broken, it is the finding *decided, not held to*. The
prompt had never been tried, so no trial's result describes words that are gone. A test holds its three lines to the
switches `sv` reads.

## Later, 5 October 2026: the spec says how many times `sv` signs in

`[stack.run.users]` in the spec now says `sv` signs in up to 60 times in one run from one address, before the
guessing check's wrong passwords, so a builder can let the test copy's limit on sign-in attempts allow that many. The
number is the code's (`SIGN_INS_IN_A_RUN`), and a test holds the spec to it and the scripted runs under it. The
prompts are unchanged.

## Later, 6 October 2026: the booking line, and safe defaults written another way

From the review of 5 and 6 October. The spec's `once` text now says exactly one copy going through is credited and a
repeat that says `completed` again is neither a finding nor a credit, so a builder chooses words only a first taking
shows. The safe-defaults section is read with its switch names in bold or followed by a dash, and a switch it has no
line for is named in the report. The prompts are unchanged.

## Later, 6 October 2026: the coding prompts shown to work reach the brief and the guidance

"The coding prompts stay with `securevibe_prompts`" still holds for the MCP prompts a person chooses: those remain the
design-time ones. But a coding prompt shown to work is now also given where the AI tool reads it while building:
in the brief for the feature whose requirements it is for, and, for the whole app, at the end of the guidance
(ADR-044). The spec also gained two sentences, after a third of Haiku 4.5's builds in the prompt-library trial wrote a
`securevibe.toml` `sv` refused: `[stack.run.ai]` takes no `enabled` (that is `[capabilities.ai]`'s), and `signup` is
a request, never true or false. Nothing more is credited: a prompt given or followed changes no requirement's status.

## Later, 7 October 2026: the design prompts say what to do when nobody answers

After the independent reviews in `docs/prompts/reviews/`, and the trials where design prompts that ask the owner
stalled the build with the owner away (six of ten `design-limits` builds wrote nothing): every design prompt that asks
the owner now ends with what to do if nobody answers, using the suggested values and writing them down as defaults to
confirm. `design-limits` names its numbers and a per-address limit that cannot lock a checker out; `design-sign-in`
names PBKDF2's rounds and the `totp` entry that lets `sv` sign in as an admin with a second step; `design-brief` says
when "write true" gives way to `settings-file-first`'s "leave the line out". Nothing more is credited for any of it.
The revised `design-limits` and `design-sign-in` are tried again in `docs/prompts/library-trial/revision-protocol.md`
only where their checks allow; until a trial agrees, their status rests on their earlier tests.


## Later, 7 October 2026: one sentence more, for `ai = true` under `[capabilities]`

The delivery test's commonest unreadable file left after the two sentences above had `ai = true` straight under
`[capabilities]`. The spec now says, among the `[capabilities]` answers, that there is no `ai` there and that whether
the app has an AI feature is `enabled` under `[capabilities.ai]`. `sv`'s refusal of such a file says the same in plain
words, in both forms toml reports it ("invalid type … expected struct AiClaims", and "duplicate key" when the file also
has a `[capabilities.ai]` header), in place of the name of a type in `sv`'s code. Nothing more is credited; whether the
sentence works is for the next trial that measures unreadable files, as Part A did.

## Correction, 7 October 2026: the revised design prompts were not in the revision trial

An entry above says the revised `design-limits` and `design-sign-in` "are tried again in
`docs/prompts/library-trial/revision-protocol.md` only where their checks allow". That protocol, fixed before its
builds, left every design prompt out, so neither was tried. Their status still rests on their earlier tests, as that
