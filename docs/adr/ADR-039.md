# ADR-039: The sign-in token checks, and which key addresses they may name

**Status:** accepted. Decided by the owner on 4 October 2026 (the three token checks, without `jku` or `kid`), and
again the same day (both ways of reaching V9.1.3 to be built, `kid` still out). Built on 4 and 5 October 2026 (#544,
#710; DESIGN, "The sign-in token the app issues itself", "A sign-in token caught naming where its key is"). Recorded
on 6 October 2026, after the second weekly review of the decision records found it had none.

**Governs:** `crates/sv-check/src/signed_in/tokens.rs`. A pull request that changes it changes this record too, or says
in its description why it does not (`docs/adr/README.md`).

## Context

Many apps an AI coding tool writes sign a person in with a JSON Web Token (a JWT): who the person is and until when,
signed with the app's key. The token is only as safe as the app's checks on it. `sv` cannot forge a token the app
would accept, since it never has the app's key, so every check has to show a fault without one.

A token's header can also name where the key that checks it comes from: `jku` (an address of a set of keys), `x5u`
(an address of a certificate), `jwk` (a key in the token itself), or `kid` (which of the app's own keys). An app that
follows `jku` or `x5u` lets whoever made the token choose the key (V9.1.3).

## Decision

- **Three checks on the app's own token,** with the real token as the control, each in `RESTS_ON_A_REFUSAL` so a
  crash is never credit (ADR-021):
  - the signature, by changing what the token says and keeping its signature (V9.1.1);
  - `alg: none`, by sending the token marked as needing no signature, with none (V9.1.2);
  - expiry, by waiting for a real token to run out and sending it 65 seconds later (V9.2.1), only when that wait is
    short, or within 90 minutes with `--slow`.
- **`jku` and `x5u`, through a test key server inside the fence.** The token is sent with its header naming an address
  on the test server; the server records whether the app came for it. Fetched is a finding
  (`probe.app-token-key-source-followed`, high). Not fetched is never credit: ignoring the header cannot be told from
  checking it against a list. Any run that signs in starts the test server.
- **`kid` stays out.** It misuses the app's own key lookup, needs no key server, and showing it would mean guessing
  at how the app looks keys up. The owner left it out twice.
- **`jwk` is read for in the code, not asked of the running app.** A key written into the token needs no fetch, so a
  run could only show it by signing a token itself, and `sv` has no signing code (`ast.token-key-source-from-token`
  speaks to it).

## Considered

- **Forging a token the app would accept.** Impossible without the app's key, which `sv` never holds.
- **Asking `kid` with a path or a query in it.** Set aside by the owner.
- **Only the code-reading rule for V9.1.3.** Cheaper and runs without Docker, but weaker evidence than the app seen
  fetching; the owner had both built.

## Consequences

- A token lasting longer than the wait leaves V9.2.1 not assessed, saying so; most tokens last 15 minutes or more.
- Every signed-in run starts one more small container, the test server.
- Adding `kid`, `jwk` at run time, or a signing step is a change to this record.

## How it is held

In `crates/sv-check/src/signed_in/tokens.rs`: `a_correct_apps_token_passes_each_check_carried_either_way`,
`each_fault_in_checking_the_token_is_found_carried_either_way`,
`a_token_taken_within_a_minute_of_its_expiry_is_not_a_fault`,
`an_expired_token_refused_counts_only_when_a_new_sign_in_still_works`,
`an_app_that_fetches_the_key_its_token_names_is_found_carried_either_way`, and
`an_app_that_does_not_fetch_is_not_assessed_and_never_credited`.

## Later, 6 October 2026: a review of this record, at the owner's asking

Read against the code and the backlog the same day. The checks and their numbers are as written; four things are
corrected here rather than in place.

- **`kid` was left out once.** The owner left out `jku` and `kid` on 4 October (BACKLOG, signed-in item 4, "The owner's
  decision"). When the owner later chose to build the key server for V9.1.3, the plan they approved covered `jku` and
  `x5u` and kept `kid` out "by the owner's word on item 4": a plan the owner approved, not a second decision. "Left it
  out twice" says more than the backlog shows.
- **"Asking `kid` with a path or a query in it. Set aside by the owner."** Nothing in the backlog or DESIGN shows this
  form put to the owner; it falls under the owner's leaving `kid` out on 4 October.
- **The test server was not seen starting.** "Any run that signs in starts the test server" is what the code does
  (`crates/sv-run/src/docker.rs`), read and not seen working: no container backend was available when it was built
  (DESIGN, "A sign-in token caught naming where its key is"; BACKLOG, V9.1.3, item 1).
- **"Only when that wait is short"** means a token due to expire within 60 seconds (`SHORT_WAIT`,
  `signed_in/tokens.rs`).

Dates here are UTC; #544 merged on 4 October in UTC, the evening of 3 October in Eastern time. Starting the test server
lives in `docker.rs` and `crates/sv-run/assets/model-provider.mjs`, both governed by ADR-019, so a change there owes a
line for ADR-019 rather than this record.
