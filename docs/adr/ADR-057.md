# ADR-057: A dashboard for `sv`, optional, with history kept only when the owner asks, outside the app's folder

**Status:** proposed, 8 October 2026. The owner answered the four questions at the end of `docs/DASHBOARD.md` that
day, after seeing a mock-up, and agreed with its recommendations. Each part below is accepted in the pull request
that builds it, which says where the build differs from this plan. Written by session securevibe-e2.

**Governs:** `docs/DASHBOARD.md`, `crates/sv-report/src/html.rs`. A pull request that changes it changes this record too, or says in its description
why it does not (`docs/adr/README.md`). The files that build each part join this list when they are written.

## Context

`sv` writes one report per run into the app's folder and the next run replaces it. Nothing shows an app at a glance,
an app over time, or every app on one computer (`docs/DASHBOARD.md`, "What `sv` has today"). The owner's answers, in
their words:

1. Who it is for: "Right now it's for me, but I'm also interested in seeing if there's a good way to include it as an
   optional feature for anyone using it."
2. One app or several: "Having different views would be good, so high level overview, drill down on one app, overview
   of all apps built with sv locally, etc."
3. History: "This view over time is definitely interesting, is there a safe way to do this you would recommend?"
4. Live: "Start with a page in a browser is fine, but also curious what it would take to make one that updates as sv
   runs and what the potential trade-offs are there."

## Decision (proposed)

- **Views:** the requirements that apply as one bar at the top of `report.html` first; then `sv dashboard`, which
  writes one page with every app checked on this computer, each opening its own page, with its runs over time when
  history is kept.
- **Optional for anyone.** The bar in `report.html` is part of the report. Everything else is off until a person turns
  it on: `sv dashboard` writes only when asked, and history is kept only once the person running `sv` says so, in a
  setting of their own (`~/.config/securevibe/`), never in `securevibe.toml`, which the AI coding tool writes.
- **History, kept safely** (`docs/DASHBOARD.md`, "Keeping history safely"): outside every app's folder, in
  `~/.local/share/securevibe/history/`, readable only by the person; a small record per run (counts, the kind of run,
  level, `sv` version, the `securevibe.toml` fingerprint, and each finding's fingerprint, severity, rule, and title),
  never code, file contents, or a credential, even shortened; a limit on how many runs are kept; and one command that
  deletes an app's history, or all of it.
- **Pages:** like `report.html`, one file, no script, nothing fetched. A page that updates during a run, if built, is
  a page `sv` rewrites as it goes and the browser reloads, not a program that listens for connections
  (`docs/DASHBOARD.md`, "A page that updates while `sv` runs").

## Alternatives considered

- **History in the app's folder** (`securevibe-report/history/`): the AI coding tool reads and writes there, and the
  folder is often committed, so a public repository would publish a dated list of the app's weaknesses. Not chosen.
- **History in the app's git history**, by committing each report: the same publication, and only for apps whose owner
  commits the report. Not chosen.
- **A local server for live updates** (`sv dashboard --serve`): smooth updates, at the cost of a listening program,
  a script in the page, protections against other software and web pages reaching it, and a port the Docker setup
  does not publish. Not chosen now; possible later as its own decision.

## Consequences

- Nothing changes for anyone who does not turn the dashboard on, beyond the bar at the top of `report.html`.
- History lives on one computer: another computer, or CI, has none, and a moved app folder starts a new history. The
  pages say so.
- History is harder for an AI coding tool to reach than the app's folder, not impossible: the tool runs as the same
  person. The record says what it is (a convenience for the person), not evidence; no requirement is ever credited
  from history.

## Later, 8 October 2026: the bars at the top of `report.html`, accepted

Build item 1 is built (backlog; DESIGN, "The short version opens with two bars"), and this part of the decision is
accepted. Where the build differs from the plan: the owner asked, when saying go ahead, to see how many requirements
do not apply. That is a second, thinner bar of where every requirement `sv` knows went (apply, do not apply, could not
be placed, above the level, counted apart), kept apart from the first so that the ones that do not apply are never
mixed with the evidence for the ones that do. `crates/sv-report/src/html.rs`, which draws both, joins the Governs
list. The rest of the decision is still proposed.
