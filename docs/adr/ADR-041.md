# ADR-041: One run at a time in a report folder, held by a lock file `sv` writes there

**Status:** accepted. Built on 4 October 2026 (#589; DESIGN, "One run at a time in a report folder"), after the owner
and their AI coding tool each ran `sv report` into one folder on family-hub and a failed run replaced a good report
with nothing to say so. Recorded on 6 October 2026, after the second weekly review of the decision records found it had
none and the owner chose it as one of the four to record.

**Governs:** `crates/sv-cli/src/report_lock.rs`. A pull request that changes it changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

Two runs writing one report folder at once leave whichever finished last, even a failed run's over a good one.
`sv` writes only into the report folder of an app's folder (ADR-017), so anything that stops two runs from colliding
has to live there too.

## Decision

- **A lock file in the report folder,** `.securevibe-report.lock`, taken before the run reads the app and held until its
  report is written, by `sv report` and the MCP server's `securevibe_write_report` alike. It is a new file `sv` writes
  into the app's folder, inside the report folder ADR-017 already allows.
- **A second run refuses at once,** naming the run that holds the folder (its command, process, and start). It does
  not wait: a run takes minutes, and a command silent because of another run looks stuck.
- **The lock is the operating system's own,** let go when the process ends however it ends, so a killed run never
  blocks the next; the file still says who held it, and the next run says that run stopped before it finished.
- **A report records when its run started,** and a run does not replace a report from a run that started after it.
  That matters only where the disk cannot lock. A start more than a minute ahead of this computer's clock is not
  believed, so a report claiming the future cannot hold the folder for good (6 October 2026).
- **A run that ends without a report takes away what it added:** the marker it wrote and the folder it made, if
  nothing else is in it. Ctrl-C removes the lock only when it is still the file this run locked.

## Considered

- **Checking whether the holder's process number still runs,** as the backlog first suggested. Set aside: a number
  can be reused, or belong to another machine or container; the operating system's lock answers exactly.
- **Waiting for the folder to be free.** Set aside, as above.

## Consequences

- A disk that cannot lock is said, and the run goes on, with only the start-time comparison to protect it.
- Shared tool reports and container names, which two runs at once also collide on, are not covered here.

## How it is held

In `crates/sv-cli/src/report_lock.rs`: `a_second_take_is_refused_and_names_the_first`,
`a_lock_left_by_a_run_that_ended_does_not_block_and_is_said`, `a_link_where_the_lock_goes_is_refused`,
`a_report_from_a_later_run_is_kept_and_one_from_the_future_is_not`, and
`ctrl_c_removes_only_the_lock_this_run_holds`. End to end, with real processes, in `crates/sv-cli/tests/report_lock.rs`:
`a_second_run_is_refused_while_the_first_holds_the_folder_and_the_first_finishes`,
`a_run_killed_outright_does_not_block_the_folder_and_the_next_says_so`,
`a_report_from_a_run_that_started_later_is_not_replaced`, and
`a_run_that_writes_no_report_leaves_the_folder_as_it_found_it`.
