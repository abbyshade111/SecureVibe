# ADR-041: One run at a time in a report folder, held by a lock file `sv` writes there

**Status:** accepted. Built on 4 October 2026 (#589; DESIGN, "One run at a time in a report folder"), after the owner
and their AI coding tool each ran `sv report` into one folder on family-hub and a failed run replaced a good report
with nothing to say so. Recorded on 6 October 2026, after the second weekly review of the decision records found it had
none and the owner chose it as one of the four to record.

**Governs:** `crates/sv-cli/src/report_lock.rs`, `crates/sv-cli/tests/report_lock.rs`,
`crates/sv-cli/src/mcp/report_writing.rs` (since 9 October 2026; see the Later entry of that date). A pull request
that changes any of them changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

Two runs writing one report folder at once leave whichever finished last, even a failed run's over a good one.
`sv` writes only into the report folder of an app's folder (ADR-017), so anything that stops two runs from colliding
has to live there too.

## Decision

- **A lock file in the report folder,** `.securevibe-report.lock`, taken before the run reads the app and held until its
  report is written, by `sv report` and the MCP server's `securevibe_write_report` alike. It is a new file `sv` writes
  into the app's folder, inside the report folder ADR-017 already allows.
- **A second run refuses at once,** naming the run that holds the folder (its command, process, and start). It does
  not wait: a run takes minutes, and a command silent because of another run looks stuck.
- **The lock is the operating system's own,** let go when the process ends however it ends, so a killed run never
  blocks the next; the file still says who held it, and the next run says that run stopped before it finished.
- **A report records when its run started,** and a run does not replace a report from a run that started after it.
  That matters only where the disk cannot lock. A start more than a minute ahead of this computer's clock is not
  believed, so a report claiming the future cannot hold the folder for good (6 October 2026).
- **A run that ends without a report takes away what it added:** the marker it wrote and the folder it made, if
  nothing else is in it. Ctrl-C removes the lock only when it is still the file this run locked.

## Considered

- **Checking whether the holder's process number still runs,** as the backlog first suggested. Set aside: a number
  can be reused, or belong to another machine or container; the operating system's lock answers exactly.
- **Waiting for the folder to be free.** Set aside, as above.

## Consequences

- A disk that cannot lock is said, and the run goes on, with only the start-time comparison to protect it.
- Shared tool reports and container names, which two runs at once also collide on, are not covered here.

## How it is held

In `crates/sv-cli/src/report_lock.rs`: `a_second_take_is_refused_and_names_the_first`,
`a_lock_left_by_a_run_that_ended_does_not_block_and_is_said`, `a_link_where_the_lock_goes_is_refused`,
`a_report_from_a_later_run_is_kept_and_one_from_the_future_is_not`, and
`ctrl_c_removes_only_the_lock_this_run_holds`. End to end, with real processes, in `crates/sv-cli/tests/report_lock.rs`:
`a_second_run_is_refused_while_the_first_holds_the_folder_and_the_first_finishes`,
`a_run_killed_outright_does_not_block_the_folder_and_the_next_says_so`,
`a_report_from_a_run_that_started_later_is_not_replaced`, and
`a_run_that_writes_no_report_leaves_the_folder_as_it_found_it`.

## Later, 6 October 2026: a review of this record, at the owner's asking

Read against the code and the backlog the same day; the decision and how it is held are as written.

- **"`sv` writes only into the report folder of an app's folder (ADR-017)" is too narrow.** ADR-017 also lets `sv`
  write `security-notes.md` (`sv notes`) and its own section of `AGENTS.md` (`sv rules`). The report folder is where a
  run's output goes, and the one place a run could collide with another.
- **"As the backlog first suggested"** could not be traced: no version of the backlog item names the holder's process
  number. The option is a fair one to have set aside; the attribution is not shown.
- **What the record leaves out:** `report.json` also records the SHA-256 of `securevibe.toml`, and a run whose
  `securevibe.toml` changed while it ran says so (DESIGN, "One run at a time in a report folder"). The item was claimed
  at the owner's asking (BACKLOG, family-hub item 2).
- **Governs** gains the end-to-end tests, `crates/sv-cli/tests/report_lock.rs`. Taking the lock and the folder checks
  (`claim_report_folder`), the MCP server's side, and Ctrl-C's release are in `main.rs` and `mcp.rs`, which the owner
  decided on 6 October to leave ungoverned.

## Later, 9 October 2026: who holds the lock, in a file beside it that is never locked

On Windows a locked file cannot be read by anyone but the run holding it, so a second run could not say which run
held the folder: the lock file carries that record, and the record was unreadable. Now the run holding the folder
also writes the record into `.stackvet-report.holder` beside the lock, which is never locked. A second run reads the
holder file first, and the lock file only when there is no holder file, as when an `sv` from before this held the folder.
The lock file still carries the record, so an older `sv` on macOS or Linux reading it is not left without one.

The holder file is written while the lock is held, never through a link, and removed just before the lock file. The
lock is still held while it goes, so the next run to take the folder cannot have its own holder file removed.

A run tells whether the lock file is still the one it locked, before removing it on the way out, as before on Unix:
by the file itself (device and inode). Elsewhere the standard library gives nothing that tells one file from another
of the same size, and Windows gives a new file the creation time of one just removed under the same name. So there a
run knows its lock by the record it wrote into the holder file, which names its process and the moment it took the
folder. Until now, outside Unix, any plain file of the same size passed for this run's, so a run stopped with Ctrl-C
could have removed another run's lock.

One more file in the report folder, a dot name beside the lock and listed with the folder's other names
(`REPORT_FOLDER_NAMES`), so `sv` knows it as its own. Found by the Windows workflow (backlog 0120). Not yet tried on
Windows itself; the workflow's next run is the first.
