# ADR-084: More in the build-loop record: each call's outcome, what was handed over, and what changed between checks

**Status:** accepted in part, 10 October 2026: decisions 1, 2, and 4 are built and accepted (see "Later, 10 October
2026" below); decisions 3, 5, and 6 are still proposed. Proposed 9 October 2026, with the backlog claim (0226, part 3, item D). The owner's decision, the same
day: "yes to A, C, and D". It extends ADR-076, whose lines held the time, the tool's name, and a check's counts. Each
part is accepted in the pull request that builds it. Written by session paper-facts.

**Governs:** `crates/sv-cli/src/build_loop.rs`, which writes the record and reads it back. A pull request that changes
what it says about the record changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

The observability review of 9 October 2026 (backlog 0226) found that the build-loop record cannot tell a check that
failed or timed out from a call that only asked for text, writes nothing for a call refused before it ran or when the
record could not be written, leaves no trace when the AI coding tool turns it off in `stackvet.toml`, does not say
which AI tool or which `sv` was used, does not record the prompts and report files handed over, and keeps only the
first and last checks' counts, so a total that drops may be a fix or a finding set aside.

## Decision

Each line of the record may also carry, and the report's paragraph says what they show:

1. **The call's outcome**: ok, timed out, crashed, or refused; never the error's text, which can quote the app.
2. **A line when the record is turned off**, so a gap is seen as one, and the report saying so when the record could
   not be written.
3. **Names `sv` itself defines** that the call asked for: a section, a feature, a question id. Never an argument the
   AI tool wrote, a path, or finding text.
4. **Which tools were used**: the AI tool's name and version from `initialize`, cut short, and `sv`'s version.
5. **What was handed over**: each prompt fetched, each report file read, and that the instructions were given at
   `initialize`.
6. **At each check, the findings' fingerprints** (hashes, not text), so the report can say how many were fixed, set
   aside, and new between the first check and the last.

The record stays in the report folder, capped, written link-safely, and credits nothing (ADR-076). A forged or edited
line is still possible for anything that can write the folder, and the report still says so; a copy outside the folder
that cannot be quietly rewritten is a separate decision (review part 3, item J).

## Alternatives considered

- **Arguments in full**: says the most, and carries the AI tool's words, paths, and the app's text into the record.
- **Counts only** (ADR-076 as built): the loop's struggle and its fixes stay invisible.

## Consequences

Lines grow from tens of bytes to a few hundred at a check (the fingerprints); the 4 MB cap still holds tens of
thousands of calls. The report can say which AI tool built the app, whether it read the report and rules it was given,
and how many findings it fixed rather than set aside.

## Later, 10 October 2026: decisions 1, 2, and 4 built

Built by session securevibe-e2 (backlog 0231). Each line of the record now carries:

- **`outcome`**: `ok`, `failed`, `timed-out` (the check ran past its time limit), `crashed` (the check stopped on a
  fault in `sv`), or `refused` (a tool `sv` does not have, written down as `unknown`, never by the name the AI tool
  sent). Never the error's words. A line naming any other outcome is one `sv` did not write, and is counted as
  unreadable.
- **`client`**: the AI coding tool as it named itself in `initialize` (`clientInfo`), kept to letters, digits,
  spaces, and `.-_+/()`, 40 characters a part (`build_loop::client_name`).
- **`sv`**: the version that answered.

When `stackvet.toml` turns the record off, the server writes one line holding only the time and `"off": true`, once
until a call is written down again, so a gap is seen as one; no call is written while it is off. A call that cannot
be written into the record is counted by the process that tried, and the next report that process writes says how
many (`unwritten`); a report written by another process, `sv report` at a terminal, cannot know of them and says
nothing of them. The report's paragraph says how many calls failed, ran out of time, stopped on a fault, or were
refused; which AI tool named itself and which `sv` answered; how many times the record was turned off; and how many
calls could not be written. Each new field of the report's `build_loop` is left out when it is empty, so a report
written before reads and seals the same.

Where the build differs from the plan: decision 1's "refused" covers only a tool `sv` does not have. A call whose
arguments are not an object names no app (its folder is in the arguments), so there is no record to write it in; it
is answered as before and not written down.
