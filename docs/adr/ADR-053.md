# ADR-053: Another user's records are checked for reading, listing, changing, and deleting, and one read alone is "checked in part"

**Status:** accepted, 7 October 2026, in the pull request that builds it; proposed the same day with the backlog
claim. Decided by the owner on 7 October 2026 ("go ahead with items 7 and 4"), from the gap analysis's finding 1.7
(`docs/GAP-ANALYSIS.md`; BACKLOG, gap analysis item 4).

**Governs:** `crates/sv-check/src/signed_in/admin.rs` (the checks on another user's records), `crates/sv-check/src/signed_in/owner_field.rs` (a record's owner taken from the request), and
`crates/sv-check/src/verified.rs` (a credit marked as in part). The new status itself is in the report's list of
statuses, which ADR-050 governs; it has a Later entry there. A pull request that changes what these say about this
changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

V8.2.2 asks that a user can reach only their own data. Today it becomes *checked* when one signed-in user, B, is
refused one read of one record user A created (`crates/sv-check/src/signed_in/admin.rs`). Nothing tries B changing
or deleting A's record, or looks for A's data in B's lists and pages: the commonest ways an app built by an AI coding
tool leaks one person's data to another. The requirement's own line says what was tried; the counts and the short
version say only *checked*, which reads as more than one refused read.

## Decision

- **B also looks for A's data where lists show it.** B opens every page under `private` and, when securevibe.toml
  names one, the record's list (`list` under `owned`). A's marker in any of them is a finding.
- **B tries to change and to delete A's record**, when securevibe.toml gives the requests (`update` and `delete`
  under `owned`, with `{id}`). A then reads the record back: B's change visible to A, or the record gone, is a
  finding. What A sees decides it, not what B was told.
- **One kind of access alone is "checked in part".** V8.2.2 is *checked* only when B was refused both reading A's
  record and changing or deleting it. When only reading was tried, the requirement is *checked in part*: a status of
  its own, below *checked*, counted and named as such in the counts and the short version, and never a pass.

## Alternatives considered

- **Keep *checked* and say more in the requirement's line.** The line already says what was tried; the counts are
  what the owner reads, and they would still say *checked*.
- **"Checked in part" for every check that rests on one sample.** Right in principle, and each needs reading on its
  own; this record starts with V8.2.2, where the gap was found, and the mechanism lets others follow.

## As built, 7 October 2026

- **Settings:** `list`, `update`, and `delete` under `[stack.run.users] owned`, all optional; the specification
  explains them with an example.
- **Lists:** the second user opens every `private` page and `list`; the first user's marker on any page that
  answered is a finding, "One user's records show on another user's pages".
- **Changing and deleting:** the second user sends `update` (with a marker of its own) and then `delete`, each with the
  first user's record's id. The first user's read-back decides: B's marker there, or the first user's gone, is a
  change; a plain 404 or 410 is a deletion; a record still holding the first user's marker is a refusal; a crash or
  no answer decides nothing. A crashed request of B's is never read as a refusal: each new request is listed among
  those the credit rests on (`RESTS_ON_A_REFUSAL`), and the crash sweep (`a_crash_never_turns_a_finding_into_a_pass`)
  caught all five ways a crash would have earned the credit before they were listed.
- **The status:** a credit is marked in part (`Verified::in_part`); a requirement whose every credit is in part is
  *checked in part* (`Status::CheckedInPart`), ranked below *checked* and above the app's own tests, counted as
  looked at by a check, with its own row in every count table, its own column in the chapter table when any chapter
  has one, and its own words in the terminal, the short version, and the MCP summary. A threat counts it as it counts
  *checked*: a threat is only ever *checked in part* by its requirements' checks. When V8.2.2 is in part, the report
  also says why (no `update` or `delete` given, or the read-backs said neither) under what was not assessed.
- **Tested:** against the scripted app with three new flaws (a list showing everybody's notes, editing and deleting
  anybody's), each found by itself; a correct app is *checked* with everything tried and *checked in part* with
  reading alone; every format has the row (`checked_in_part_is_its_own_row_in_every_format_and_never_checked`).
  Broken on purpose, each caught: reading alone credited in full; the report ignoring in part; a change never seen;
  a deletion never seen; lists never searched (a first attempt did not compile and was redone).

## Later, 8 October 2026: a refusal counts only when the owner's own request works

The second documentation review found that the change and delete checks could credit V8.2.2 in full for a request
that never reached a route. `update` and `delete` are form POSTs unless they say otherwise, which the specification did
not say; for an app whose routes take `PUT` or `DELETE`, the second user's request answered 405, the first user's
record stayed as it was, and that was read as a refusal. Now the first user also makes a second record of their own
and sends the same request at it: the second user's request leaving the record as it was counts as a refusal only
when the owner's own request does change or delete theirs. When it does not, the check says it could not tell, and
V8.2.2 is checked in part, naming the request and `method`. A second record, so the first stays as it was for the
checks that read it later. The new requests are among those the credit rests on, so a crashed control is not one
that worked. The specification now says how to give `method`, `json`, `token-field` and `id-field`.

Tested against the scripted app with routes that take another method: reading is credited in part and the note names
the change and delete requests; the correct app is still checked in full. Broken on purpose (the control switched
off), the test fails. Everything else in this record stands.

## Later, 9 October 2026: a record's owner taken from the request

The checks on the `owned` record now also ask whether the second user can put a record into the first user's account by
adding the owner field the first user's record names (`user_id`, `owner_id`, and five more) to the request that
creates it (`probe.owner-field-trusted`, `signed_in/owner_field.rs`; the gap analysis's finding 13(a)). It follows this
record's control: the second user's plain record, made by the same request without the field, must not be shown to the
first user, or being shown the other one proves nothing and the report says so. Only ever a finding, citing V15.3.3,
V8.2.3, and V8.2.2; it changes no credit for V8.2.2. It makes two more records in the app, both the second user's.
Everything else in this record stands.

**Later, 10 October 2026: more checks that rest on one sample** (session securevibe-e2, backlog 0006 part 4, the
rest of the gap analysis's finding 1.7). An inventory of the running checks found about fifty that give a requirement
plain *checked* from one sample (one response, one page, one record, one action, one upload, one log line, or one of

both of its credits: one SVG refused, or two dangerous parts of one SVG removed). Nothing else changes yet.
**Status: proposed** for the rest: each of the others to be marked in part where one sample cannot speak for what the
