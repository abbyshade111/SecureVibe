# ADR-035: A preflight of the run settings, read from the code and never run

**Status:** accepted. The owner chose on 5 October 2026 to do all six items of "The loop" (BACKLOG), and on the same
day asked for item 5, this one, to be built. Written first as `proposed` (#740), as `docs/adr/README.md` asks for a
substantial decision, and built the same day; "Where the build differs from the plan", below.

**Governs:** `crates/sv-cli/src/preflight.rs`. A pull request that changes it changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

`sv run` can test an app only if the app gives it what `[stack.run]` and `[stack.run.users]` say: a server that
listens where `sv` asks, at the port it gives, a seed that makes the accounts it names, the sign-in form at the path
and with the fields the settings give, and the tables made by the app when it starts. In the third prompts trial most
of the builds that could not be tested failed on one of these: a seed that ignored the `SV_` accounts, a sign-in path
not where the settings said, tables made only by the seed (BACKLOG, "The loop", item 5). Each was found only by
running the app, after the build was over, and the MCP server cannot run the app: starting it runs code, "a decision
a person makes at a terminal rather than one a model makes in a loop" (`crates/sv-cli/src/mcp.rs`, "What it will and
will not do").

## Decision

`sv preflight [PATH]`, and the MCP tool `securevibe_preflight`, read `securevibe.toml` and the app's files and say,
for each thing `sv run` will need, whether the code appears to give it.

- **It runs nothing.** It reads the files the report's own listing reads, and no code, command, or container starts.
- **What it looks at:** the start command; that the app listens on every address and at `$PORT`; that the seed file
  the settings name exists and reads the `SV_` accounts `sv` will give it (the admin's too, when admin pages are
  listed); that the tables are not made only in the seed; that each path the settings name (health, sign-in,
  sign-up, sign-out, private and admin pages, admin actions) and each form field they send appears in the code.
- **Each answer is one of three:** looks right, look at this, or could not tell. "Looks right" means the text was
  found, not that it works. It says so.
- **It credits nothing** and is not evidence of any requirement (ADR-006, ADR-022). It is a hint for the builder,
  before the run that is the evidence.
- **The server's instructions offer it** after the code is written and before `securevibe_check`.

## Alternatives considered

- **Starting the app from the MCP server.** That would answer each question for certain, and it breaks the rule that
  a model never makes `sv` run code: text in the app could steer it into running anything.
- **Leaving it to `sv run`.** It already says why a run could not start or sign in, but only after the build, when
  the AI tool that could fix it in a minute has finished.

## Consequences

- **It can be wrong both ways.** A route built from parts is not found and reads as "look at this"; a path that
  appears in a comment reads as "looks right". The answers say what was looked for, so a person can judge.

## Where the build differs from the plan

- **A seed that is the app's own file** (`seed = "python app.py seed"`) gets "could not tell" for the tables, not "look
  at this": whether the app makes them when it starts or only when it seeds is not in the text. Found by running the
  preflight on the loop trials' builds, two of which seed that way
  (`a_seed_that_is_the_app_itself_cannot_say_where_the_tables_are_made`).
- **What only describes the app is not read:** `securevibe.toml`, Markdown, and plain text, where a path or a variable
  named in prose would read as found (`prose_and_the_manifest_do_not_count_as_code`).
- **Checked on the examples before anything else:** `notes-with-users`, the example built to be signed in to, has
  nothing to look at; `flask-booking` starts on `127.0.0.1`, and the preflight says so
  (`crates/sv-cli/tests/preflight.rs`).
- **Each rule was broken on purpose** and the suite run: every one of the eleven was caught by the test named for it,
  and three of them (loopback, the port, a path) by the test of prose as well.

## Later, 6 October 2026: hints at what the run will test

The preflight also reads the code for some of what `sv run` will *test*, not only what it needs (DESIGN, "The
preflight hints at what the run will test"). In the loop trials the builders fixed what `securevibe_check` named, and
their running apps kept as many problems as any other arm's, because only the run looks for them. The new section
covers a limit on wrong passwords, the four security headers, the session cookie's SameSite, and an AI feature's
screening, limit, and off switch.

The decision above holds for it unchanged:
- it runs nothing;
- each answer is one of the three;
- it credits nothing.

Two things were added so it stays that way:
- **Counted apart.** The opening count still says only whether the run can start and sign in, and the hints have
  their own heading and count. Each JSON item carries `for`, `needed` or `tested`, which the tool's output schema
  requires.
- **Where the text cannot settle it, it says "could not tell".** That covers a framework that sets SameSite itself
  (Django, Rails), and a limit that may or may not cover the AI feature on its own. A limit whose number the owner has
  not stated under [policy] is said to go untried by the run.
