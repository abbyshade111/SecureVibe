# ADR-018: `sv` checks apps written in any language, with rules of its own among the checks

**Status:** accepted, 27 September 2026. The owner asked for this record that day, saying the ruling it
replaces "definitely needs to be updated", and accepted the draft the same day.

**Governs:** `data/ast-rules.json`, `crates/sv-check/src/ast.rs`, `data/adapters.json`,
`crates/sv-check/src/adapters.rs`, `tools/coverage.py`. A pull request that changes any of these changes this record
too, or says in its description why it does not (`docs/adr/README.md`).

**Supersedes:** part of v1's ADR-012 (on the `v1` branch, `docs/adr/ADR-012.md`). ADR-012's rule about honest
reporting stays in force. What changes is its limit on what SecureVibe checks and how.

## Context

ADR-012 was written on 20 September 2026, after the first app from outside, a Flask app in Python, was
reported as "0 of 106 applicable requirements verified", having had one JavaScript file read. It sorted apps
into three tiers:

1. Node apps that v1 built, which were the only ones scored.
2. Apps in other languages, which were checked with outside tools and never scored.
3. Everything else, which was only read for secrets and malware.

The owner accepted it with one ruling called out as the load-bearing part: **no custom static-analysis rules
for other languages.** Its reasons were that writing them would be "months of work to be worse than semgrep at
semgrep's job", and that nobody should revisit the ruling by writing "just a few" Python rules.

Two days later, on 22 September 2026, work began on `sv` as a second version with "no wizard and no language":
the person builds the app in any AI coding tool, and `sv` checks it whatever it is written in. On 23 September
`sv` took on the tree-sitter parser and wrote its first four rules of its own, for Python, JavaScript,
TypeScript, and Go. No record revisited ADR-012's ruling when that happened. On 26 September `sv` became the
top of the repository and v1 moved to its branch, with ADR-012 still saying the opposite of what `main` does.

What `sv` does, as of this record:

- **Rules of its own**: twelve, in `data/ast-rules.json`, across fourteen languages (Python, JavaScript,
  TypeScript, Go, Ruby, PHP, Java, C#, Kotlin, Rust, C, C++, Dart, and Swift), plus the script inside HTML
  pages. They cover code run from a string, shell commands built from a value, SQL joined from pieces, unsafe
  deserialization, paths built from a value, weak hashes and ciphers, encryption with no tamper check, open
  redirects, a download piped to a shell, and `ws://` addresses.
- **Other tools**: the language's own security tools (bandit, gosec, brakeman, semgrep, and CodeQL for
  JavaScript and Python), run when the owner asks and reported as *not run* when they are not installed.
  Semgrep runs packs that cover every language, and a rule earns credit only for a language in the app and
  only when it is mapped to a requirement, one rule at a time.
- **Dependencies in every ecosystem it recognizes**: pins read in each one's own way (Maven and Gradle
  included), with a floating version reported as a finding, and a bill of materials that can be matched
  against an advisory database the owner downloads.

## Decision

**`sv` checks apps in any language, and a language is not a tier.** The same claims, the same requirements,
and the same reports apply whatever the app is written in. What differs between languages is what `sv` could
read, and the report says that for each rule and each language, instead of putting the whole app in a tier.

**`sv` writes a small number of rules of its own**, as tree-sitter queries in a data file, where all of these
hold:

- The question is about a single place in the code that a parser can see: a call and what is passed to it.
  A question that needs the flow of data across the program is left to tools built for that.
- A rule is taught a language together with a sample it must find there and one it must not. For most
  pairs a test fails when either sample is missing; the oldest rules' first languages are held by tests of
  their own instead. Breaking a rule on purpose has to turn a test red.
- A rule that cannot settle a question from one place in the code says so. It is *finding-only*, which means
  a clean run earns no credit, and its confidence is marked low where it is a guess.

**Outside tools are not replaced.** They run beside `sv`'s rules, and when two independent tools agree on the
same line, that is stronger evidence than either one alone.

**ADR-012's rule on reporting stays in force**, unchanged, and every part of `sv` applies it:

- A check that does not apply is not a check that failed.
- A scan that did not run is not a clean result, and a tool that is not installed is *not run*.
- A wrong statement in a report is worse than a gap in it.
- Code that `sv` could not read is never counted as clean. A language present in the app with no grammar
  silences every rule for the whole app, and a rule that was not taught a language claims nothing about it.

## What ADR-012 said, and what happens to each part

| ADR-012 | Now |
|---|---|
| No custom static-analysis rules for other languages | **Replaced** by the decision above |
| Three tiers, with only v1's own Node apps scored | **Replaced.** No app is placed in a tier by its language. Each requirement gets a status from its own evidence (*checked*, *needs attention*, one of the tiers for a person's word, or not verified), whatever the language |
| Choose semgrep's packs by the languages present | **Met another way.** `sv` runs packs that cover every language (`p/security-audit` and `p/default`, plus `p/ai-best-practices` for an app that may call a model) and counts a rule only for a language present in the app |
| Give osv-scanner every lockfile | Kept in spirit: `sv` reads each ecosystem's own pins and matches against a database the owner downloads, without running osv-scanner |
| Stop asking Node questions of other apps | Kept. Nothing in `sv` assumes Node |
| Raise unpinned dependencies as a finding | Kept, in every ecosystem `sv` recognizes |
| Say what was checked, on the page | Kept, per rule and per language instead of per app |

## Alternatives considered

- **Keep ADR-012's ruling, and rely on outside tools alone.** Every outside tool is opt-in and may not be
  installed. Reported honestly as *not run*, that would leave an app with no code reading at all whenever
  nothing is installed. The widest of the tools, semgrep, also comes with a condition. Its rules are under a
  license that limits their use, and the owner's review on 26 September 2026 found SecureVibe's use
  acceptable only while nothing is sold or otherwise made money from.
- **Write many rules, to compete with semgrep.** ADR-012's warning against this holds. `sv`'s own rules are
  deliberately few, and each one has to earn its place with the samples above.
- **Stay Node-only, as v1 was.** The person now builds the app in their own tool, in whatever language it
  chooses, so a Node-only checker would turn most apps away.

## Consequences

- Adding a language takes three things: a grammar, a query for each rule or a stated reason why the language
  has nothing for that rule to find, and the samples each query must find and must not find. The design notes
  record what each addition cost ("Fourteen languages, and why the fifteenth silences everything").
- Every rule is `sv`'s to maintain in every language it is taught. That is the cost ADR-012 predicted, and it
  is kept small by keeping the rules few.
- If SecureVibe is ever sold or otherwise made money from, semgrep's rules must be re-examined first. `sv`'s
  own rules are the part of the code reading that has no such condition.
- ADR-012 stays as it was on the `v1` branch. History there is not rewritten. This record is where the ruling
  is replaced.

## Later, 4 October 2026: a broken file holds back only the rules it could hide something from

The deep review found that one file the parser could not read in full silenced every code rule for the whole app
(H25). Every rule reads JavaScript, so one vendored script the parser choked on took every clean result for the
code out of the report. What counts as evidence is unchanged: a rule claims nothing is absent only where it could
have looked. What changed is how precisely that is decided.

- **A file that did not parse cleanly holds back only the rules whose call it names.** A rule reports a call only
  when the call's name matches its pattern. If no word anywhere in the file matches, even a perfect parse would have
  found nothing there, so the rule is not held back. If any word matches, wherever it is, the rule is.
- **Only patterns made of words count.** A pattern that can match more than a single word (a quoted path, the
  shell's `.`, a name with its module, a character class) always holds its rule back.
- **A file that was not opened** still holds back every rule that reads its language, since nothing is known about
  what it names. A language with no parser, and a rule whose query would not compile, still hold back every rule.

DESIGN, "A broken file holds back only the rules it could hide something from". Held by four tests in
`crates/sv-check/tests/clean_coverage.rs` and `the_words_in_a_file_rule_out_only_what_a_name_pattern_can_match`.

## Later, 5 October 2026: outside tools run for at most half an hour, with only the environment they need

The deep review's improvement 3. `sv` started each outside tool (Semgrep, CodeQL, gosec, and the others in
`data/adapters.json`) with the owner's whole environment and waited for it however long it took. Built by session
securevibe-e9 at the owner's asking, in branch `claude/securevibe-e9-tool-limits`.

- **A time limit.** A tool's run, and CodeQL's step before it, is stopped after half an hour (`TOOL_SECONDS`, or the
  entry's own `time_limit_seconds`), and asking a tool its version after a minute. A tool stopped this way did not
  run: its report is not read, and the report says it was stopped. On Unix it leads a process group of its own, and
  the whole group is stopped, since Semgrep's work is done by a second program it starts.
- **Only the environment a tool needs.** From the owner's environment, only `PASSED_ON`: where programs and the home
  and temporary folders are, the language, a proxy and certificates, and where Java, Go, and Python keep what they
  need. Keys and tokens for other services are left out; Semgrep, given a token for its own service, would use it.
- **`GOTOOLCHAIN=local`,** so a Go tool uses the Go installed here, rather than fetching and running the toolchain the
  app's `go.mod` names.

Held by `a_tool_that_does_not_finish_is_stopped_with_what_it_started_and_not_read`,
`a_tool_is_handed_only_the_environment_it_needs`, and `a_tool_that_does_not_say_its_version_is_broken_not_waited_for`
(`crates/sv-check/src/adapters.rs`).

## Later, 6 October 2026: `ast.download-piped-to-shell` is only ever a finding

The documentation review of 6 October 2026 (BACKLOG, "Found by the documentation review", item 1) found that a clean
run credited V15.2.4 (components come from the expected repository, no dependency confusion) because the rule that
finds `curl … | sh` and its relatives was not marked findings-only. Not finding a download piped to a shell says
nothing about where the app's dependencies come from, so the rule is now `findingsOnly`: a download piped to a shell
is still a finding against V15.2.4, and a script without one credits nothing. Proposed in the claim (#830), accepted
here. Everything else in this record stands.

## Later, 7 October 2026: a Semgrep rule counts only when Semgrep was handed a file it reads

The gap analysis of 7 October 2026 (`docs/GAP-ANALYSIS.md`, 1.2) found that a clean Semgrep run credited requirements
through rules that had read nothing. Many of Semgrep's rules name the files they read (`paths.include` in the rule):
Rails template rules read `*.erb`, nginx rules read `*.conf`, the .NET cookie rule reads `web.config`. Semgrep applies
that to files named on its command line too, and `sv` hands it only the app's code files, so those rules never ran over
anything. A clean run counted them anyway, because the map said only that they were for "any language". A
JavaScript app's cookie settings (V3.3.1) were "checked" through a `web.config` rule and a Scala Play rule. A Go app's
anti-forgery protection (V3.5.1) went through a Django template rule, and a Ruby or PHP app's TLS settings (V12.1.1)
through nginx rules.

**Decision.**
- Each mapped rule now carries the files it reads, copied from its own definition: `targets` from `paths.include` and
  `skips` from `paths.exclude`, in `data/adapters.json`, written by `tools/semgrep_rule_map.py --targets` from the same
  semgrep-rules checkout as the map.
- A clean run counts a rule that names its files only when `sv` handed the tool at least one file the rule reads. This
  holds for rules of one language too. The WordPress plugin rules read only `wp-content/plugins/`, so a PHP app that
  is not a plugin no longer has its anti-forgery protection credited through them.
- The coverage count (`tools/coverage.py`) leaves out the 22 loaded rules whose files `sv` never hands Semgrep. No
  requirement was named only by them, so the counts do not move.

**What did not change.** The 214 key-pattern rules (`generic.secrets`) read every file except a few kinds, so they
still count over code. Rules that name no files still count as before.

**Not done, and left for later.** The gap analysis also proposed handing Semgrep the app's templates and configuration
files, so that these rules run at all. That would change what `sv` gives an outside tool, and the "it did not read all
the files it was given" check would need to learn which of those files Semgrep reads. It is in the backlog.

## Later, 8 October 2026: Semgrep is handed the files its rules name, and only those count as unread

The backlog's gap analysis item 34, the part left for later on 7 October, taken by session securevibe-e9 at the
owner's "pick your next backlog item".

**What was measured** with semgrep 1.180.0, by handing it one file of each kind and reading back its list of files
read. Semgrep leaves out, without a word in its report or its list, a file it was handed that no rule it loaded reads,
and a rule of Semgrep's `generic` or `regex` language with no `paths.include` reads every file. The packs `sv` runs
load 45 such rules (the key patterns), so today every file handed over is read. Templates and notebooks have been
handed over since 8 October (ADR-054), as files with a language.

**Decision.**
- Semgrep is handed, besides the app's code files, each other file of the app that a rule in the map names in its
  `paths.include`: nginx's `*.conf`, `web.config`, `*.tf`, `.npmrc`, an MCP configuration (`handed_files` in
  `crates/sv-check/src/adapters.rs`). Those rules now run, and credit a clean run for an app that has such a file.
- The "it did not read all the files it was given" check counts a file only when a loaded rule in the map reads it:
  one its `paths.include` names, or one its language's parser reads, as measured (`read_by_a_loaded_rule`,
  `SEMGREP_EXTENSIONS`), or every file for a rule of any language. If a pack stopped loading the key-pattern rules, a
  `.hbs` page no other rule reads would no longer hold back every other rule's clean run. A rule the map does not know
  is left out: only rules in the map credit anything.
- The coverage count leaves out no loaded rule now, since none reads only files `sv` never hands Semgrep.

## Later, 8 October 2026: what a tool's log says it read, and what it says did not happen, count

gosec's report names only what it found, and with `-quiet` a clean run wrote no report at all, so no clean gosec run
was ever credited and nothing noticed, since no test ran the real tool. With `GOPROXY=off` and `CGO_ENABLED=0` (ADR-032,
Later, the same day) a cgo file is left out of its build and its analyzers fail without the app's modules, and a
report that said nothing about either would have read as clean. Two fields on an entry, both read from the tool's
stderr, which `sv` keeps up to 64 KB of:

- **`read_log_prefix`**: a line holding this text names a file the tool read (gosec's `Checking file: `). A code
  file of the tool's language, by `sv`'s own listing, that the log never names is listed as unread, and a log naming
  none is a run that read nothing; neither is credited as clean. A log longer than `sv` keeps says so rather than
  counting the rest unread.
- **`unfinished_when`**: lines that mean part of the run did not happen, each with what it means in words the owner
  can act on (gosec's `Error building the SSA representation`: its analyzers did not run, and the remedy is `go mod
  download` in the app, by the owner, since `sv` lets no tool download). A run whose log holds one is not credited as
  clean; its findings stand.

gosec's `-quiet` is gone, so the log is written and a clean run writes a report, and `-tests` is given, so it reads the
test files `sv` hands every other tool. Held by `crates/sv-check/src/adapters/fence_tests.rs` and
`crates/sv-check/tests/tool_fence.rs`, and by `crates/sv-check/tests/gosec_fence.rs` where gosec is installed.
