# ADR-018: `sv` checks apps written in any language, with rules of its own among the checks

**Status:** accepted, 27 September 2026. The owner asked for this record that day, saying the ruling it
replaces "definitely needs to be updated", and accepted the draft the same day.

**Governs:** `data/ast-rules.json`, `crates/sv-check/src/ast.rs`, `data/adapters.json`,
`crates/sv-check/src/adapters.rs`. A pull request that changes any of these changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

**Supersedes:** part of v1's ADR-012 (on the `v1` branch, `docs/adr/ADR-012.md`). ADR-012's rule about honest
reporting stays in force. What changes is its limit on what SecureVibe checks and how.

## Context

ADR-012 was written on 20 September 2026, after the first app from outside, a Flask app in Python, was
reported as "0 of 106 applicable requirements verified", having had one JavaScript file read. It sorted apps
into three tiers:

1. Node apps that v1 built, which were the only ones scored.
2. Apps in other languages, which were checked with outside tools and never scored.
3. Everything else, which was only read for secrets and malware.

The owner accepted it with one ruling called out as the load-bearing part: **no custom static-analysis rules
for other languages.** Its reasons were that writing them would be "months of work to be worse than semgrep at
semgrep's job", and that nobody should revisit the ruling by writing "just a few" Python rules.

Two days later, on 22 September 2026, work began on `sv` as a second version with "no wizard and no language":
the person builds the app in any AI coding tool, and `sv` checks it whatever it is written in. On 23 September
`sv` took on the tree-sitter parser and wrote its first four rules of its own, for Python, JavaScript,
TypeScript, and Go. No record revisited ADR-012's ruling when that happened. On 26 September `sv` became the
top of the repository and v1 moved to its branch, with ADR-012 still saying the opposite of what `main` does.

What `sv` does, as of this record:

- **Rules of its own**: twelve, in `data/ast-rules.json`, across fourteen languages (Python, JavaScript,
  TypeScript, Go, Ruby, PHP, Java, C#, Kotlin, Rust, C, C++, Dart, and Swift), plus the script inside HTML
  pages. They cover code run from a string, shell commands built from a value, SQL joined from pieces, unsafe
  deserialization, paths built from a value, weak hashes and ciphers, encryption with no tamper check, open
  redirects, a download piped to a shell, and `ws://` addresses.
- **Other tools**: the language's own security tools (bandit, gosec, brakeman, semgrep, and CodeQL for
  JavaScript and Python), run when the owner asks and reported as *not run* when they are not installed.
  Semgrep runs packs that cover every language, and a rule earns credit only for a language in the app and
  only when it is mapped to a requirement, one rule at a time.
- **Dependencies in every ecosystem it recognizes**: pins read in each one's own way (Maven and Gradle
  included), with a floating version reported as a finding, and a bill of materials that can be matched
  against an advisory database the owner downloads.

## Decision

**`sv` checks apps in any language, and a language is not a tier.** The same claims, the same requirements,
and the same reports apply whatever the app is written in. What differs between languages is what `sv` could
read, and the report says that for each rule and each language, instead of putting the whole app in a tier.

**`sv` writes a small number of rules of its own**, as tree-sitter queries in a data file, where all of these
hold:

- The question is about a single place in the code that a parser can see: a call and what is passed to it.
  A question that needs the flow of data across the program is left to tools built for that.
- A rule is taught a language together with a sample it must find there and one it must not. For most
  pairs a test fails when either sample is missing; the oldest rules' first languages are held by tests of
  their own instead. Breaking a rule on purpose has to turn a test red.
- A rule that cannot settle a question from one place in the code says so. It is *finding-only*, which means
  a clean run earns no credit, and its confidence is marked low where it is a guess.

**Outside tools are not replaced.** They run beside `sv`'s rules, and when two independent tools agree on the
same line, that is stronger evidence than either one alone.

**ADR-012's rule on reporting stays in force**, unchanged, and every part of `sv` applies it:

- A check that does not apply is not a check that failed.
- A scan that did not run is not a clean result, and a tool that is not installed is *not run*.
- A wrong statement in a report is worse than a gap in it.
- Code that `sv` could not read is never counted as clean. A language present in the app with no grammar
  silences every rule for the whole app, and a rule that was not taught a language claims nothing about it.

## What ADR-012 said, and what happens to each part

| ADR-012 | Now |
|---|---|
| No custom static-analysis rules for other languages | **Replaced** by the decision above |
| Three tiers, with only v1's own Node apps scored | **Replaced.** No app is placed in a tier by its language. Each requirement gets a status from its own evidence (*checked*, *needs attention*, one of the tiers for a person's word, or not verified), whatever the language |
| Choose semgrep's packs by the languages present | **Met another way.** `sv` runs packs that cover every language (`p/security-audit` and `p/default`, plus `p/ai-best-practices` for an app that may call a model) and counts a rule only for a language present in the app |
| Give osv-scanner every lockfile | Kept in spirit: `sv` reads each ecosystem's own pins and matches against a database the owner downloads, without running osv-scanner |
| Stop asking Node questions of other apps | Kept. Nothing in `sv` assumes Node |
| Raise unpinned dependencies as a finding | Kept, in every ecosystem `sv` recognizes |
| Say what was checked, on the page | Kept, per rule and per language instead of per app |

## Alternatives considered

- **Keep ADR-012's ruling, and rely on outside tools alone.** Every outside tool is opt-in and may not be
  installed. Reported honestly as *not run*, that would leave an app with no code reading at all whenever
  nothing is installed. The widest of the tools, semgrep, also comes with a condition. Its rules are under a
  license that limits their use, and the owner's review on 26 September 2026 found SecureVibe's use
  acceptable only while nothing is sold or otherwise made money from.
- **Write many rules, to compete with semgrep.** ADR-012's warning against this holds. `sv`'s own rules are
  deliberately few, and each one has to earn its place with the samples above.
- **Stay Node-only, as v1 was.** The person now builds the app in their own tool, in whatever language it
  chooses, so a Node-only checker would turn most apps away.

## Consequences

- Adding a language takes three things: a grammar, a query for each rule or a stated reason why the language
  has nothing for that rule to find, and the samples each query must find and must not find. The design notes
  record what each addition cost ("Fourteen languages, and why the fifteenth silences everything").
- Every rule is `sv`'s to maintain in every language it is taught. That is the cost ADR-012 predicted, and it
  is kept small by keeping the rules few.
- If SecureVibe is ever sold or otherwise made money from, semgrep's rules must be re-examined first. `sv`'s
  own rules are the part of the code reading that has no such condition.
- ADR-012 stays as it was on the `v1` branch. History there is not rewritten. This record is where the ruling
  is replaced.

## Later, 30 September 2026

The weekly review of the records found the figures above out of date; the decision is unchanged. On this day
`data/ast-rules.json` holds 18 rules, not twelve, with queries in fifteen languages: the fourteen named above and
shell, which was already there when this record was written and which `DESIGN.md` counts apart. The six rules added
since are a digest compared with `==`, a model loaded with pickle, a model download not pinned, and a model name
that moves on its own (#377), a key made from a password with too few rounds (#450), and static files served from the
app's own folder. Every one keeps the rule stated above: a finding never becomes a pass, and each language a rule
cannot speak to says why.
