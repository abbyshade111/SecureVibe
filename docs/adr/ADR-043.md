# ADR-043: A seal is a signature any computer can check, against keys the owner chose to trust

**Status:** accepted. Chosen by the owner on 6 October 2026, after the Kaspa research (BACKLOG, "Research: could the
Kaspa blockchain …") recommended SSH-format signatures over a chain, and after session securevibe-e10 walked the owner
through the plan below. The owner took every recommendation ("go with the recommendations please"). Proposed with
the claim (#853) and built the same day; "Built" at the end says where the build differs from the plan. Changes part of
ADR-026, which says so in a dated "Later" entry.

**Governs:** `crates/sv-check/src/seal.rs`, `crates/sv-check/src/signed.rs`, `crates/sv-cli/src/review.rs`. A pull
request that changes any of these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv review` seals each answer a person records (ADR-026) with HMAC-SHA-256 under a key in
`~/.config/securevibe/review-key`. The same key makes a seal and checks it. So:

- **Only a computer holding the key can check a seal.** Since 6 October 2026, a sealed answer on any other computer
  (CI, the container, a second laptop) is a proposal, and the report says it carries a seal that computer cannot
  check (ADR-026, "Later, 6 October 2026: no key, no credit").
- **Giving CI the key would let CI make seals,** and anything that can read a CI secret during a run, the app's own
  build included, could seal answers as the owner.

A signature splits the key in two. The private half makes seals and stays on the owner's computer; the public half
checks them and can be copied anywhere without letting anyone make one. The research found SSH-format Ed25519
signatures (`ssh-keygen -Y sign`, `-Y verify`) need no network and no money, and that `ssh-keygen` alone can check
one. It found the same weak point in every design: the list of trusted keys. Whoever can add a key to it can seal.

## Decision

The owner's five choices, each the recommendation offered:

1. **A seal names an app id held in the trusted list, not only the folder.** The app id stays what it is today (16 hex
   characters of a SHA-256 of the app's folder on the computer where it was first sealed), and the trusted list says
   which key may seal for which app id. On the owner's computer a seal counts only when its app id is this folder's,
   as now. On a computer given a trusted list (CI), a seal counts when its app id and key are on that list, wherever
   the app's folder is there. An answer copied into another app still fails, because that app's list names another id.
2. **A new key, made for `sv` alone,** in the same folder as today's: `review-signing-key` (OpenSSH's own format, so
   `ssh-keygen` can read it) with `review-signing-key.pub` beside it. Not the person's existing SSH key.
3. **A passphrase is offered, not required.** `sv review` asks once, when it makes the key, whether to protect it with
   one; if so it asks for it, without showing it, each time it signs. It is the only step here an AI coding tool
   running as the owner cannot take for them, because it is held in the owner's head.
4. **Today's seals keep counting where they count today.** A `v2:` seal is still checked with `review-key` on the
   computer that holds it. The next `sv review` lists every entry whose `v2:` seal holds here and asks one yes to sign
   them all again, without asking each question again, since the seal already shows they were recorded here. Entries
   whose seal does not hold are asked about one by one, as now.
5. **Built with the `ssh-key` Rust library** (RustCrypto; Apache-2.0 or MIT), with its Ed25519 support, not by calling
   the `ssh-keygen` program, so the check is the same on every computer and in the container.

And what follows from them:

- **The seal** is written `v3:<app id>:<signature>`, the signature being an SSH signature (`SshSig`) in base64 on one
  line, under the namespace `securevibe-review`, over the same domain-tagged, length-prefixed fields as today. It
  carries the public key that made it, so no key id is needed beside it.
- **The trusted list** is in OpenSSH's `allowed_signers` format, one line per app and key, the app id as the
  principal and `namespaces="securevibe-review"` on each line: `~/.config/securevibe/allowed_signers` on the owner's
  computer, which `sv review` writes when it makes the key, and the variable `SV_TRUSTED_SEALS` anywhere else, which
  the owner sets from a repository variable on CI. When the variable is set it is the list; this is no weaker than the
  file, which the same tool could edit.
- **The report says which key it trusted and from where**: the key's SHA-256 fingerprint and "this computer's list"
  or "the list in SV_TRUSTED_SEALS", so the owner can compare it with the fingerprint `sv review` showed when it made
  the key.
- **`sv review` shows the public line to put in `SV_TRUSTED_SEALS`.** It is the public half, made to be shared; the
  private half is never printed, logged, or written anywhere but its file, as the rule for every key says.
- **Report seals are unchanged** (ADR-034): `sv report` seals its folder where it runs, CI included, where no person
  answers anything, so a signature would add nothing there.
- **No network and no money**, as before. One new dependency, `ssh-key`, and what it needs to make a key from the
  system's randomness and to read a passphrase without showing it; the pull request names each.

## Considered

- **Kaspa, or any blockchain.** Set aside on the research: it costs money for every seal, needs the network, forgets
  a transaction after about 30 hours on an ordinary node, and still cannot say which key is the owner's or who was at
  the keyboard.
- **Keeping the folder as the only app binding.** Simpler, but a folder on CI is never the one on the owner's
  computer, so nothing would count there, which is most of the point.
- **The person's existing SSH key.** One less key, but it would then sign for two unrelated purposes, and a key they
  use for servers or GitHub may be held by an agent `sv` should not drive.
- **A required passphrase.** The strongest, and the most tiresome: every review session asks. Offered instead.
- **Asking every recorded answer again.** The most cautious migration, but a `v2:` seal that holds here already shows
  the answer was recorded here.
- **Calling `ssh-keygen`.** No new library, but the container image would need OpenSSH, and `sv` would depend on
  whichever version each computer has.
- **A trusted list committed in the repository.** Set aside: the AI coding tool edits the repository, and adding its
  own key there is one line.

## Consequences

- **CI and the container can credit the owner's recorded answers** once given `SV_TRUSTED_SEALS`, without being able
  to make a seal.
- **What a seal still cannot show** (said in every report, as now): that a person, not a tool running as them, was at
  the keyboard, unless the key has a passphrase; and that a trusted key is the owner's, since whoever can change the
  trusted list, the local file or the repository variable, can add one. An AI coding tool with the owner's GitHub
  login can change a repository variable.
- **Two apps in one repository share one CI list,** so an answer copied from one into the other counts on CI there,
  though not on the owner's computer. The report on CI names the app id each seal was made for.
- **One more dependency** to keep current, and a seal about four times as long as today's on its line.
- To be held by tests that break each guard in turn: a forged signature, a changed field, a seal for another app, a
  key not on the list, a key on the list for another app or another namespace, a `v2:` seal on a computer without
  `review-key`, and a re-signed entry checked on a computer with only the public list.

## Built, 6 October 2026: where it differs from the plan

Built the same day by session securevibe-e10 (DESIGN, "Seals become signatures"), and this record made accepted in the
same pull request.

- **The signature is written in hex, not base64,** like every other part of a seal, so a notes file's
  `Sealed by sv review:` line, which takes only a seal of hex parts as a seal, reads it as one. A seal is 394
  characters (187 bytes of signature).
- **The passphrase is asked once per `sv review`,** when it unlocks the key, not once per signature. Three wrong ones
  stop it with nothing recorded.
- **`sv review` no longer makes `review-key`.** It only reads one already there, to check and sign again the entries
  sealed with it. Nothing else changes for those: on the computer that holds it, a `v2:` seal still counts.
- **A list `sv` cannot read in full trusts nothing.** A line with an option other than `namespaces` (OpenSSH's
  `cert-authority`, `valid-after`, `valid-before`), an unclosed quote, or a key that cannot be read makes the whole
  list unusable, and the report says which line. A principal is matched whole, so an OpenSSH pattern (`*`) never
  matches. A line with no `namespaces` trusts its key for every namespace, as OpenSSH reads it.
- **SV_TRUSTED_SEALS, when set and not empty, is the list wherever a report is made,** the owner's computer included;
  `sv review` itself uses only the file beside the key, the one it writes to.
- **Dependencies.** `ssh-key` 0.6.7, the latest release (0.7 is still a release candidate), and `ssh-encoding` 0.2,
  which `ssh-key` already uses, named directly to write a signature out as bytes; `libc`, already used by `sv-run`,
  in `sv-cli`, to stop the terminal showing the passphrase. Forty crates are compiled into `sv` that were not before,
  most of them for the passphrase (AES, ChaCha20, bcrypt-pbkdf) and older versions of `sha2`, `hmac`, and `digest`
  beside the ones `sv` uses.
- **Governs** `crates/sv-check/src/signed.rs` too, where the signing and the list are.

Held by `a_signed_seal_counts_where_a_list_trusts_its_key_for_the_app_and_nowhere_else`,
`a_key_the_list_does_not_trust_for_this_app_seals_nothing`, `a_list_sv_cannot_read_in_full_trusts_nothing`,
`the_signing_key_is_made_private_once_locked_when_asked_and_never_shown`, and
`ssh_keygen_checks_a_seal_with_the_same_list` (`crates/sv-check/src/signed.rs`), which has `ssh-keygen -Y verify` check
a seal against the same list; `seals_made_with_the_review_key_are_signed_again_at_one_yes` and
`a_passphrase_is_asked_for_when_chosen_and_nothing_signs_without_it` (`crates/sv-cli/src/review.rs`); and end to end in
`what_a_person_records_counts_and_the_report_says_where_its_seal_was_checked`, which now makes the report a second time
with no key and only SV_TRUSTED_SEALS, in another folder, and finds the owner's answer counted.
Broken on purpose fourteen ways, one at a time: the signature not checked, the folder not checked on this computer's list, the list's app ids ignored, its keys ignored, its namespaces ignored, an option it does not read accepted, the app id left out of what is signed, older seals not offered for signing again, the app not put on the list, the passphrase not kept, the key file readable by others, SV_TRUSTED_SEALS not read by the report, the variable read only where there is no folder, and the report not saying what to do. Every one was caught. Eight were caught by one test only, so a second test was written for each, in another test, and each then went red in two.

Not tested: that the terminal hides the passphrase as it is typed, which needs a person's terminal; the tests type it
where nothing is shown anyway. Not tried on a real CI run with a repository variable.
