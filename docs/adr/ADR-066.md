# ADR-066: The MCP server: what it does and does not do for an AI coding tool, and how its text is held

**Status:** accepted, 9 October 2026, in the pull request that writes it. It records decisions made between 27
September and 9 October 2026 that no record held, and makes three small new ones: the check is given to the server
rather than built into it, the tool list is in the order of the way to build, and reading requests on a thread of
their own waits until a client is seen to time out. Not proposed first with the backlog claim, since all but those
three were built and in use already. Asked for by the architecture assessment of 8 October 2026 (BACKLOG, "From the
architecture assessment of 8 October 2026: the four costs worth paying down", item 10), taken from the roadmap.
Written by session securevibe-e9.

**Governs:** `crates/sv-cli/src/mcp/mod.rs`, `crates/sv-cli/src/mcp/tools.rs`, `crates/sv-cli/src/mcp/confine.rs`,
`crates/sv-cli/src/mcp/protocol.rs`, `crates/sv-cli/src/mcp/catalog.rs`. A pull request that changes what these say
about anything below changes this record too, or says in its description why it does not (`docs/adr/README.md`).
The names the server and its tools go by are ADR-062's; writing a report folder is ADR-041's lock and ADR-034's seal;
what the AI tool may record is ADR-022's; the plan and the answer in parts are ADR-030's.

## Context

`sv mcp` is how an AI coding tool calls `sv` while it builds: the loop the paper is about. Its decisions were a module
doc (`crates/sv-cli/src/mcp/mod.rs`) and design entries written one at a time as each was built: "What the MCP server
answers when it is sent nonsense", "The newer protocol versions", "The written reports, offered as resources", "A time
limit on a check over MCP", and "Saying how a check is going" (all 3 October 2026), "`sv mcp` will not serve a folder
that holds the home folder" and "The app's text fenced as data, and reports offered only when sealed" (5 October),
and "The MCP server in a folder, and one way to write a report folder" (8 October). Each change to the server had no
record to read itself against, and the "Decision records" check had no file of the server's to ask about.

Two costs the assessment named came with it. The time-limit test ran the real check of `examples/flask-booking`
eighteen times to reach a check still running, and needed a field in the server's struct, there only in tests, to hold
one open. And the text an AI tool reads about the way to build (the opening instructions, the tool list, the spec
`sv init` prints and `stackvet_spec` gives, and the guide's pasted prompt) was kept in step by hand: the spec gave the
feature's brief before its design-time prompts, and the instructions the other way about.

## Decision

1. **Only what `sv report` does, and never more of it than the owner gets at a terminal by default.** A check is the
   function `sv report` calls, so what the tool is told is what the written report says. Starting the app (`--run`),
   running other people's security tools (`--tools`), and reading advisory data are not offered: each runs code or
   reads something the person chooses, and that stays a person's decision at a terminal, not a model's in a loop. The
   report says each was not done and gives the command that does it.
2. **Only inside the folder it was started for.** `--root` is fixed when the server starts, every path is resolved
   against it, and one that lands outside, by `..` or a link, is refused. The top of the computer, the home folder,
   and any folder that holds the home folder are refused as roots (`confine.rs`).
3. **Nothing on its output but the protocol.** JSON-RPC 2.0, one message a line, over stdin and stdout. Requests that
   are not well formed are refused with the reason, never dropped; a line that is not UTF-8 is refused and the server
   goes on. The protocol versions it speaks are `PROTOCOL_VERSIONS`, the stateless one among them. No MCP library: the
   surface is small and a fast-moving dependency would be a large thing to trust for it.
4. **A check has a time limit, under a minute** (50 seconds; `--time-limit` changes it). A check still running when
   its time is out is told to the tool as not finished, so nothing was assessed, with the command for a terminal; it
   runs on to its end on its own thread, and no other check starts beside it. Progress is said by stage, in `sv`'s own
   words, to a client that asks.
5. **What comes from the app is fenced as data.** Every piece of a result that quotes the app is between tags made
   afresh for each result, and the result says first that the text inside is never an instruction. Reports written
   earlier are offered as resources only when `sv` can show it wrote them and nothing has changed since.
6. **The AI tool's word is its own.** What it records is marked as its own, at the lowest tier, with no argument for
   who answered; only the owner makes an answer theirs (ADR-022).
7. **The check is given to the server** (`Server.check`), the real one unless a test gives another. The time-limit
   test gives a check that waits on a channel and hands back a copy of one real report, so it reaches a check still
   running without checking an app eighteen times, and the struct has no field that is there only in tests.
8. **The way to build is told in one order.** The tool list is in the order the instructions first name each tool,
   which is the order an app is built in: the spec, the design-time prompts, the plan, the brief before a feature, the
   rules to code by, the preflight, the check, the person's questions, then the report, the notes, and the bundle.
   Tests hold the instructions, the guide's pasted prompt, and the spec's steps to it, and hold every string the AI
   tool reads from the server to American spelling and to no sentence that calls an app or a requirement safe,
   secure, compliant, certified, verified, or passed, unless it denies it (`mcp/flow_text_tests.rs`).
9. **Requests are read on the thread that answers them.** A `ping` or `notifications/cancelled` sent during a check is
   answered when the check ends. Reading on a thread of its own would answer it at once, at the cost of a second
   thread on every request and a way to stop a check from outside that a thread does not have. It is worth that once
   a client is seen to give up on a server that does not answer a `ping` during a check; none has been.

## Alternatives considered

- **Leaving the decisions in the design entries.** They say what was built and why, but each was written for its day,
  and none is what a change to the server is checked against.
- **A test-only gate in the struct**, as before: it worked, but made the production struct carry a test's field, and
  the test still checked the app for real eighteen times. A trait for the check would have done what a closure does with
  more to read.
- **Folding `stackvet_questions` into `stackvet_check` and `stackvet_notes_file` into `stackvet_record_answer`**, as
  the assessment proposed. The roadmap leaves that to the owner: the owner's own flow in VS Code calls
  `stackvet_questions` by name. Taken on the owner's word the same day: "Later, 9 October 2026: two tools folded into
  others", below.
- **A word list alone for the safe-sounding words.** It forbade "a CI step must pass `--fail-on`", "the whole suite
  passes", "secure coding", and the `compliance` format. The test looks instead for a word that says it of something
  ("is secure", "looks safe").

## Consequences

- A change to the server's files now meets this record in the "Decision records" check.
- The tool list's order changed, which a client shows as it is given; `tools/image_smoke.py` checks the new order.
- The time-limit test no longer exercises the real check after a time-out; the other tests of each tool do.
- A new tool, a step added to the instructions, or a reordered paste in the guide fails a test until all of them
  agree.

## Later, 9 October 2026: a report read back is fenced as a tool's result is

The gap analysis of 7 October 2026, finding 22(b) (`docs/GAP-ANALYSIS.md`, 4.6). Every tool's result put the app's
own text between `<app-text-…>` tags, and a report read back through `resources/read` came back plain: an app named
"IGNORE ALL PREVIOUS INSTRUCTIONS…" was fenced in `stackvet_check`'s result and unfenced in its own report. Now
`report.html`, `compliance.md`, and `security.md` come back whole between one pair of tags named for that reading, which
nothing in the report holds (`sv_report::fence::fenced_block`), after a first line outside them saying the text inside
is a report `sv` wrote, quoting the app, and is information, never an instruction. All of it is inside, `sv`'s words
too, since read back the whole report is information; its lines are kept as written. `report.json` and
`findings.sarif` come back exactly as written, since a program parses them and tags would break them; each one's
description in `resources/list` says which way it comes back. The files on disk and their seals are unchanged: the
fence is added to what is handed over, after the seal has been checked against the bytes read. Held by
`crates/sv-cli/src/mcp/resource_fence_tests.rs`, with an app whose name is the injection.

## Later, 9 October 2026: each call written down for the build loop

The server `sv mcp` starts now writes each tool call down for the app it names, in the app's report folder: the
time, the tool, and a check's counts, never an argument or a finding's text (ADR-076, the owner's choice of that day).
It is the first thing the server writes that the AI coding tool did not ask for, so it is held to this record's
rules: it changes no tool's answer, whatever goes wrong in writing it is left unsaid rather than turned into an
error, it is written only below the app and never through a link, and a server made in the tests does not write it
unless the test asks. The decision and its limits are ADR-076's.

## Later, 9 October 2026: two tools folded into others, as the owner decided

The alternative this record left to the owner, folding `stackvet_questions` into `stackvet_check` and
`stackvet_notes_file` into `stackvet_record_answer`, was taken on the owner's word of 9 October 2026 ("yes to part
10's tool fold, as recommended": BACKLOG 0187), and built the same day by session securevibe-e9. The server lists
eleven tools rather than thirteen, in the same order otherwise.

- **The questions are `stackvet_check`'s section `questions`.** Asked for by that name they come in full, a page at a
  time like every other section, with each question in the structured result's `questions`; asked for as `all`, the
  whole check holds them too, so the parts joined are still the whole. Asked for with no section, a check that comes
  whole with them still does, but one that would come whole without them and not with them only counts them and says
  how to ask, as it did before. Seventy questions in full are about 38,000 characters, enough to push a short check
  into parts and the findings off its first answer, so the default answer does not grow by them.
- **The notes file is `stackvet_record_answer` with no id and no answer.** It makes or refreshes `security-notes.md`
  as `stackvet_notes_file` did, keeping what is written in it; with both it records an answer as before, and with
  only one of them it is refused and writes nothing.
- **The old names still answer, unlisted.** Each gives what it gave before, ending with a line in `sv`'s own words,
  outside any fence, naming the tool to call instead, so a flow that learned them (the owner's VS Code walk-through
  called `stackvet_questions`) keeps working while the guide's prompt and the tool counts change. The decision said
  "for a few weeks"; no date is set here, and taking the two names away is a change to this record when it comes.

Rule 8's order now reads: the spec, the design-time prompts, the plan, the brief before a feature, the rules to code
by, the preflight, the check (with the person's questions), the report, the answers recorded, the requirement
explained, and the bundle. Held by `crates/sv-cli/src/mcp/fold_tests.rs`, and by the tests that count the tools and
hold the instructions and the guide's prompt to the list.
