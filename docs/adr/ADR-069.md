# ADR-069: A line break and a Bcc header in the address a reset is mailed to (V1.3.11)

**Status:** accepted, 9 October 2026, in the pull request that builds it; proposed with the backlog claim (0085, part
16). Asked for by the owner ("please continue to work through and pick up new items as you merge"). Written by session
paper-facts.

**Governs:** `crates/sv-check/src/signed_in/reset.rs`, where the check this record adds, probe.mail-header-injected,
follows the password-reset check. A pull request that changes what it says about this changes this record too, or
says in its description why it does not (`docs/adr/README.md`).

## Context

ASVS V1.3.11 (level 2) reads: "Verify that the application sanitizes user input before passing to mail systems to
protect against SMTP or IMAP injection." Nothing in StackVet speaks to it. The signed-in checks already ask the app
for a password reset and read what it mails from the run's own mail server, which lists every recipient of every
message, `Bcc` included. An address typed into a form, carrying a line break and a header of its own, becomes a header
of the message when the app hands the text to its mail library as it came: the classic way to make an app's own mail
account send to anybody.

## Decision

- **Asked only after the reset check has seen its own email arrive**, so the mail server is known to work and the
  account to be reachable.
- **Two more reset requests** for the same account: its address followed by `\r\n` and then by `\n` alone, each with
  `Bcc: ` and an address of `sv`'s own, made for the run.
- **A finding (high)** when any message reaches `sv`'s address: the app's mail account sends where a stranger tells it.
- **Credited, marked in part (ADR-053),** when the account receives a reset email after the requests and nothing reaches
  `sv`'s address: the app took the line break out, or refused it as part of the address and still mailed the account.
  One field and one kind of mail were tried.
- **Not assessed**, and said, when no email is sent for either request: an app that finds the account by the exact
  address it was given sends nothing, and that says nothing either way.

## Alternatives considered

- **The sign-up form's address too.** Not here: a sign-up that accepts the address makes an account with it, which the
  checks after it would have to work around.
- **Full credit.** Rejected: other fields (a subject, a name) and other mail (a contact form) were not tried.

## Where the build differs from the proposal

- **Asked after the whole reset, not straight after its email arrives.** A new reset request may cancel the code the
  reset check was about to use, which an app is right to do, so the two requests come last; the reset check reports
  whether its email arrived, and only then are they sent.
- **Said when not asked.** When the reset email never arrived, or there is no `reset`, V1.3.11 is said as not assessed:
  the suite holds every requirement to be named in every configuration, and that guard caught the first version.
- **Not run end to end** with an app under `sv run`, which needs Docker and Mailpit.
