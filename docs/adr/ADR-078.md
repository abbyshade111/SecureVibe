# ADR-078: CodeQL for Ruby, and for Java only where it reads the code without building it or reaching the network

**Status:** accepted for Ruby, 9 October 2026, in the pull request that builds it; Java not added, as the decision
below says when it cannot stay offline. Proposed the same day with the backlog claim (0147, item 7). The owner's
decision, the same day: "let's go ahead with Ruby and Java once confirmed it stays offline". Written by session
securevibe-e9. What was found is at the end.

**Governs:** `data/codeql-suites.json`, which lists the queries each CodeQL suite runs, and the codeql-ruby and
codeql-java entries in the adapters' file, which is not listed here, since it is changed often for other tools (as
ADR-064 says of the AI checks' file). A pull request that changes what they run or credit changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

CodeQL follows a value from where it enters the app to where it is used, which no rule `sv` writes can do. It runs
today for JavaScript, TypeScript, and Python (codeql-javascript and codeql-python), each reading the code without
building it, offline, and crediting four requirements no other check reaches. The bundle a person installs for those
already carries Go, Ruby, and Java. Go cannot be read without building it, and its build fetches the app's modules
over the network, which `sv` does not do (`CLAUDE.md`, ADR-027 and ADR-052 for the only exceptions); so it is left out.
Ruby needs no build. Java can be read without one (CodeQL's build mode "none"), and whether it then reaches for the
network to fetch the app's dependencies is to be seen, not assumed.

## Decision

- **codeql-ruby:** the bundle's `ruby-security-extended` suite, run as the two others are: a database made from the
  source without a build, analyzed offline, removed afterwards.
- **codeql-java:** the `java-security-extended` suite, with `--build-mode=none`, added only after a run here shows
  it opens no network connection: run with no route out, it must finish with the same results as with one, and a run
  that tries to fetch anything is the end of it. If CodeQL offers a setting that turns the fetching off, it is used and
  named. If it cannot be made to stay offline, Java is not added, and the item says why.
- **Each rule cited only where it speaks to the requirement**, as for the other two: the map is read rule by rule,
  a rule that fits none is left unmapped and its finding still shown, and a clean run credits only the rules its
  report says ran (`credit_loaded_only`). Java read without a build may miss some results, so its credit says so.
- **Not Go**, for the network fetch above, unless the owner decides otherwise.

## Alternatives considered

- **Java with a build.** More accurate, but it runs the app's own build (Maven or Gradle and their plugins), which is
  the app's code running on the person's computer outside the fence, and it fetches dependencies.
- **All three languages at once.** Go's fetch is a decision for the owner, not a data change.

## Consequences

- Two more entries in `data/adapters.json`, each with its map, and the coverage files regenerated.

## What was found, 9 October 2026, with CodeQL 2.27.2

- **Ruby is added** (codeql-ruby). With no network at all, building the database and analyzing it gave the same
  results as with one. A planted `Gemfile`, `Rakefile`, `bin/bundle`, and `bin/setup`, each written to leave a mark,
  left none, and a link to a file and to a folder outside the app put nothing of either into the database. On a Rails
  controller it found nine problems (SQL, command, and code injection, cross-site scripting, an open redirect, a path
  from a parameter, unsafe deserialization, a regular expression from a parameter, and CSRF protection not enabled);
  on a plain Sinatra file, none, since its models are Rails's. 24 of the suite's 50 queries are mapped: 21 cite what
  their twin in the JavaScript or Python map cites, and three are Ruby's own (`rb/kernel-open`, V1.2.5;
  `rb/regexp-injection`, V1.2.9, as `regex-injection` does in the other two; `rb/insecure-mass-assignment`,
  V15.3.3). The queries the other two maps leave unmapped are left unmapped here too, and so is
  `rb/csrf-protection-not-enabled`, which flagged a controller on a Rails base class that turns the protection on by
  default. No requirement's level count moves: each one Ruby reaches had a check already.
- **Java is not added.** Its build-less mode is not build-less: CodeQL found Maven and ran it on the app's
  `pom.xml` with a plugin of its own, and Maven reached for Maven Central to fetch the app's dependencies. Offline, the
  same app gave one result where online gave three, since the dependencies are what let CodeQL follow a value. Worse,
  with a `gradlew` planted in the app, CodeQL ran it: the planted script left its mark. That is the app's own code run
  on the person's computer outside the fence, which `sv` never does. No setting turns this off (the extractor's
  options choose where dependencies go, not whether they are fetched), and hiding Maven does not stop CodeQL looking
  for the app's own wrappers. Copying only the `.java` files elsewhere would keep both out, but found one of the
  three problems. So, as decided above, there is no Java entry, and an app in Java is told CodeQL is not run for it
  the way any language without an entry is.
- **`tools/codeql_suites.py --only`** measures one adapter's suite and keeps the rest as recorded, for a bundle that
  carries only some languages' query packs, as the one used here did.
