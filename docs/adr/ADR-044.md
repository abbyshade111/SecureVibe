# ADR-044: The coding prompts shown to work reach the AI tool when it builds what they are for

**Status:** accepted. Decided by the owner on 6 October 2026, after the prompt-library trial
(`docs/prompts/library-trial/`), as the first of two changes before testing how a prompt is best delivered (BACKLOG,
"Test the prompt library where the prompts have something to fix", item 4).

**Governs:** `crates/sv-cli/src/brief.rs`. A pull request that changes it changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

The prompt-library trial showed four coding prompts working where the problem they are for was common: the AI
feature's guard, the security headers, private pages kept out of the cache, and keys kept out of the code. A prompt
helps only if the AI tool has it while it writes the code it is for. Until now the MCP server offered the coding
prompts only through `securevibe_prompts`, a tool the builders in the loop trials seldom called, and
`securevibe_before`, the brief for one feature that builders did call, gave only the design-time prompts.

## Decision

- **The brief for a feature** (`sv brief`, `securevibe_before`) gives, under "Rules to code by", every coding prompt
  the library marks `shown` whose requirements include one the feature brings, applying now or once
  securevibe.toml says the app has the feature.
- **The guidance** (`securevibe_guidance`, asked with no topic) ends with every other coding prompt marked `shown`:
  those none of whose requirements any feature brings, which are about the whole app (`whole_app_prompts` in
  `crates/sv-cli/src/main.rs`). So each shown prompt reaches a builder once, from the brief for its feature or from
  the guidance the server's instructions ask it to read before writing code.
- **Only prompts shown to work.** A prompt not shown is not offered at the moment a feature is built: it has not been
  shown to change anything, and it would crowd the ones that have. `securevibe_prompts` still gives every prompt, each
  marked.
- **Nothing is credited** for a prompt given or followed, as before (ADR-028, "Nothing is credited";
  `crates/sv-check/src/prompts.rs`, "What it is worth"). ADR-028's own "Later, 6 October 2026" entry records
  that the coding prompts no longer stay only with `securevibe_prompts`.

## Alternatives considered

- **Every prompt, marked.** More to read at the moment of building, most of it not shown to matter.
- **Only in the plan.** The plan is read once, at the start; a feature's brief is read when that feature is built,
  which is when its prompt is needed.

## Consequences

- **Whether this delivery works is measured,** not assumed: the delivery test compares builds with this `sv` and
  without it, the full server attached to both (`docs/prompts/library-trial/`).
- A test holds the promise: across every feature's brief and the guidance, each shown prompt appears exactly once
  and no other does (`every_coding_prompt_shown_to_work_reaches_the_builder_once_and_no_other_does`); each part of
  it was broken on purpose and caught.

## Later, 6 October 2026: the delivery test

Tested as the Consequences said (`docs/prompts/library-trial/delivery.md`): with this `sv`, a feature's brief
seldom reached the builder, because `securevibe_before` refuses until `securevibe.toml` exists and builders ask for
it first; the guidance did reach them, and helped, less than pasting the same prompt into the request. So delivery
through the brief is not shown to work, and the decision stands only as the first place the prompts are given: the
backlog has the two changes the test points to (a brief that answers before the file exists, and the shown prompts
named where every builder starts). A delivered prompt also did harm once: `secrets-in-the-environment` made an app
refuse to start without a key `sv run` cannot give it.

## Later, 7 October 2026: and where every builder starts

At the owner's word, after the delivery test: the coding prompts marked `shown` are also given in full at the end of
the specification (`sv init`, `securevibe_spec`) and of the MCP server's opening instructions, both read before any
code, by `prompts_at_start()` in `crates/sv-cli/src/main.rs` from `data/prompts.json`. The brief and the guidance keep
giving them too. A test holds that every shown prompt is in both places in full and no other is
(`the_prompts_shown_to_work_are_where_every_builder_starts_and_no_others`). Whether it works is measured by
`docs/prompts/library-trial/start-protocol.md`.


## Later, 7 October 2026: the brief before securevibe.toml

The delivery test of 6 October 2026 found that most builders asked for a feature's brief before writing
`securevibe.toml`, were refused, and seldom asked again, so the AI feature's brief, which carries `ai-feature-guard`,
reached few of them (BACKLOG, "`securevibe_before` refuses until `securevibe.toml` exists"). The brief now answers
without the file: it gives the coding prompts shown to work whose requirements include any the feature can bring, at
any level, since no level is known yet to narrow them, and says that which requirements apply, and the tests, wait for
the file. Once the file is written, the brief narrows to what this record's decision says. Everything else in this
record stands.

## Later, 7 October 2026: two more prompts shown, one that credits nothing

The owner marked `isolate-the-window` and `security-contact` shown after the revision trial
(`docs/prompts/library-trial/revision.md`), so both now reach every builder by this record's routes. `isolate-the-window`
was shown on Sonnet 5.5 (10 of 10 builds with the problem without it, 0 of 10 with it) and not on Haiku 4.5 (7 of 7, then
4 of 10), and the owner chose to show it with Haiku's result recorded. `security-contact` is the first shown prompt that
credits no requirement: it asks for a `SECURITY.md` and a `security.txt` page, which say how to report a problem and
nothing about how secure the app is. Having no requirements, it reaches a builder through the opening instructions,
the specification and the guidance, and through no feature's brief. Everything else in this record stands.

## Later, 7 October 2026: `production-server` shown

The owner marked `production-server` shown after the recipe trial (`docs/prompts/library-trial/recipe.md`): with
Sonnet 5.5 on a Flask app, the server's version given away in 5 of 10 builds without it and 0 of 9 with it. It now
reaches every builder by this record's routes. Its last sentence, on running one worker with SQLite, is not yet tried.
Everything else in this record stands.

## Later, 7 October 2026: `password-rules` shown

The owner marked `password-rules` shown after the three sentences' trial (`docs/prompts/library-trial/sentences.md`):
with its sentence naming `zxcvbn`, a common password accepted in 0 of 10 Sonnet builds, against 10 of 10 in the recipe
trial without the prompt. It now reaches every builder by this record's routes. The same trial tried
`production-server`'s SQLite sentence (above) and `isolate-the-window`'s sentence on Python's own error pages; both are
kept. Everything else in this record stands.
