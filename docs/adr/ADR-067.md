# ADR-067: A session that is one fixed key, found from repeated sign-ins (V7.2.2)

**Status:** accepted, 8 October 2026, in the pull request that builds it; proposed with the backlog claim (0085, part
14). Asked for by the owner ("please continue to work through and pick up new items as you merge"). Written by session
paper-facts. Numbered ADR-066 in the claim at first; that number went to the MCP server's record, merged just before.

**Governs:** `crates/sv-check/src/signed_in/sessions.rs`, where the check this record adds, probe.session-token-static,
sits beside probe.session-id-weak. A pull request that changes what it says about this changes this record too, or says
in its description why it does not (`docs/adr/README.md`).

## Context

ASVS V7.2.2 (level 1) reads: "Verify that the application uses either self-contained or reference tokens that are
dynamically generated for session management, i.e. not using static API secrets and keys." Nothing in StackVet
speaks to it. `probe.session-id-weak` (V7.2.3: reference tokens unique, from a CSPRNG, with 128 bits) signs the first
test user in a second time and finds a cookie whose value repeats, among other things. It never compares two users,
which is where one key for everybody shows, and it stops at once when the app signs in with a token rather than a
cookie, which is where a fixed key is most often handed out.

## Decision

- **Three sign-ins:** the first test user's, the second sign-in of the same user that `probe.session-id-weak` already
  makes, and one of the second test user, all at the end of the signed-in checks where the others already sign in
  again.
- **The session values compared:** each cookie the sign-in answer set, by name, and the token when the app answers
  with one.
- **A finding (high)** when any of them is the same at two of the three sign-ins, saying which and between whom.
- **Credited** when there is at least one session value and every one differs at all three: V7.2.2 asks that the
  session is not one static key, and three different values from three sign-ins is that, seen. It does not show how
  they are made, which is V7.2.3's question and stays its own.
- **Not assessed**, and said, when the sign-in did not work, the second user could not sign in, or no session value
  was given.

## Alternatives considered

- **Add V7.2.2 to `probe.session-id-weak`.** Rejected: that rule also finds a cookie too short to hold 128 bits, which
  says nothing about V7.2.2, so its findings would cite a requirement they do not show failing.
- **Finding only.** Rejected: unlike randomness, being static is something the values themselves show either way.
- **The static half from `docs/PARTIAL-CHECKS.md`** (a key set in the browser's code from a literal or a public
  variable). Left out: a public key for a map or analytics service looks the same, and it belongs with the code rules.

## Where the build differs from the proposal

- **Two sign-ins of one person, not three of two.** `sv` promises at most 60 sign-ins in a run (`SIGN_INS_IN_A_RUN`),
  and the busiest run in the tests was already there, so the check uses the second sign-in of the first test user
  that `probe.session-id-weak` already made, and no new one. The second user is signed in only by the owned-records
  check, when there is one. A key fixed for everybody, or for each person, is the same at two sign-ins of one person
  either way.
- **That second sign-in is now made for an app that signs in with a token too**, where before it was skipped; the
  V7.2.3 comparison stays for cookies only.
- **Credit needs the new session to open the private page**, so a sign-in that failed quietly and handed back an empty
  session is not taken for a new one. A sign-in answered by the limiter, or one that set again only some of the
  values, is said.
- **A repeated cookie is found by both rules**, since it breaks both requirements; the tests that hold each flaw to one
  rule state this pair.
- **Not run end to end** with an app under `sv run`, which needs Docker.
