# ADR-077: The readers of untrusted input fuzzed weekly, apart from the workspace and the tests

**Status:** accepted, 9 October 2026, in the pull request that builds it; proposed the same day with the backlog claim
(0191, part 3). The owner's decision, the same day: "go ahead with the fuzzing please". Written by session
securevibe-e9. Where the build differs from the plan is at the end.

**Governs:** `fuzz/Cargo.toml` and the targets beside it (`fuzz/fuzz_targets/*.rs`), `fuzz/seed.sh`, and
`.github/workflows/fuzz.yml`; and the exclude line in the workspace's `Cargo.toml`, which ADR-020 governs and which is
not listed here.
A pull request that changes what these say about fuzzing changes this record too, or says in its description why it
does not (`docs/adr/README.md`).

## Context

`sv` reads what an app, an AI coding tool, or an outside tool hands it: messages on the MCP server's input, the app's
`stackvet.toml`, lockfiles and software bills of materials, and the reports semgrep, CodeQL, and the other tools
write. A file planted in an app that makes `sv` panic, or run for ever, stops the check, and the person is left with
no report rather than a finding. The tests feed each reader the inputs someone thought of; nothing feeds them the ones
nobody did. Fuzzing does: a program mutates inputs by the million and keeps the ones that reach new code, until one
crashes.

## Decision

- **`cargo fuzz`** (libFuzzer), the usual tool for Rust, in a crate of its own at `fuzz/`, kept out of the workspace,
  so `cargo test --workspace`, the build, and the image are unchanged and gain no dependency.
- **Targets, one per reader:** the MCP server's handling of one line of input; `stackvet.toml`; the lockfile and
  software bill of materials readers; and each outside tool's report reader. Each target calls the same function `sv`
  calls, and asserts only that it returns, with an answer or an error, rather than panicking.
- **Run weekly, and by hand,** in a workflow of its own (fuzz.yml, beside the other workflows), a few minutes a target, on
  Rust's nightly toolchain, which `cargo fuzz` needs and which nothing else uses. The repository is public, so the
  runs cost nothing. The weekly run is not a required check: it tests `main`, not a pull request.
- **A crash becomes a test.** A crash the run finds is kept as a file the workflow uploads; it is fixed by adding the
  input to the ordinary tests first, seeing it fail, then fixing the reader, so the fix is held by `cargo test` on the
  stable toolchain, and the fuzzing run finds the next one.
- **Starting inputs** are the examples and fixtures already in the repository; nothing is downloaded.

## Alternatives considered

- **Property tests (`proptest`) inside the ordinary suite.** Run on every pull request, but they generate inputs from
  a description someone wrote, which finds less in a parser than fuzzing's coverage-guided mutation, and they add
  time to every run of the tests.
- **Fuzzing on every pull request.** A few minutes a target on each pull request is a large share of CI's time for
  inputs that change rarely; weekly, and by hand after a change to a reader, is enough.

## Consequences

- One more workflow, and a crate that builds only on nightly Rust. A change to a reader's function signature breaks
  its target, which the weekly run reports.

## Where the build differs from the plan

- **Four targets, not one per reader.** `mcp_line` feeds whatever arrives on the MCP server's input to the server's
  own loop (`sv_cli::mcp::serve`, made public for it), serving an empty folder so a tool call is refused rather than
  checking anything. `manifest` is `stackvet.toml`. `lockfiles` reads the same text as every lockfile format `sv`
  reads (one hidden public function in `sv_check::sbom`, `read_as_every_lockfile`, rather than widening sixteen
  readers) and as the app's own test report (JUnit XML, TAP, or JSON). `tool_reports` reads it through every
  adapter's SARIF reader. One target per reader would have meant twenty-odd binaries for the same coverage.
- **No software bill of materials reader**, because `sv` writes one and reads none.
- **The starting inputs** are copied by `fuzz/seed.sh` from the repository's examples and test fixtures (9 manifests,
  11 lockfiles and test reports, 12 tool reports, and one MCP session), into a folder that is not committed.
- **Tried here first.** A minute each on 9 October 2026 found nothing (from 14,000 runs for `mcp_line` to 455,000
  for `lockfiles`), and a crash planted in the manifest reader, on any input holding a chosen word, was found and its
  input written out within the two minutes given.
