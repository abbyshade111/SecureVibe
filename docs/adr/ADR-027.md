# ADR-027: `sv probe` asks only public addresses, and only the ones it checked

**Status:** accepted. Decided on 4 October 2026, when the owner asked for the deep review's S13 to be built. Until
now the one network exception `sv` makes had no record of its own: it was a sentence in `CLAUDE.md` and in ADR-017.

**Governs:** `crates/sv-check/src/production.rs`, `crates/sv-check/src/live_tls.rs`. A pull request that changes any
of these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv` opens no network connection of its own, with one exception the owner asks for by name: `sv probe <address>`
asks the live site a few read-only questions through `curl` (at most four requests), and asks this computer's
resolver once about its HTTPS records. The address is typed by a person, which is the consent.

The deep review of `sv` at `eff3f17` found two ways the exception was wider than it said (S13, low, reproduced):

- **Any address was accepted that was not `localhost` or `127.*`.** `https://10.0.0.1`, `https://169.254.169.254`
  (where cloud machines keep their credentials), or a public-looking name that looks up to a private address would
  all be asked. A person who is told to run `sv probe` on an address, by a page, a README, or an AI coding tool,
  could then be made to reach their own network.
- **curl's globbing was on**, so `{a,b}` or `[1-9]` in an address turned one request into several, past the cap.

While building the fix, a third came to light: `--disable`, which stops curl reading a `.curlrc`, was written
after other flags, and curl reads it only as the very first argument. A `.curlrc` on the owner's computer could
have added headers, cookies, or another address to every request.

## Decision

- **Public addresses only.** An address on this computer, a private network (10/8, 172.16/12, 192.168/16, fc00::/7),
  a shared network (100.64/10), a link-local range (169.254/16, fe80::/10), the unspecified address, multicast,
  broadcast, and the ranges kept for testing and the network's own use are refused, typed or looked up. An IPv6
  address carrying an IPv4 one is judged by the IPv4 one. The message says what the address is and points at
  `sv report --run` for checking the app locally.
- **Looked up once, by `sv`, and held to it.** The name is looked up through this computer's own resolver, as
  curl would have done. If any address it gives is refused, the whole name is. Then every curl is given
  `--resolve` for each port it may use, so it connects only to the addresses checked and cannot get a different
  answer from a second lookup.
- **One address is one request.** `--globoff` on every curl, and an address holding `{`, `}`, `[`, or `]` (other
  than around an IPv6 address) is refused before curl sees it.
- **Every curl starts `--disable --globoff --proto =http,https`**, in one place (`Curl::args`), so no `.curlrc`
  is read and nothing but a web address can be asked.

## Alternatives considered

- **Let curl look the name up, and check afterwards which address it used.** By then the request has been made.
- **Ask the owner to confirm a private address.** `sv probe` is for the address the app is served from to the
  public; a private one is checked with `sv report --run`, inside the fence.
- **Turn off the system's proxy** (`--noproxy '*'`). Left as it is: on a network that needs a proxy, the probe
  would stop working. Through a proxy, the proxy looks the name up rather than curl; the check above still refuses
  any name that looks up to an internal address on this computer.

## Consequences

- An app served only on a private network, or behind a name that looks up to one, cannot be probed. That is the
  point, and the message says what to use instead.
- The lookup curl used to make is now made by `sv`. It is the same question to the same resolver, so the number of
  connections `sv probe` makes does not change.
- Through a proxy, `--resolve` does not apply, and the proxy decides where the request goes.

## How it is held

In `crates/sv-check/src/production.rs`: `an_address_on_this_computer_or_its_network_is_refused_however_it_is_written`,
`a_name_that_looks_up_to_an_internal_address_is_refused_and_curl_is_held_to_what_was_checked`, and
`every_curl_reads_no_config_globs_nothing_and_speaks_only_http`. End to end, with a `curl` of the test's own on the
path: `an_internal_address_is_refused_before_anything_is_asked` and
`a_public_address_is_asked_with_no_config_no_globbing_and_web_addresses_only`
(`crates/sv-cli/tests/probe_addresses.rs`). Seven guards were undone in turn, and each turned a test red.

## Later, 5 October 2026 (the second weekly review)

One sentence above promises more than the code does. An IPv6 address is judged by the IPv4 one inside it only when it is
written `::ffff:a.b.c.d` or `::a.b.c.d` (`not_public`, `crates/sv-check/src/production.rs`). A 6to4 address
(`2002::/16`) and a NAT64 one (`64:ff9b::/96`) carry an IPv4 address too and are not judged by it, and the documentation
ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32) are not refused. Fixing it is a backlog entry
("`sv probe` and the IPv6 forms that carry an IPv4 address").

## Later, 5 October 2026: the IPv6 forms that carry an IPv4 address, and the documentation ranges

The gap the entry above names is closed (BACKLOG, "`sv probe` and the IPv6 forms that carry an IPv4 address"). `not_public`
now judges by the IPv4 address inside it every IPv6 form that is routed to that address: 6to4 (`2002::/16`, the
address in its second and third groups), NAT64's well-known prefix (`64:ff9b::/96`, in its last two), and Teredo
(`2001::/32`, the client's address in its last two, each bit inverted), besides `::ffff:a.b.c.d` and `::a.b.c.d` as
before. NAT64's prefix for a network's own translator (`64:ff9b:1::/48`, RFC 8215) is refused outright, since where its
IPv4 address sits is that network's choice. The documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24,
2001:db8::/32) and IPv6's old site-local range (`fec0::/10`) are refused. Each form is held by a case in
`an_address_on_this_computer_or_its_network_is_refused_however_it_is_written`, with a control for 6to4, NAT64, and
Teredo carrying a public address, which is still accepted. The record's rule is unchanged: only a public address is
asked.

## Later, 6 October 2026: no proxy, plain HTTP on port 80, and a certificate problem only when curl says so

From the review of 1 to 4 October (items 1 to 3). curl is told to use no proxy, since a proxy looks the name up itself
and the request would not be held to the checked address; the plain-HTTP question goes to port 80, held there too, and
is credited only for a refused connection; and a failed verified request is a certificate problem only when curl says
the certificate was, so a timeout answered on the retry is not assessed. Still at most four requests. The decision
stands.

## Later, 6 October 2026: one more request, to an API address the owner names

The owner's decision, 6 October 2026 ("Yes, please go ahead with both of those"), asked whether `sv probe` may make
one more request for V4.1.2, which asks that only the pages people open in a browser redirect plain HTTP to HTTPS and
an API not. `sv probe <address> --api <path>` adds one question, and only then: a HEAD over plain HTTP, on port 80 of
the same host and held to the same checked address, to the path the owner typed, shaped as a program asks (it
accepts JSON and carries this probe's own name rather than a browser's). Answered with a redirect to HTTPS on this
host, it is a finding (`probe.api-redirected-to-https`); anything else credits nothing, since one address is not every
endpoint, and says what it got. A run with `--api` may make five requests, and the fetcher's cap follows the target
(`MOST_REQUESTS_WITH_API`); without it, still four, and V4.1.2 is not assessed, saying how to ask. The path comes from
the command line, like the address, and is held to being a path on that host: no host of its own, no `..`, no
characters curl or a shell would read. Everything else in this record stands. DESIGN, "V4.1.2: an API asked over plain
HTTP the way a program asks".


## Later, 8 October 2026: a host name with letters outside ASCII is refused

From the review of 8 October 2026 (item 6). `sv probe https://bücher.example` was taken as typed. A name like that is
looked up, and connected to, by its `xn--` form, so the one lookup `sv` makes and the address curl is held to by
`--resolve` were for a name curl never asks for, and the hold would not have held. Such a name is now refused before
anything is asked, with a sentence saying to give its `xn--` form, which a browser's address bar gives when the
address is copied from it. `sv` does not convert the name itself: that would take an IDNA library, a dependency, for
a case an owner meets rarely and can answer in one copy. Values the site sends that a finding quotes (a header, a
redirect's address) are also cut to 200 characters on one line now (`finding::quoted`); they are still read whole.
Everything else in this record stands. Design entry
`docs/design/0308-three-low-findings-header-values-a-host-outside-ascii-and.md`.

## Later, 8 October 2026: the DNS transaction id is not the process id

The review of `sv` that day (BACKLOG, "From the review of 8 October 2026", item 6): the one DNS question this record
allows carried a transaction id formed from the process id, which `ps` shows anyone on the computer, so an answer
forged by a bystander with the id would have been taken for the resolver's. **The id is now sixteen bits drawn from
the operating system's randomness** (`live_tls::query_id`, through the standard library's hasher seed, which costs no
dependency). The question, its one resolver, and what is done with the answer are unchanged. Held by
`crates/sv-check/src/live_tls/id_tests.rs`.
