# ADR-036: `sv` finds its data beside itself, and an install does not live in a working folder

**Status:** proposed. Written with the claim of BACKLOG "A built `sv` cannot be moved" on 5 October 2026 by session
securevibe-e9, at the owner's asking to take it next, as `docs/adr/README.md` asks for a substantial decision.

**Governs:** `crates/sv-frameworks/src/lib.rs`. A pull request that changes it changes this record too, or says in
its description why it does not (`docs/adr/README.md`).

## Context

`sv` reads about twenty files of its own at run time: the OWASP frameworks, its rules, its questions, its prompts. It
finds them through the folder it was compiled in (`env!("CARGO_MANIFEST_DIR")` plus `../../data`), fixed when it is
built. `SV_DATA_DIR` moves only the OWASP part; every other file is read from the build folder whatever it says. So a
copy of `sv` works until its build folder goes away, and then fails. In my-first-app (28 September and 4 October
2026) the owner's `PATH` and the app's `.mcp.json` both named `sv` inside a build folder that was later removed: the
program went with its folder, and the owner edited `~/.zshrc` and the AI tool's settings by hand twice.

## Decision

- **One place answers "where is the data"**, in `sv-frameworks`, which every crate that reads data depends on. Every
  file `sv` reads at run time is found through it. Its order:
  1. `SV_DATA_DIR`, now the whole `data` folder, every file in it, not only the OWASP part.
  2. Beside the program: a `data` folder next to `sv`, or `../share/securevibe/data` from it, the usual place for an
     installed program's files. The program's own path is followed through any link to it.
  3. The folder it was built from, as before, so a build in the repository and the Docker image keep working.
  A folder counts only when it holds the OWASP frameworks. When none does, `sv` says each place it looked.
- **An install that does not live in a working folder:** a script, run by the owner, that builds `sv` and puts it
  with its data in a folder of its own (`~/.local/share/securevibe`), and links `~/.local/bin/sv` to it. The owner's
  `PATH` and an AI tool's settings then name a path that does not move when a build folder is removed.

## Alternatives considered

- **Compiling every data file into the program.** One file to copy, and nothing to find. But the loaders read files
  by path, outside tools are handed some of them, and the owner edits rule data and expects the next run to use it
  without a rebuild. Finding the folder keeps all of that and fixes the fault. It can be added later.
- **`sv install`, a command that copies itself.** It would write outside the app folder from inside `sv`, which `sv`
  otherwise never does; a script the owner runs on purpose is plainer about what it does.

## Consequences

`SV_DATA_DIR` changes meaning: it named the folder holding `frameworks/`, which was already the whole `data` folder
in practice, and now every file is read from it. A data folder beside an installed `sv` is used before the build
folder, so a stale install is used rather than a newer checkout; `sv --version` names the commit it was built from.
