# ADR-036: `sv` finds its data beside itself, and an install does not live in a working folder

**Status:** accepted. Written first as `proposed` with the claim of BACKLOG "A built `sv` cannot be moved" on 5 October
2026 by session securevibe-e9, at the owner's asking to take it next (#754), and built the same day; "Where the build
differs from the plan", below.

**Governs:** `crates/sv-frameworks/src/data.rs`, `tools/install.sh`. A pull request that changes either changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv` reads about twenty files of its own at run time: the OWASP frameworks, its rules, its questions, its prompts. It
finds them through the folder it was compiled in (`env!("CARGO_MANIFEST_DIR")` plus `../../data`), fixed when it is
built. `SV_DATA_DIR` moves only the OWASP part; every other file is read from the build folder whatever it says. So a
copy of `sv` works until its build folder goes away, and then fails. In my-first-app (28 September and 4 October
2026) the owner's `PATH` and the app's `.mcp.json` both named `sv` inside a build folder that was later removed: the
program went with its folder, and the owner edited `~/.zshrc` and the AI tool's settings by hand twice.

## Decision

- **One place answers "where is the data"**, in `sv-frameworks`, which every crate that reads data depends on. Every
  file `sv` reads at run time is found through it. Its order:
  1. `SV_DATA_DIR`, now the whole `data` folder, every file in it, not only the OWASP part.
  2. Beside the program: a `data` folder next to `sv`, or `../share/securevibe/data` from it, the usual place for an
     installed program's files. The program's own path is followed through any link to it.
  3. The folder it was built from, as before, so a build in the repository and the Docker image keep working.
  A folder counts only when it holds the OWASP frameworks. When none does, `sv` says each place it looked.
- **An install that does not live in a working folder:** a script, run by the owner, that builds `sv` and puts it
  with its data in a folder of its own (`~/.local/share/securevibe`), and links `~/.local/bin/sv` to it. The owner's
  `PATH` and an AI tool's settings then name a path that does not move when a build folder is removed.

## Alternatives considered

- **Compiling every data file into the program.** One file to copy, and nothing to find. But the loaders read files
  by path, outside tools are handed some of them, and the owner edits rule data and expects the next run to use it
  without a rebuild. Finding the folder keeps all of that and fixes the fault. It can be added later.
- **`sv install`, a command that copies itself.** It would write outside the app folder from inside `sv`, which `sv`
  otherwise never does; a script the owner runs on purpose is plainer about what it does.

## Consequences

`SV_DATA_DIR` changes meaning: it named the folder holding `frameworks/`, which was already the whole `data` folder
in practice, and now every file is read from it. A data folder beside an installed `sv` is used before the build
folder, so a stale install is used rather than a newer checkout; `sv --version` names the commit it was built from.

## Where the build differs from the plan

- **Every command checks for the data before it starts.** Found while testing: `sv check` reads its rules through the
  same place, but a wrong `SV_DATA_DIR` let it carry on with the build folder's files, which is the passing-over this
  record rules out. Each command now stops at once and says why when there is no data folder.
- **`sv --version` names the data folder** on a second line, so a copy whose data is older than its code, or one
  reading some other copy's data, says so.
- **The install script never replaces a file at `bin/sv` it did not put there.** A copy of `sv` the owner put in
  `~/.local/bin` by hand is left as it is, and the script stops and says so.

Held by `crates/sv-frameworks/src/data.rs`'s own tests (the order of the places, a link followed to the program, a
folder without the frameworks passed over, a wrong `SV_DATA_DIR` named) and `crates/sv-cli/tests/moved.rs`: a copy
of the real `sv`, linked from another folder, with its data beside it, reads that data and checks an example app;
`SV_DATA_DIR` still comes first and a wrong one stops a check; the install script installs, replaces its data whole,
and leaves a file of the owner's alone; and no source file outside a test module names `CARGO_MANIFEST_DIR` but
`data.rs`.


## Later, 8 October 2026: the install script builds with `--locked`

`tools/install.sh` now runs `cargo build --release --locked` (backlog item 25(h); `docs/GAP-ANALYSIS.md`, 5.3).
Without it, a build was free to pick newer versions of the pieces `sv` is made from than the ones in `Cargo.lock`,
which are the versions every test of `sv` ran with, so the owner's copy could differ from the tested one in a way
nobody chose. With it, a `Cargo.lock` that is out of date stops the build with an error rather than being quietly
updated. How the program finds its data, which is what this record decides, is unchanged.
`the_install_script_builds_with_the_versions_in_cargo_lock` in `crates/sv-cli/tests/moved.rs` runs the script with a
stand-in `cargo` and fails if `--locked` is not among what it was asked.


## Later, 9 October 2026: a Homebrew formula keeps the same rule

The owner decided that day to offer `sv` through Homebrew for Mac and Linux (backlog 0120), in a repository of its
own, `abbyshade111/homebrew-stackvet`. Its `Formula/sv.rb` builds with `cargo build --release --locked`, as
`tools/install.sh` does, installs the program and `data/` together in Homebrew's own folder for `sv` (`libexec`),
and links `bin/sv` to the program. This record's rule is what makes that work: `sv` follows the link to its real
place and finds `data/` beside it, so the formula needs no `SV_DATA_DIR` and no folder of its own. Nothing here
changed; the formula is a second installer that keeps the same layout. Its test, run by that repository's CI on
`macos-latest` and `ubuntu-latest`, asserts that `sv --version` names `libexec/data` and that `sv check` on a
one-file app reads the file and says what it could not assess. First green run: 9 October 2026, after a first run
that failed before any step because the setup action's branch had been renamed.
