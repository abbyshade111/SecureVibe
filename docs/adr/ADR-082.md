# ADR-082: What `sv` saw of the running app kept beside the report, with credentials removed

**Status:** proposed, 9 October 2026, with the backlog claim (0226, part 3, item A). The owner's decision, the same
day: "yes to A, C, and D". Each part is accepted in the pull request that builds it, which says where the build
differs from this plan. Written by session paper-facts.

**Governs:** `crates/sv-cli/src/report_files.rs`, the list of files a report folder holds, and
`crates/sv-check/src/secrets.rs`, whose redaction everything kept here passes through. The files that write the
records join this list when they are written. A pull request that changes what these say about the kept records
changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

The observability review of 9 October 2026 (backlog 0226) found that `sv` keeps its conclusions and almost nothing of
what it saw. Each probe's response (status, headers, and up to 4,000 characters of body, `ProbeResponse`), the app's
log that the logging credits are read from, what the stand-in services received (the test model's requests, the test
sign-in provider's, the mail), and each outside tool's raw output are held in memory and dropped when the run ends. A
person who asks why a requirement was credited from the running app, or why a probe found something, can read only
the sentence `sv` wrote about it.

## Decision

`sv` keeps a record of what it saw beside the report, in the report folder, every time it writes a report with the
running app, so a person can follow a credit or a finding back to the exchange it rests on.

1. **What is kept.** For each probe request: an id, the method, the path, the status, the response headers, and the
   body excerpt `sv` already keeps. From the stand-in services: the test model's record of what it was sent, the paths
   it was asked for, the sign-in provider's requests, and each mail's recipient, subject, and time (not its body). From
   the app's log: the lines a logging check matched, and a short tail. Each finding and credit read from the running
   app names the ids of the records it rests on.
2. **Credentials removed first.** Everything kept passes through `secrets::redact_text` before it is written, and
   `sv`'s own test accounts' passwords and secrets are replaced as the seed failure already does. A test plants a key
   built from pieces in each kind of record and fails if it reaches the file.
3. **Bounded.** A fixed most per kind of record and in total, with the report saying what was left out.
4. **Under the seal and in the bundle.** The record is one of the report folder's files, sealed with the report
   (ADR-034), and `sv bundle` refuses it as it refuses any file holding a credential.
5. **Said plainly.** The report says the record is there, what it holds, and that it is the app's own text, which can
   hold personal data the app was given during the run (only `sv`'s own test accounts are signed in).
6. **Outside tools' raw output** is kept only when asked for (`--keep-tool-output`), since it can be large and holds
   the app's code; the tool's version, arguments, and exit code are recorded always (review part 2, item 14).

## Alternatives considered

- **Keep nothing more** (today): every "why" answered by prose alone. Rejected by the owner.
- **Keep it outside the app's folder**, beside the history: safer from the AI coding tool's reading, but then it does
  not travel with the report it explains, and the seal could not cover it.
- **Keep it only when asked**: the record would be missing exactly when a surprising result was not expected.

## Consequences

A report folder holds one more file after a run with the app. It holds the app's text, so it needs the same care as
the app's logs: the report says so, and the redaction is tested by breaking it. The paper and the trial scorers can
read probe outcomes from it rather than from the report's words.
