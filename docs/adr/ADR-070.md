# ADR-070: Client-side technology that is no longer supported, found in the app's code (V3.7.1)

**Status:** accepted, 9 October 2026, in the pull request that builds it; proposed with the backlog claim (0085, part
17). Asked for by the owner ("please continue to work through and pick up new items as you merge"). Written by session
paper-facts.

**Governs:** `crates/sv-check/src/config.rs`, which runs the check this record adds, config.client-tech-unsupported,
from a file of its own beside the other checks that read the app's files. A pull request that changes what it says
about this changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

ASVS V3.7.1 (level 2) reads: "Verify that the application only uses client-side technologies which are still
supported and considered secure. Examples of technologies which do not meet this requirement include NSAPI plugins,
Flash, Shockwave, ActiveX, Silverlight, NACL, or client-side Java applets." Nothing in StackVet speaks to it. The
plug-ins it names are rare in an app written today and leave unmistakable traces. What a new app is more likely to
carry is a front-end library its makers no longer support, which the requirement's first sentence reaches as well:
AngularJS, Vue 2, an old Bootstrap or jQuery, picked up from an old tutorial or by an AI coding tool's habit.

## Decision

- **Plug-ins:** a `.swf` or `.xap` file among the app's own, and in its pages and templates `<applet`, an `<object>`
  with a `clsid:` class, the Flash or Silverlight content types, an `<embed>` of a `.swf`, and `language="vbscript"`.
  `ActiveXObject` is left out: old libraries name it as a fallback.
- **Libraries past their end of life,** each with the date its makers gave, read from endoflife.date on 9 October
  2026: AngularJS (the package `angular`, every version; 31 December 2021), Vue 2 (31 December 2023), Bootstrap 3
  (24 July 2019) and 4 (1 January 2023), and jQuery 1 and 2 (no longer supported). Found in the bill of materials
  `sv` already builds from the app's manifests and lockfiles, and in an address that loads one from a CDN with its
  version in it (`code.jquery.com/jquery-1.12.4.min.js`, `cdn.jsdelivr.net/npm/vue@2.7.16`).
- **Only ever a finding (medium):** no list of what a page loads is complete, so finding none shows nothing, and the
  check is listed as one that only finds.
- **The dates are data, written once with their source,** so the finding can say when support ended, and a later
  pull request can add a library or a date without changing the rule.

## Alternatives considered

- **Plug-ins alone,** as `docs/PARTIAL-CHECKS.md` proposed. Rejected as too narrow: it rated its own value low.
- **Every library a vulnerability database names.** That is the advisories check's job, and a vulnerable version is
  not an unsupported one; this is about support having ended.
- **A live lookup of end-of-life dates.** Rejected: `sv` runs with no network for what it reads, and the answer would
  change between runs.

## Where the build differs from the proposal

- **What a `package.json` asks for is read too.** The bill of materials lists only what a lockfile names, so an app
  with a `package.json` and no lockfile showed nothing; the version asked for, by its first number, is read as well,
  and the finding says it is what the manifest asks for.
- **The check is in `crates/sv-check/src/client_tech.rs`,** run from the configuration checks beside the rich-text
  check, whose way of finding the manifest line it shares.
- **A CDN address counts only when the name follows `/`, `@` or `-` and is followed by its version,** so look-alikes
  (`myvue@2`) and Angular's own packages (`@angular/core@18`) are left alone.
