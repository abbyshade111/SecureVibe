# ADR-048: The weak password-derivation rule cites storing passwords as well as making keys

**Status:** accepted, 7 October 2026, in the pull request that builds it; proposed the same day with the backlog
claim. Decided by the owner on 7 October 2026 ("cite both V11.4.2 and V11.4.4"), after both independent
reviews of the prompt library (`docs/prompts/reviews/`) found that `ast.weak-password-key-derivation` cites only
V11.4.4. Written with the claim, as `docs/adr/README.md` asks for a decision that changes evidence.

**Governs:** `data/ast-rules.json`, for the requirements this rule cites. A pull request that changes them changes this
record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`ast.weak-password-key-derivation` reports a PBKDF2 call with fewer rounds than OWASP recommends. It cites V11.4.4:
"approved key derivation functions with key stretching parameters when deriving secret keys from passwords". But the
call it finds is as often a password being stored as a key being made: in the loop trials 23 Haiku builds stored their
users' passwords with too few PBKDF2 rounds. Storing passwords is V11.4.2: "passwords are stored using an approved,
computationally intensive, key derivation function ... with parameter settings configured based on current
guidance". The prompt `password-hashing`, about storing passwords, could not cite V11.4.2, because `tools/coverage.py`
holds a prompt to the requirements its rules cite.

## Decision

- The rule cites **V11.4.2 and V11.4.4**: the same weakness, whether the derived value is a stored password hash or a
  key. Its title and description say both.
- **Nothing more is credited.** The rule is findings-only: it never credits a requirement. What changes is which
  requirements a finding is reported under, so a weak PBKDF2 used to store passwords now shows under V11.4.2, where a
  reader looks for it.
- `password-hashing` cites V11.4.1 and V11.4.2, the requirements it is about.
- `docs/COVERAGE.md` now lists V11.4.2 among the requirements plain `sv check` can settle (25 became 26), by that
  page's own definition: a check that can mark a requirement *needs attention* can settle it, as this rule already
  could for V11.4.4. A clean result is still not a pass, and the page says beside the requirement that `sv` reports
  it only ever as a finding.

## Alternatives considered

- **V11.4.2 only.** The rule cannot tell from the call alone whether the result is stored as a password hash or used
  as a key, so dropping V11.4.4 would hide the key case.
- **Telling the two cases apart.** Possible in part (where the result is written next to a user record), and a larger
  change than the owner chose.
