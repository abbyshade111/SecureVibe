# ADR-050: The app's own tests are a tier of their own, below an automated check

**Status:** accepted, 7 October 2026, in the pull request that builds it. Proposed the same day with the backlog
claim. Decided by the owner on 7 October 2026 ("go ahead with the first four"), the first of the four places to start
in `docs/GAP-ANALYSIS.md` (1.1). Where the build differs from the plan is under "As built".

**Governs:** `crates/sv-check/src/suite.rs` (which test names credit which requirements),
`crates/sv-report/src/lib.rs` (the statuses and their order), `crates/sv-report/src/threats.rs` (which statuses
settle a threat). A pull request that changes either changes this record
too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`sv` asks the AI coding tool to write tests that name the requirements they show (`sv init`'s specification, the
feature briefs), and runs the app's test command under `sv run`. When the command passes, every requirement id named
in a test file has been credited as *checked*, the same status as `sv`'s own checks, and the short version calls it
"an automated check looked and found nothing wrong". But the AI coding tool writes both the tests and the command, and
the credit has rested on the name alone: any file under `tests/`, a Markdown note among them, a comment.

ADR-022 ranks the AI coding tool's answer lowest (*stated*) because it is "the author grading its own work". Through a
test the same author's work reached the highest tier. A passing test is more than an answer, since it ran and the app
did what the test asked; but what the test asked is the author's choice, and nothing here reads whether it asks what
the requirement asks.

## Decision

- A new status, **tested by the app's own tests**, between *checked* and *documented by the owner*. A requirement
  whose only evidence is the app's own tests has it. It never becomes *checked*, and the short version says whose
  tests they are ("your app's own tests, written by your AI coding tool, passed") apart from what `sv`'s checks did.
- **A threat is never settled by it alone**, as it is not by any other tier below *checked*.
- **Only code is read.** A requirement id counts only in a file of a language `sv` reads; a Markdown or text file under
  `tests/` credits nothing.
- **Requirements a test cannot show** (documentation, deployment, process: the list the report already keeps of ids
  left off "tests to write") are never credited by the app's tests; a test naming one is supporting evidence only.

## Consequences

- Reports with app tests show fewer *checked* requirements and a new row; nothing previously *not verified* changes.
- Not done here, and left on the backlog: reading the test report even when the suite passes, so only cases the
  report names as passed count; and showing that a test fails when the protection it names is removed.

## As built, 7 October 2026

- **The status** is `Status::AppTested`, written `app-tested` in `report.json`, labeled "tested by the app's own
  tests", and ranked between *checked* and *documented*. It has its own count (`counts.app_tested`), its own row
  in every table, its own line in the short version, the terminal, and the AI coding tool's summary, and its own
  column in the chapter table when any chapter has one. The opening sentence counts it apart from both "looked at by
  something" and "somebody's word".
- **How it is kept apart.** The credit still arrives as a `Verified` with the check id `app-tests`
  (`sv_check::suite::CHECK_ID`), and the report moves every one of those into `tested_by` rather than `checked_by`.
  No caller can make a test *checked* by passing it in with the other checks. A requirement with a check of `sv`'s
  and a passing test is *checked*, and shows the test beside it.
- **Requirements a test cannot show** are the report's existing `not_for_tests` list and the design-review
  requirements (`manual_only`). A test naming one goes to `supported_by`.
- **Threats** show these requirements in a group of their own, "your app's own tests ran without failing, which is
  not evidence about this threat", and count them toward nothing. "Before going live" still lists them, since only
  *checked* and *checked by hand* take an item off that list.
- **Prompts** are not offered for them, as for *checked* and *documented*: a passing test is evidence of some kind.
- **Wording.** No label says the tests "passed". The report's own guard forbids that word outside a denial, since
  it would be read as the requirement being met. They "ran without failing".
- **Not done:** the end-to-end count test (`crates/sv-cli/tests/counts_add_up.rs`) cannot give a requirement this
  status, because that needs the app started under `sv run` with a container backend. It accepts zero for this
  one status and says so. Every format is held to the sum with it present in `sv-report`'s
  `the_app_s_own_tests_are_a_tier_below_a_check_of_sv_s`.

## Later, 7 October 2026: a status beside *checked* (ADR-053)

*Checked in part* joins the list of statuses, between *checked* and the app's own tests: a requirement whose every
check tried only part of what it asks, first V8.2.2 when another user was refused reading a record and changing or
deleting it was not tried. Like this record's tier, it is counted apart in every table and never as *checked*.
Everything else in this record stands.
