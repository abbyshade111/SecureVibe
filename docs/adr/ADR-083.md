# ADR-083: History that can show a trend: each requirement's status in each run, and why two runs differ

**Status:** accepted, 10 October 2026: every decision is built (see the four "Later, 10 October 2026" entries below,
which say where each build differs from the plan). Proposed 9 October 2026, with the
backlog claim (0226, part 3, item C). The owner's decision, the same
day: "yes to A, C, and D". It extends ADR-057, whose history kept counts and findings only. Each part is accepted in
the pull request that builds it. Written by session paper-facts.

**Governs:** `crates/sv-cli/src/history.rs`, which writes and reads the history, and
`crates/sv-report/src/dashboard.rs`, which defines a run's record and reads it. A pull request that changes what these
say about what history keeps changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

History (ADR-057), kept only when the owner turns it on and outside the app's folder, records per run the counts and
each finding's fingerprint, severity, rule, and title. It can say "checked: 41 then, 40 now" but not which requirement
moved or why. Its "can these two runs be compared" key hashes only `stackvet.toml`, so an edit to the security notes,
the decisions file, a check made by hand, or a review seal moves requirements while the dashboard calls the runs
comparable. A run that failed leaves no record, and the dashboard keeps showing the last report as current. A record
`sv` cannot read is passed over without a word (review part 1, item 8).

## Decision

When history is on, each run's record also keeps:

1. **Each requirement's status**: its id and status word, nothing of the app's code or text.
2. **The run's outcome and exit code**, and a record for a run that failed or was stopped, saying so.
3. **More in the comparison key**: hashes of the security notes, the decisions file, the review seal, and `sv`'s data
   folder beside `stackvet.toml`'s, each named as the reason when two runs differ ("your security notes changed").
4. **Records still readable when `sv` adds to them**, and the dashboard counting any it could not read.

And `sv compare <older report folder> [<newer>]`, which reads two sealed reports, lists each requirement whose status
changed with the credit or finding gained or lost on each side, and writes nothing. It works whether or not history is
on.

## Alternatives considered

- **`sv compare` alone**, keeping history as it is: answers "what changed between these two" but never draws a trend
  across many runs.
- **Keep whole reports in history**: everything, but the app's text outside its folder, which ADR-057 avoided.

## Consequences

Each history record grows by a few kilobytes (one line per requirement). History stays private, outside the app's
folder, and never evidence. The dashboard can draw each requirement over time, and the paper can take counts from
`sv`'s records rather than by hand.

## Later, 10 October 2026: decision 1 built

Built by session securevibe-e2 (backlog 0230). Each run history keeps now holds `requirements`, a list of each
applicable requirement's id and status word, and nothing else about it; the record's format is 2. The dashboard's
"what changed" names each requirement whose status moved between two runs ("V1.1.1: not verified then, checked now"),
including one that applies in only one of them ("did not apply"), the first twelve by name and the rest counted.
A record from before format 2 still reads, with no statuses, and when it is set against a newer one whose counts differ,
the page says which requirements moved is not known, rather than guessing. As planned, with one addition: the cap of
twelve named, so a run that moves many requirements at once does not bury the rest of the page.

## Later, 10 October 2026: decision 3 built

Built by session securevibe-e2 (backlog 0230). Each report's `run_record` now carries `inputs`: the SHA-256 of the
security notes and of the design decisions as the run read them (`null` for a file that was not there), and of every
file in `sv`'s data folder, by name and content. A run kept in history copies them; the record's format is 3. The
dashboard no longer compares two runs whose notes or decisions differ, and says which changed ("your security notes
changed between them, and with them what they credit"); nor two by the same `sv` given different data. A record from
before format 3 is still compared as it was, and when something moved between it and the next, the page says whether
the notes, the decisions, or the data changed is not known.

Where the build differs from the plan: there is no review seal file to hash. A review's seals are lines inside
`stackvet.toml`, the security notes, and the design decisions, so the three hashes already cover them. What checks a
seal is the person's own keys, in their settings folder, and those are left out on purpose: no record of a secret key,
not even its hash, is kept outside the place it lives. A change of trusted keys therefore does not by itself mark two
runs as not comparable; the moved requirements still show.

## Later, 10 October 2026: decision 2 built

Built by session securevibe-e2 (backlog 0230). Each kept run now says how it ended (`outcome`: finished, failed, or
stopped) and what `sv` ended with (`exit_code`); the record's format is 4, and one from before reads as finished, since
only finished runs were kept. When history is on, `sv report` keeps a record of a run that failed (an error `sv` could
not get past, after the app's folder was named; it ends with 3) and of one stopped with Ctrl-C (130). That record holds
when it started, which `sv`, and how it ended, and nothing else: not the error, which can quote the app's own files,
and not the app's name, which a failed run may never have read (the name kept stays the last one known). The dashboard
shows such a run for what it was, never compares it, sets the next run against the last one that finished, and, when
the newest run did not finish, says so above the report shown, in each app's view and in the view of every app: "The
latest run, on ..., did not finish. The report shown is from the last run that did, on ...".

Where the build differs from the plan: Ctrl-C ends `sv` from two places deep in a run (starting the app, and running
the outside tools), each through `exit::exit_with`; rather than thread the history through both, `sv report` sets one
step with `exit::on_interrupt` that `exit_with` takes before it ends with 130. A command line that names no app folder
is not a run and leaves no record.

## Later, 10 October 2026: decision 4 and `sv compare` built

Built by session securevibe-e2 (backlog 0230). Decision 4 was already true of history: every field of a kept run has a
default, a field a later `sv` adds is passed over, and a file that does not read as a run is counted and said on the
page (ADR-057). A test now holds the second of these, and that an outcome this `sv` does not know is not guessed at:
the record is counted as unread instead.

`sv compare OLDER [NEWER]` reads two reports' `report.json` (a report folder, or an app folder with one in its
`stackvet-report`; NEWER is this folder's report when not given) and prints each requirement whose status changed,
with what credited it or was found against it on one side and not the other, the findings that came or went, and the
counts. It writes nothing and works whether history is on or not. It compares them with the same rule the dashboard
uses (`Run::not_comparable_with`), and when the two runs were not alike it says so first, rather than refusing: the
person asked for these two.

Where the build differs from the plan, which said it "reads two sealed reports": a report whose seal cannot be checked
here (written on another computer, before reports were sealed, or changed since) is still compared, and the output
says first that `sv` cannot show it wrote that report, with why. Refusing would leave no way to compare a report made
in CI or by an older `sv`, and `sv compare` credits nothing, so what it reads is never evidence either way.
