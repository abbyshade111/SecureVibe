# ADR-051: The tests must pass before a pull request merges into main, and every commit on main is tested

**Status:** accepted, 7 October 2026, in the pull request that changes the workflow; proposed the same day with the
backlog claim. Decided by the owner on 7 October 2026: "I definitely want the tests required before merging and
thought I had turned that on" (`docs/GAP-ANALYSIS.md`, 7.1). The required check itself waits on the owner (below).

**Governs:** `.github/workflows/rust.yml`. A pull request that changes it changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

On 7 October 2026 the only check required before merging into `main` was "Decision records" (the ruleset "Main - ADR
Check"). The `test` job of `rust.yml` (formatting, lints, and the whole test suite) was not required, so a pull
request could merge with it failing or still running: #871 and #873 did that day. And on `main`, 19 of the last 50
runs of `rust.yml` were canceled before they finished: the concurrency group was one per branch, and when a run is
already waiting, GitHub cancels the waiting one in favor of the newest, whatever `cancel-in-progress` says. So about
four in ten commits on `main` were never tested there.

## Decision

- **`test` is a required check on `main`**, held to GitHub Actions' own run (app 15368) so nothing else can satisfy it.
  This is a repository setting. A Claude Code session cannot change repository settings through its GitHub
  connection, so the owner makes it; until then this record says what was decided, not what is in force.
- **Every commit on `main` is tested.** `rust.yml`'s concurrency group on `main` is the commit, not the branch, so no
  run there waits behind another and none is replaced. Branches keep one group each, and a newer push still cancels
  an older run, since only the newest commit of a pull request can be merged.
- **The image is still published once at a time and newest last.** The publishing job has its own group on `main`,
  never canceled while it runs; a waiting one is replaced by a newer one, which only skips publishing an image that
  is already out of date.
- "Up to date with `main` before merging" stays off: with several sessions merging each hour it would re-run every
  pull request after every merge. The tests on `main` itself catch two changes that pass apart and fail together.

## As built (7 October 2026)

- `rust.yml`'s group is `rust-<commit>` on `main` and `rust-<branch>` elsewhere. The publishing job has the group
  `rust-publish-main`, and moves the `latest` tag only when its commit is still the newest on `main`, since runs on
  `main` can now finish out of order; the commit's own tag is always pushed.
- The session that built this tried to add `test` to the ruleset and was refused: its GitHub connection may not write
  repository settings. The owner adds it on GitHub: Settings, then Rules, then Rulesets, then "Main - ADR Check";
  under "Require status checks to pass", add `test` from GitHub Actions, and save.

## Later, 7 October 2026: a passing run means the fence tests ran

From the gap analysis (`docs/GAP-ANALYSIS.md`, 7.2; BACKLOG, item 30). The tests this record requires include the fence
tests, and each of them, finding no container backend, takes an honest-absence path and passes: right on a computer
without Docker, and wrong on a CI runner whose Docker broke, where all of them would pass while testing nothing.
`rust.yml`'s test job now sets `SV_REQUIRE_BACKEND=1`, and with it one test
(`a_container_backend_is_here_where_ci_says_it_must_be` in `crates/sv-run/tests/fence.rs`) fails when no backend
answers. So the required check passing now says the fence was exercised. On a person's own computer, without the
variable, nothing changes.

## Later, 8 October 2026: the suite runs on `main` every night, and the example apps' verdicts are a snapshot

At the owner's asking ("can you help me set up the nightly routine you proposed"), from the end-of-day write-up of
8 October 2026. Two things:

- **A nightly run.** `rust.yml` gains a `schedule` trigger, 03:17 UTC every day, which runs the same `test` and
  `image` jobs on `main` whether or not anything was pushed. The toolchain step installs the newest stable, the
  runner image moves, and the image job reaches Docker Hub, so a quiet day can break the build with no commit to
  blame; GitHub's failure mail is the one-line note the write-up asked for. The `publish` job keeps its `push`
  condition, so a scheduled run publishes nothing. A Claude routine was not made for this: the pieces the write-up
  named (the full suite with a container backend, the credit census, the example apps re-scored) all run here
  already, free, and a routine would spend tokens to say what the mail says.
- **The example apps' verdicts, held.** `crates/sv-cli/tests/verdicts.rs` runs `sv report` on every app under
  `examples/` and holds each requirement's status to `tests/verdicts/<app>.json`. The write-up proposed comparing
  each night with the night before; a snapshot in the repository is stronger, since it fails at pull-request time
  and makes the change say why, by updating the snapshot in the same pull request (`SV_UPDATE_VERDICTS=1`). Only
  the static report is held: the statuses a reading of the code can reach.

**Governs:** unchanged.


## Later, 9 October 2026: a Windows workflow beside this one, not required

The owner asked that day for Windows as well as Mac and Linux (backlog 0120). `sv` had never been built on Windows,
so `.github/workflows/windows.yml` builds it on `windows-latest`, runs it on an example app, and runs the whole test
suite there. It is a separate workflow and not a required check: it is how what breaks on Windows is found out, and a
red result there must not stop pull requests that have nothing to do with Windows. It runs on every change to `main`,
weekly, by hand, and on a pull request that changes it. Each failing test becomes an annotation, with one more
giving the counts, so the results can be read through GitHub's API. What this record decides about `rust.yml` (the
tests required before merging, every commit on `main` tested) is unchanged. If Windows becomes supported, the job
moves into `rust.yml` and becomes required, with another entry here.


## Later, 9 October 2026: CI signs in to Docker Hub

On 9 October 2026 `main` went red at three merges in a row, and so did every pull request, for a reason that had
nothing to do with the code. Docker Hub refused images with "429 Too Many Requests": signed out, every pull counts
against a limit shared by everybody on the runner's address. The `image` and `publish` jobs could not fetch the
`rust` and `debian` images they build from. In the `test` job, `host_cookie` could not fetch `busybox` for the
fence's gateway check, so the app was never started.

Offered a mirror (`mirror.gcr.io`) or a sign-in, the owner chose the sign-in and gave the repository two secrets,
`DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`. Each of `test`, `image`, and `publish` now signs in to Docker Hub before
its first pull and signs out at its end, even when a step fails. The secrets are handed to the sign-in step alone,
through its environment, never on a command line. Where they are not given, as in a pull request from a fork, the
step says so as a warning and the pulls go unsigned, as before. The same when Docker Hub refuses the sign-in itself, which it did on its first try ("500 Internal Server Error"): three tries, then a warning, and the run goes on unsigned rather than failing for a fault of Docker Hub's.

What it costs: while the `test` job runs, the token sits in the runner's Docker settings, where the tests could read
it. Those tests are this repository's own; a fork's pull request is never given the secrets. The apps the tests start
run inside containers, which never see the runner's files. The token should allow reading public images and nothing
else, so a leak would cost a pull limit, not the account. `sv` itself is unchanged: it never signs in anywhere, and
what it pulls on a person's computer is theirs to decide.

## Later, 9 October 2026: Docker Hub's images through Google's mirror

The sign-in above did not keep `main` green. On its next runs Docker Hub refused the sign-in itself three times
running, so the pulls went unsigned and were refused in turn: the `image` job failed a minute into its build, and the
`test` job's `a_host_prefixed_cookie_signs_the_browser_in_and_a_weakened_start_is_warned_about` could not start its
containers. Run in a session whose Docker fetched through the mirror below, while Docker Hub was refusing that session
outright, the same test started the app and passed. Offered the mirror again that evening, the owner said "yes, please
go ahead".

The `test`, `image`, and `publish` jobs now set Docker's own `registry-mirrors` setting on the runner to
`mirror.gcr.io`, Google's copy of Docker Hub: an image named on Docker Hub is asked of the mirror first, and of Docker
Hub when the mirror cannot answer. Before the sign-in, `test` fetches the images the suite starts, and `image` and
`publish` fetch the Dockerfile's two base images by their fingerprints, so these come from the mirror; one that fails to
fetch warns and is left to the suite or the build, as before. Both base images' fingerprints were checked against the
mirror: each answered with the same manifest, byte for byte, and an image is only used if it matches its fingerprint.
The Dockerfile and the code keep Docker Hub's names, so Dependabot's weekly base-image updates, a build by hand, and
what `sv` pulls on a person's computer are unchanged. The sign-in stays, for what falls through to Docker Hub.

## Later, 10 October 2026: Windows every night, and a routine that reads the night into the backlog

The owner asked the same night that the Windows suite had first passed whole (2,753 passed, none failed): "a nightly
routine that runs the windows check and adds any issues to the backlog. That way PRs don't get bogged down but
still checking regularly." So:

- **`windows.yml` runs every night**, at 04:41 UTC, after the nightly Rust run at 03:17, instead of once a week. It
  still runs on every push to `main` and is still not a check on pull requests, so nothing waits for it. The
  repository is public, so its Windows minutes are not billed.
- **A routine reads the night's runs each morning** (07:06 New York time, a Claude Code routine in a fresh session
  each time, owned by the owner's account). It reads the runs on `main` from the last day: Rust and Windows every
  day, and Fuzz, Audit, and CodeQL on the days they run. For each failure, it adds a backlog item naming the check,
  the test, what it said, and the run, or a dated "seen again" line on an item that already names it. All of it
  goes in one pull request with auto-merge on. It fixes nothing itself, and on a night with nothing failing it opens
  no pull request. A red `main` it finds is still the merging session's to fix within the hour, as above; the item is
  the trace that it was seen.

Whether to make the Windows run a required check on pull requests stays the owner's decision; this takes the
other road.
