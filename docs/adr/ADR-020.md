# ADR-020: `sv` is written in Rust

**Status:** accepted. Decided when `sv` was begun (its first Rust code is dated 22 September 2026) and written
down here on 30 September 2026, from the owner's reason given that day, because the ADR analysis found that no
record named it (BACKLOG, "Records that disagree with what was built", item 8).

**Governs:** `Cargo.toml`, `crates/*/Cargo.toml`. A pull request that changes any of these changes this record too, or
says in its description why it does not (`docs/adr/README.md`).

**Replaces, for `sv`:** v1's ADR-001 (on the `v1` branch), "TypeScript everywhere with a single npm install".
That record describes v1 and stays as it was.

## Context

v1 was a TypeScript app, one `npm install` for the server and the web page. `sv` is a different program: a
command-line tool and MCP server that reads somebody else's app, starts it behind a network fence, and says what
it found. It is itself a piece of security software, and the project asks apps to be built Secure by Design, so
the language it is written in is held to the same idea.

## Decision

`sv` is written in Rust. **The owner's reason, 30 September 2026:** Rust is a memory-safe language, which suits
Secure by Design principles; many projects are moving code from other languages to Rust for the same reason.

What that buys, in the standard's own terms: ASVS V1.4 ("Memory, String, and Unmanaged Code") asks for memory-safe
strings and copies (V1.4.1) and for no dangling pointers or use after free (V1.4.3). In Rust's safe code a read or
write past the end of a buffer stops the program rather than overflowing, and the compiler refuses a program that
could use memory after freeing it. It is said here as a property of the language,
not as a check `sv` makes of itself, and no report cites it.

## Alternatives considered

- **TypeScript, as v1.** Memory-safe too, through a garbage collector, and it would have kept one language across
  both versions. This record does not say why it was not kept beyond the reason above; memory safety alone does
  not tell Rust and TypeScript apart, and the owner gave no further reason.
- **Go or Python.** Also memory-safe. Not recorded as considered.

## Consequences

- **Memory safety covers safe Rust only.** `sv` has five `unsafe` blocks, all in `sv-run`
  (`crates/sv-run/src/lib.rs` and `cleanup.rs`): installing the Ctrl-C handler, `_exit` from inside it, killing a
  process group, asking whether a process is alive, and reading the computer's name. Each calls the C library
  directly.
- **The code parsers are C.** Every tree-sitter grammar `sv` reads apps with is C code compiled into the `sv`
  binary. A fault in a grammar is a memory fault in `sv`, and the language does not protect against it.
- **Integer overflow is not caught in the release build.** V1.4.2 (integer overflow) is not bought by the
  language as `sv` is built: Rust checks arithmetic for overflow in debug builds, and the release profile in
  `Cargo.toml` sets no `overflow-checks`, so a release build wraps around silently.
- **The outside tools are not Rust.** bandit, gosec, brakeman, semgrep, and CodeQL, which `sv report --tools` and
  `sv bundle --tools` run, are separate programs in their own languages; this decision says nothing about them.
- Building `sv` needs a Rust toolchain (`cargo build --release -p sv-cli`, as the README says), or the container
  image, which carries a built `sv`.

## Later, 5 October 2026 (the second weekly review)

- **Five `unsafe` blocks in `sv`, seven in the workspace.** The five above are those in the program. Since 3 October a
  test, `crates/sv-check/tests/stand_in.rs`, has two more, each `std::env::set_var`.
- **Not all of `sv` is Rust, and was not when this was written.** Three JavaScript helpers in `crates/sv-run/assets/`
  (the browser driver, and the stand-in sign-in provider and AI model) are compiled into the binary as text and run
  under Node inside the fenced containers (ADR-019), never in `sv`'s own process.

## Later, 6 October 2026: four more `unsafe` blocks, to hide a passphrase

ADR-043 lets the owner put a passphrase on the key `sv review` signs with, and `sv review` stops the terminal showing it
as it is typed. That takes the C library's terminal settings (`tcgetattr`, `tcsetattr`) through `libc`, already a
dependency of `sv-run` and now of `sv-cli` too, in four `unsafe` blocks in `crates/sv-cli/src/review.rs`: reading the
settings, turning the echo off, putting them back, and the zeroed settings the first is read into. So `sv` has nine
`unsafe` blocks, not five, and the workspace fourteen: the tests' `std::env::set_var` calls are five by now
(`credit_log.rs` has two, `probe_curl.rs` one, `stand_in.rs` two). The same change adds `ssh-key` and `ssh-encoding`
to `sv-check` (ADR-043 names each, and the crates they bring), all Rust.
