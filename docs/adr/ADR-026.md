# ADR-026: The owner's word counts only when `sv review` recorded it

**Status:** accepted. Decided by the owner on 4 October 2026, after the deep review of `sv` at `eff3f17` found that an
AI coding tool could clear its own findings (R1, high). Built the same day: #578 (the reports say what securevibe.toml
says, not that "a person" decided), #588 (`sv review`, for findings set aside and answers confirmed), and #598 (the
owner's own answers). Changes part of ADR-022 and ADR-023, which each say so.

## Context

ADR-022 credits an answer at the tier of whoever gave it, and ADR-023 lets a person set a finding aside. Both rested on
a name in a file: `by = "owner"` in `securevibe.toml`, or `Written by: owner` in `security-notes.md`. ADR-022 said so
plainly: "Nothing in a file can stop a tool that edits it from writing `Written by: owner`." The deep review reproduced
it: a tool that wrote `by = "owner"` under `[[finding-review]]` had its finding shown as "SET ASIDE BY A PERSON". That
mattered more than any other gap, because the tool rewrites code until a warning stops, and one line in a file it is
already editing is the easiest way to stop one.

The review offered two fixes. The first was to say only what is known ("securevibe.toml says the owner set it aside").
The second was an interactive command that refuses input from anything but a terminal and keeps its record outside the
app's folder. The owner chose the second, with one change and one answer:

- **The record stays in `securevibe.toml`**, sealed, rather than outside the app's folder, so decisions travel with the
  code, can be reviewed in a pull request, and count on CI.
- **A sealed entry counts on a computer with no key to check it**, such as CI, saying that its seal could not be
  checked there.

The same afternoon the owner asked for the same rule for the owner's own answers, which had the same gap one step over.

## Decision

An entry counts as a person's word only when `sv review` recorded it.

- **`sv review [PATH]`** runs only when what it reads and what it writes are both a terminal, which an AI coding tool
  running a command does not have. It goes through every entry that does not count on this computer, shows what is
  being decided, and asks for the person's name or `owner`. It refuses the AI coding tool's name, a reason too short to
  count, and a confirmation that says nothing about what was looked at. It is not an MCP tool.
- **What it records is sealed.** The seal is HMAC-SHA-256 over every field of the entry, each prefixed by its length,
  under a 32-byte key from the system's randomness. The key is kept in `~/.config/securevibe/review-key` (or under
  `XDG_CONFIG_HOME`), outside the app's folder; the folder is readable by its owner only, and the key is never printed.
  The seal is written into `securevibe.toml` as `seal = "v1:<key id>:<mac>"`, and in `security-notes.md` as a line
  `Sealed by sv review: …` under `Written by: owner`. That line is never part of the answer, and the AI coding tool
  cannot record it through `securevibe_record_answer`.
- **What needs a seal:**
  - a finding set aside, under `[[finding-review]]` (ADR-023);
  - an answer confirmed, a `confirmed` entry under `[design]` or `[checked-by-hand]` (ADR-022);
  - the owner's own answers: a `[design]` answer or a `[checked-by-hand]` result written `by = "owner"`, and a section
    of `security-notes.md` marked `Written by: owner`. These are the tiers *attested*, *checked by hand*, and
    *documented by the owner*.
- **Where a seal is checked:**
  - On the computer that holds the key, a seal that does not match is a proposal. That covers an entry changed after it
    was recorded, and a seal that was made up. A seal made with another key is a proposal too: this computer cannot
    check it, and a made-up seal naming a key that is not here would look the same.
  - On a computer with no key at all, a sealed entry counts, and the report says it was recorded on another computer
    and its seal could not be checked.
  - A key file that cannot be used makes every entry a proposal.
- **Without a seal that holds**, a finding set aside or a confirmation is a proposal: the finding still counts, and
  the answer stays the AI coding tool's. An owner's own answer drops one tier, to *stated by the AI coding tool*. A
  `no` or a `problem` is still a finding, because reporting a missing control never overstates the app. Every report
  says why an entry does not count and that `sv review` is how to make it count.
- **The reports say what a seal shows and what it cannot**: how an entry was recorded, and that it has not changed
  since; not who was at the keyboard.

## Alternatives considered

- **Saying only what the file says.** Built first (#578) and kept: the reports name the file, not "a person". On its own
  it left the finding cleared, so the owner chose to go further.
- **A record outside the app's folder.** The review's suggestion. Set aside because decisions would no longer travel
  with the code, and every finding set aside would come back on CI and on every other computer.
- **Showing the git author of the entry.** Set aside: an AI coding tool commits under the owner's own git name, so the
  author would vouch for the owner just as `by` does, and look like more evidence than it is.
- **Public-key signatures**, so any computer could check a seal. Weighed by the session that built it, not by the owner:
  a computer would still need its own list of trusted keys to tell the owner's key from one the tool made, and new
  dependencies would be needed.

## Consequences

- **Entries recorded before this change count only once recorded again.** The owner runs `sv review` once and is
  walked through them.
- **A seal stops the easy way, not every way.** The tool runs as the person, so a tool set on faking it could read the
  key or fake a terminal. The seal makes that a deliberate act rather than one line in a file. The code, the README,
  and every report say so.
- **On CI, or any computer with no key, a sealed entry is taken on trust**, as the owner decided, and says so. A tool
  could write a made-up seal there, but the same entry is a proposal on the owner's own computer, where they see it.
- **Recording from a second computer** means copying the key file there; otherwise its seals are proposals on the
  first computer.
- **Any edit to a recorded entry**, a single word of the reason included, makes it a proposal again until recorded
  again.
- **One new dependency**, `toml_edit`, so that `sv review` changes only the entry and keeps the owner's comments and
  layout.

## How it is held

In `crates/sv-check/src/seal.rs`: `a_seal_holds_on_the_computer_that_made_it_and_nowhere_it_was_changed`,
`no_seal_or_a_malformed_one_is_a_proposal_wherever_it_is_read`,
`another_computers_seal_counts_only_where_there_is_no_key_to_check_it`,
`the_key_is_made_private_once_and_read_back_the_same`, and `every_field_of_an_owners_answer_is_sealed`. The judgments:
`an_entry_counts_only_as_sv_review_sealed_it` (`review.rs`), `a_confirmation_counts_only_as_sv_review_sealed_it`
(`confirm.rs`), `the_owners_answer_counts_as_theirs_only_when_sv_review_recorded_it` (`design.rs`),
`the_owners_check_counts_as_theirs_only_when_sv_review_recorded_it` (`hand.rs`), and
`an_owners_section_counts_as_theirs_only_when_sv_review_recorded_it` (`notes.rs`). The command, in
`crates/sv-cli/src/review.rs`: `a_finding_is_recorded_only_with_a_persons_name_and_a_reason_long_enough`,
`a_confirmation_records_what_was_shown_in_whichever_form_it_was_written`,
`the_owners_own_answers_are_recorded_only_as_the_owners`, `a_line_that_may_hold_a_key_is_never_shown`, and
`a_write_that_would_not_count_is_put_back`. End to end: `it_refuses_to_run_when_not_in_a_terminal` and
`what_a_person_records_counts_and_the_report_says_where_its_seal_was_checked` (`crates/sv-cli/tests/review_terminal.rs`,
which drives the real binary in a pseudo-terminal), and
`an_owners_answer_is_theirs_only_as_recorded_and_not_changed_since` (`crates/sv-cli/tests/owner_answers.rs`). Each
guard was undone in turn and a test went red: twenty-one for the first part, thirteen for the owner's answers.
