# ADR-026: The owner's word counts only when `sv review` recorded it

**Status:** accepted. Decided by the owner on 4 October 2026, after the deep review of `sv` at `eff3f17` found that an
AI coding tool could clear its own findings (R1, high). Built the same day: #578 (the reports say what securevibe.toml
says, not that "a person" decided), #588 (`sv review`, for findings set aside and answers confirmed), and #598 (the
owner's own answers). Changes part of ADR-022 and ADR-023, which each say so.

**Governs:** `crates/sv-check/src/seal.rs`, `crates/sv-check/src/review.rs`, `crates/sv-check/src/confirm.rs`,
`crates/sv-cli/src/review.rs`. A pull request that changes any of these changes this record too, or says in its
description why it does not (`docs/adr/README.md`).

## Context

ADR-022 credits an answer at the tier of whoever gave it, and ADR-023 lets a person set a finding aside. Both rested on
a name in a file: `by = "owner"` in `securevibe.toml`, or `Written by: owner` in `security-notes.md`. ADR-022 said so
plainly: "Nothing in a file can stop a tool that edits it from writing `Written by: owner`." The deep review reproduced
it: a tool that wrote `by = "owner"` under `[[finding-review]]` had its finding shown as "SET ASIDE BY A PERSON". That
mattered more than any other gap, because the tool rewrites code until a warning stops, and one line in a file it is
already editing is the easiest way to stop one.

The review offered two fixes. The first was to say only what is known ("securevibe.toml says the owner set it aside").
The second was an interactive command that refuses input from anything but a terminal and keeps its record outside the
app's folder. The owner chose the second, with one change and one answer:

- **The record stays in `securevibe.toml`**, sealed, rather than outside the app's folder, so decisions travel with the
  code, can be reviewed in a pull request, and count on CI.
- **A sealed entry counts on a computer with no key to check it**, such as CI, saying that its seal could not be
  checked there.

The same afternoon the owner asked for the same rule for the owner's own answers, which had the same gap one step over.

## Decision

An entry counts as a person's word only when `sv review` recorded it.

- **`sv review [PATH]`** runs only when what it reads and what it writes are both a terminal, which an AI coding tool
  running a command does not have. It goes through every entry that does not count on this computer, shows what is
  being decided, and asks for the person's name or `owner`. It refuses the AI coding tool's name, a reason too short to
  count, and a confirmation that says nothing about what was looked at. It is not an MCP tool.
- **What it records is sealed.** The seal is HMAC-SHA-256 over every field of the entry, each prefixed by its length,
  under a 32-byte key from the system's randomness. The key is kept in `~/.config/securevibe/review-key` (or under
  `XDG_CONFIG_HOME`), outside the app's folder; the folder is readable by its owner only, and the key is never printed.
  The seal is written into `securevibe.toml` as `seal = "v1:<key id>:<mac>"`, and in `security-notes.md` as a line
  `Sealed by sv review: …` under `Written by: owner`. That line is never part of the answer, and the AI coding tool
  cannot record it through `securevibe_record_answer`.
- **What needs a seal:**
  - a finding set aside, under `[[finding-review]]` (ADR-023);
  - an answer confirmed, a `confirmed` entry under `[design]` or `[checked-by-hand]` (ADR-022);
  - the owner's own answers: a `[design]` answer or a `[checked-by-hand]` result written `by = "owner"`, and a section
    of `security-notes.md` marked `Written by: owner`. These are the tiers *attested*, *checked by hand*, and
    *documented by the owner*.
- **Where a seal is checked:**
  - On the computer that holds the key, a seal that does not match is a proposal. That covers an entry changed after it
    was recorded, and a seal that was made up. A seal made with another key is a proposal too: this computer cannot
    check it, and a made-up seal naming a key that is not here would look the same.
  - On a computer with no key at all, a sealed entry counts, and the report says it was recorded on another computer
    and its seal could not be checked.
  - A key file that cannot be used makes every entry a proposal.
- **Without a seal that holds**, a finding set aside or a confirmation is a proposal: the finding still counts, and
  the answer stays the AI coding tool's. An owner's own answer drops one tier, to *stated by the AI coding tool*. A
  `no` or a `problem` is still a finding, because reporting a missing control never overstates the app. Every report
  says why an entry does not count and that `sv review` is how to make it count.
- **The reports say what a seal shows and what it cannot**: how an entry was recorded, and that it has not changed
  since; not who was at the keyboard.

## Alternatives considered

- **Saying only what the file says.** Built first (#578) and kept: the reports name the file, not "a person". On its own
  it left the finding cleared, so the owner chose to go further.
- **A record outside the app's folder.** The review's suggestion. Set aside because decisions would no longer travel
  with the code, and every finding set aside would come back on CI and on every other computer.
- **Showing the git author of the entry.** Set aside: an AI coding tool commits under the owner's own git name, so the
  author would vouch for the owner just as `by` does, and look like more evidence than it is.
- **Public-key signatures**, so any computer could check a seal. Weighed by the session that built it, not by the owner:
  a computer would still need its own list of trusted keys to tell the owner's key from one the tool made, and new
  dependencies would be needed.

## Consequences

- **Entries recorded before this change count only once recorded again.** The owner runs `sv review` once and is
  walked through them.
- **A seal stops the easy way, not every way.** The tool runs as the person, so a tool set on faking it could read the
  key or fake a terminal. The seal makes that a deliberate act rather than one line in a file. The code, the README,
  and every report say so.
- **On CI, or any computer with no key, a sealed entry is taken on trust**, as the owner decided, and says so. A tool
  could write a made-up seal there, but the same entry is a proposal on the owner's own computer, where they see it.
- **Recording from a second computer** means copying the key file there; otherwise its seals are proposals on the
  first computer.
- **Any edit to a recorded entry**, a single word of the reason included, makes it a proposal again until recorded
  again.
- **One new dependency**, `toml_edit`, so that `sv review` changes only the entry and keeps the owner's comments and
  layout.


## Later, 5 October 2026: `sv review` writes today's fingerprint

"Nothing else in the file is changed" has one exception now. When a person records a `[[finding-review]]` entry
whose fingerprint is in the form used before 5 October 2026 and names one line, `sv review` writes that line's
fingerprint in today's form in its place, and seals over it, so the entry watches what today's fingerprint watches
(deep review A2; ADR-023, "Later, 5 October 2026"). An earlier fingerprint that names several identical lines is
left as it is, and the person is told it cannot count until written again. What is sealed is unchanged: every field
of the entry, as written. A sealed entry is never rewritten, by the report or by `sv review`, so seals made before
this still verify. Held by `an_earlier_fingerprint_on_identical_lines_is_left_and_todays_shows_its_one_line`
(`crates/sv-cli/src/review.rs`) and `what_a_person_records_counts_and_the_report_says_where_its_seal_was_checked`.

## Later, 6 October 2026: no key, no credit; and a seal names its app

The review of the code merged on 1 to 4 October found two gaps in this record (BACKLOG, items 8 and 11), and the owner
settled both the same day.

- **On a computer with no key, a sealed entry no longer counts** (item 8). It had counted there, unchecked, as decided
  above. But such a computer cannot tell the owner's seal from one the AI coding tool wrote in the right form, and the
  report said the entry was "recorded through `sv review` on another computer", which claimed more than was known. Now
  such an entry is a proposal there, like one with no seal. The report says it carries a seal this computer cannot
  check, and what to do: run `sv review` once on this computer, or read the report on the computer that sealed it.
  This reverses "A sealed entry counts on a computer with no key to check it" in Context, the matching line under
  Decision, and "On CI … a sealed entry is taken on trust" under Consequences. CI and the container now credit an
  owner's entry only when given the key, as the README says to do for the container.
- **A seal names the app it was made for** (item 11). A sealed answer copied from one app into another on the same
  computer had counted there. The seal is now `v2:<key id>:<app id>:<mac>`. The app id is 16 hex characters of a
  SHA-256 of the app's folder, with every link followed, and the MAC covers it. A seal for another folder is a
  proposal, and says so. The folder, not the app's name in `securevibe.toml`, because the AI coding tool can change the
  name to match.
- **What this costs the owner:**
  - Every entry sealed before this change (`v1:`) is a proposal until `sv review` is run once in the app. The report
    says so, and `sv review` asks about each one.
  - So is every entry in an app moved to another folder, or recorded on a second computer where the app is in another
    folder.

`Sealed::Unchecked` is gone: a seal that counts was checked here. Held by `a_seal_counts_only_where_this_computers_key_checks_it`,
`a_seal_counts_only_in_the_app_it_was_made_for`, `a_seal_made_before_seals_named_their_app_is_asked_about_again`, and
`an_app_is_its_folder_however_it_is_reached` (`seal.rs`), the judgments in `review.rs` and `confirm.rs`, and end to end in
`what_a_person_records_counts_and_the_report_says_where_its_seal_was_checked`, which copies a recorded app to another
folder.

## Later, 6 October 2026: what a sealed notes section leaves out of its seal

The lines a section of the notes says who wrote it on are left out of what `sv review` seals, as Decision says. They
were left out wherever they stood, and by how they began, so a line beginning `Written by:` or `Sealed by sv review:`, or
a byline in emphasis, could be added anywhere in a sealed section and the seal still held (item 10 of the review of 1 to
4 October). Now each is left out only when it can carry nothing else: a `Written by:` line naming one of the two
writers, a seal line holding a well-formed seal and nothing more, and a byline only above the answer. Anything else is
part of the answer and sealed with it. What a seal is made over is otherwise unchanged, so a section sealed before this
still holds unless such a line stood inside it. Held by `a_line_added_inside_a_sealed_section_breaks_its_seal`
(`crates/sv-check/src/notes.rs`).

## Later, 6 October 2026: seals become signatures (ADR-043)

The owner chose SSH signing for what `sv review` records, so that a computer given only the public half of the key
can check a seal and cannot make one (ADR-043). From now on `sv review` signs each entry (`v3:<app id>:<signature>`)
with `review-signing-key` and makes no `review-key`. A signed entry counts where a list of trusted keys names its key
for the app: this computer's `allowed_signers`, beside the key, where the app is also its folder, as above; or
SV_TRUSTED_SEALS on CI and in the container, where the folder is never the one it was recorded in.

- **What is kept from this record.** `sv review` runs only in a terminal; what it records is written into
  `securevibe.toml` and the notes files; every field is covered, each with its length first; an entry changed after
  it was recorded is a proposal; a seal names its app; and what the seal cannot show is said in every report.
- **What changes.** "On a computer with no key, a sealed entry no longer counts" (the entry of 6 October above) now
  reads: on a computer with no list of trusted keys. CI and the container credit the owner's entries when given the
  list, not the key, and could not make a seal with it. "Not who was at the keyboard" still holds, except that a key
  with a passphrase cannot sign without the person who knows it.
- **`v2:` seals** made with `review-key` still count on the computer that holds it, and `sv review` there offers to
  sign them all again at one yes. `review-key` stays where it is, and nothing reads it but those checks.
- **Report seals** (ADR-034, `report-key`) are unchanged.
