# ADR-052: Packages installed before the run, outside the fence, in a container that sees only the dependency files

**Status:** accepted, 7 October 2026, in the pull request that builds it; proposed the same day with the backlog
claim. The owner agreed the recommendation that day ("I agree with your recommendation, please go ahead and write it
up as proposed"), from the gap analysis's item 3.1 (`docs/GAP-ANALYSIS.md`; BACKLOG, gap analysis item 9, its "Later"
part), read the record, and approved it ("I read ADR-052 and approve it, go ahead and build it").

**Governs:** `crates/sv-run/src/install.rs` (the install step: what it is given, what it runs, what it refuses) and
`crates/sv-run/src/docker.rs` (where it runs and how the app is given the packages). The setting itself is one line
of the manifest's run section, and the specification explains it; neither of those files is listed here, since both
are changed often for other reasons. A pull request that changes
what the governed files say about this changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

**Changes:** ADR-019 (the app runs on a network with no way out) gains a Later entry: the app still does, and a
separate step before it may download packages. `CLAUDE.md`'s rule that `sv` opens no network connection of its own,
with one exception, gains a second exception, named there.

## Context

`sv run` starts the app with its folder mounted read-only and no network (ADR-019), and runs `build` inside that same
fence (`crates/sv-run/src/docker.rs`). So `pip install` or `npm install` cannot work, and an app that needs packages
does not start: every running check reads "not assessed". That is honest, but most apps an AI coding tool writes use
packages (Flask, Express, an ORM, a password-hashing library). Every trial build so far was told to use the standard library
only, for this reason (206 by the gap analysis's count, and the revision trial's 110 since), so the trials have measured a kind of app few people build. The revision
trial showed what that costs: `production-server` recommends gunicorn, which no build could use. Today the only
route is to build an image yourself and name it with `image`, which a non-programmer cannot be expected to do.

## Decision

An **install step**, run before the app, in a container of its own that is thrown away afterwards:

1. **Turned on by the owner, per app**: a setting in `securevibe.toml`, under `[stack.run]` (its exact name is for
   the pull request that builds it), and nothing installed without it. The run summary and the report say when it
   ran.
2. **It sees only the dependency files**: `requirements.txt`, or `package.json` with
   `package-lock.json` (more ecosystems later, each its own change). The app's code, `.env`, and everything else in
   the folder are not mounted, so nothing secret is in reach while the network is open.
3. **Exact versions only.** Every package pinned to one version (`==` in `requirements.txt`, or a
   `package-lock.json`), with hashes used wherever the file gives them; otherwise the step refuses and says why. What
   is installed is what the app names, and the known-vulnerability check reads the same list.
4. **No package code runs while the network is open.** Python: wheels only (`pip install --only-binary=:all:`), so no
   `setup.py` runs. Node: `npm ci --ignore-scripts`. Packages are downloaded and unpacked,
   never executed, until the app runs behind the fence.
5. **The result is mounted read-only into the fenced run.** The app still runs with no way out, exactly as now; a bad
   package can do nothing that leaves the container.
6. **Cached by the lockfile's fingerprint**, so a second run downloads nothing.
7. **The report says what happened**, in plain words: "Packages were downloaded from PyPI (or npm) before the run, in
   a container that saw only the dependency files; the app itself ran with no network."

## Alternatives considered

- **`sv` builds the app's own Dockerfile.** Every line the AI coding tool wrote would run with the network open and
  the whole project in view. A much wider opening for the same gain. Building an image yourself and naming it with
  `image` stays the documented route for whatever the install step cannot do.
- **Let `build` reach the network.** The app's own code would run with the network open, which is what the fence
  exists to prevent.
- **Nothing beyond documentation** (the gap analysis's "Now" part, which this record does not replace). Honest, and
  leaves most real apps unassessed.

## Consequences

- **Some packages will not install this way**: those with no ready-made wheel, or that need their install scripts
  (Node's `bcrypt`, some database drivers). The step names the package and points to building an image.
- **`sv` causes downloads** for the first time beyond `sv probe`: from the package registries only, only when the owner
  turns it on, and said in every report it affects.
- **The trials can use briefs that allow packages**, once this is built, and tests of prompts such as
  `production-server` become fair.
- **Not decided here:** limiting the install container's network to the registries' addresses (worth doing if the
  fence can, a question for the pull request that builds this), and ecosystems beyond Python and Node.

## As built, 7 October 2026

- **The setting is `install = true`** under `[stack.run]`. Absent or false, nothing is installed or downloaded.
- **The packages go in a Docker volume, not a folder on the owner's computer**: `sv-deps-py-…` or `sv-deps-node-…`,
  named from a fingerprint of the image and the dependency files, labeled `stackvet.deps` (`securevibe.deps` before
  the rename, ADR-062). It lives inside the container backend, so nothing is written into the owner's folders and
  Colima's sharing does not matter. A volume counts as filled only when the install wrote its mark last; one an
  interrupted install left is emptied and filled again. `docker volume ls --filter label=stackvet.deps` lists them;
  nothing removes them automatically, and `sv run` and the report name the ones a run kept, with the command that
  removes them (backlog 226, part 2, item 18).
- **Python:** `pip install --only-binary=:all: --target`, mounted read-only at `/sv-deps`, with `PYTHONPATH` set and
  `/sv-deps/bin` first on `PATH`. **Node:** `npm ci --ignore-scripts`, mounted read-only at `/node_modules`, which
  Node finds from `/app` by itself, with `/node_modules/.bin` first on `PATH`. Both are set on the app's container,
  so the start command, `seed`, and the tests all find them.
- **A correction to "what is installed is what the app names":** every line of `requirements.txt` must name one
  version, but the packages those depend on are chosen by pip at the first install, as pip always does, unless the
  file pins them too. A `package-lock.json` names every one. The volume then holds the same versions for every later
  run with the same file.
- **Not built:** limiting the install container's network to the registries. It runs on Docker's ordinary network;
  what keeps it safe is what it is given (only the dependency files) and what it runs (no package's own code).
- **Tested** (`sv_run::install` and `crates/sv-run/tests/install.rs`): with a real container backend, a fixture app
  that imports `six` starts only with the install step, shows the installed version on its page, and a second run
  reuses the download; without the step it fails to start, naming `six`. Broken on purpose, each was caught: npm's
  install scripts allowed; pip allowed to build from source; the app's folder mounted into the install container;
  any version accepted; the packages given to the app writable; Python's import path not set (caught only by the
  test with a real backend).

## Later, 8 October 2026: only in Docker's own `python` and `node` images

The review of `sv` that day (BACKLOG, "From the review of 8 October 2026", item 1) found the hole this record's
"no package's own code runs" did not close. The install container runs `sh -c "pip install …"` or `npm ci …`, and
those programs are the *image's*; `image` is whatever `securevibe.toml` names. An app that named an image of its own
had that image's `sh`, `pip`, `npm`, and settings files run with the internet, the owner's local network, and the
container backend's bridge address reachable: not the packages' code, but code of whoever made the image, with the
way out the fence exists to deny. The hardening (read-only, every capability dropped, an empty environment, only the
dependency files mounted) kept the owner's files out of reach, not the network.

**Decision:** the install step runs only when `image` is one of Docker's own `python` or `node` images, with or
without a tag, a digest, or Docker Hub's own prefix (`install::official_image`). Any other image is refused before
the folder is looked at, in plain words that name the image and the route that stays: build the packages into your
own image and leave `install` out. Those two images are also the only ones in which the packages are sure to fit the
interpreter the app then runs them with, so nothing an app could do before is lost that worked.

**Alternatives set aside:** asking the owner at the terminal before running another image (the MCP server has no
terminal to ask at, and the answer would have to be remembered); running the install in an image `sv` chooses to
match the app's (`docker image inspect` does not say which Python or Node an arbitrary image holds). The item this
record's "Not decided here" left open, limiting the install container's network to the registries' addresses, is still
open and would narrow the same hole further.

Held by `the_install_runs_only_in_dockers_own_python_or_node_images` (`crates/sv-run/src/install.rs`): nine names
admitted, twelve refused (`--privileged` among them), and `plan` refusing a `ghcr.io` image in those words while
admitting `python:3.12-slim` over the same folder. The record's **Governs** line is unchanged: `install.rs` is where
this lives.

## Later, 8 October 2026: npm packages only from the npm registry, and no linked dependency file

The review of 8 October (item 2) found that this record's "downloads its packages from PyPI or npm" held for Python
and not for Node: `requirements.txt` was held to exact versions, but `npm ci` fetches each package from the address
its `package-lock.json` names, and a lockfile is a file anyone can edit, so the one container of `sv`'s that can
reach the internet would fetch from any server it was given. `plan` now refuses a lockfile any of whose packages is
downloaded from anywhere but `https://registry.npmjs.org/` (a look-alike host and plain `http` included), or carries
no SHA-256, SHA-384, or SHA-512 `integrity` fingerprint, or is a local folder; it reads lockfile versions 2 and 3
(`packages`) and version 1 (nested `dependencies`), passes a package bundled inside another, and refuses a lockfile
it cannot read rather than taking it as clean. The review also found the dependency files read through `is_file`,
which follows a link: a `requirements.txt`, `package.json`, or `package-lock.json` that is a link is now refused
before anything is read, so the container is given the app's own files and nothing they point to. Each refusal
names what was refused, in plain words, before anything runs. The decision stands, and is now true for both.

Held by `crates/sv-run/tests/npm_sources.rs`: eight guards broken in turn, each caught.

## Later, 8 October 2026: the volume's name is a SHA-256

The review of `sv` that day (BACKLOG, "From the review of 8 October 2026", item 6): the volume's name was two FNV-1a
passes over the ecosystem, the image, and the dependency files, which is a checksum rather than a hash, so a
dependency file could be written to land on another app's volume name and be served that app's packages. **The name
now carries the first 128 bits of a SHA-256** over the same bytes (`install::volume_name`; `sha2`, already a
dependency of `sv-check`, added to `sv-run`). Every existing volume gets a new name once and is filled again; the
old ones stay until the owner removes them, as this record says nothing removes them automatically. Held by the
volume-name tests in `install.rs` and `crates/sv-run/src/install/volume_tests.rs`.
