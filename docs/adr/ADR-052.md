# ADR-052: Packages installed before the run, outside the fence, in a container that sees only the dependency files

**Status:** proposed, 7 October 2026, with the backlog claim. The owner agreed the recommendation that day ("I agree
with your recommendation, please go ahead and write it up as proposed"), from the gap analysis's item 3.1
(`docs/GAP-ANALYSIS.md`; BACKLOG, gap analysis item 9, its "Later" part). The pull request that builds it makes it
accepted, and nothing is built before the owner has read this record.

**Governs:** `crates/sv-run/src/docker.rs`, where the install step will run. The pull request that builds it adds the
files that hold its setting and its wording in the specification. A pull request that changes what these say about
this changes this record too, or says in its description why it does not (`docs/adr/README.md`).

**Changes:** ADR-019 (the app runs on a network with no way out) gains a Later entry: the app still does, and a
separate step before it may download packages. `CLAUDE.md`'s rule that `sv` opens no network connection of its own,
with one exception, gains a second exception, named there.

## Context

`sv run` starts the app with its folder mounted read-only and no network (ADR-019), and runs `build` inside that same
fence (`crates/sv-run/src/docker.rs`). So `pip install` or `npm install` cannot work, and an app that needs packages
does not start: every running check reads "not assessed". That is honest, but most apps an AI coding tool writes use
packages (Flask, Express, an ORM, a password-hashing library). Every trial build so far was told to use the standard library
only, for this reason (206 by the gap analysis's count, and the revision trial's 110 since), so the trials have measured a kind of app few people build. The revision
trial showed what that costs: `production-server` recommends gunicorn, which no build could use. Today the only
route is to build an image yourself and name it with `image`, which a non-programmer cannot be expected to do.

## Decision (proposed)

An **install step**, run before the app, in a container of its own that is thrown away afterwards:

1. **Turned on by the owner, per app**: a setting in `securevibe.toml`, under `[stack.run]` (its exact name is for
   the pull request that builds it), and nothing installed without it. The run summary and the report say when it
   ran.
2. **It sees only the dependency files**: `requirements.txt`, or `package.json` with
   `package-lock.json` (more ecosystems later, each its own change). The app's code, `.env`, and everything else in
   the folder are not mounted, so nothing secret is in reach while the network is open.
3. **Exact versions only.** Every package pinned to one version (`==` in `requirements.txt`, or a
   `package-lock.json`), with hashes used wherever the file gives them; otherwise the step refuses and says why. What
   is installed is what the app names, and the known-vulnerability check reads the same list.
4. **No package code runs while the network is open.** Python: wheels only (`pip install --only-binary=:all:`), so no
   `setup.py` runs. Node: `npm ci --ignore-scripts`. Packages are downloaded and unpacked,
   never executed, until the app runs behind the fence.
5. **The result is mounted read-only into the fenced run.** The app still runs with no way out, exactly as now; a bad
   package can do nothing that leaves the container.
6. **Cached by the lockfile's fingerprint**, so a second run downloads nothing.
7. **The report says what happened**, in plain words: "Packages were downloaded from PyPI (or npm) before the run, in
   a container that saw only the dependency files; the app itself ran with no network."

## Alternatives considered

- **`sv` builds the app's own Dockerfile.** Every line the AI coding tool wrote would run with the network open and
  the whole project in view. A much wider opening for the same gain. Building an image yourself and naming it with
  `image` stays the documented route for whatever the install step cannot do.
- **Let `build` reach the network.** The app's own code would run with the network open, which is what the fence
  exists to prevent.
- **Nothing beyond documentation** (the gap analysis's "Now" part, which this record does not replace). Honest, and
  leaves most real apps unassessed.

## Consequences

- **Some packages will not install this way**: those with no ready-made wheel, or that need their install scripts
  (Node's `bcrypt`, some database drivers). The step names the package and points to building an image.
- **`sv` causes downloads** for the first time beyond `sv probe`: from the package registries only, only when the owner
  turns it on, and said in every report it affects.
- **The trials can use briefs that allow packages**, once this is built, and tests of prompts such as
  `production-server` become fair.
- **Not decided here:** limiting the install container's network to the registries' addresses (worth doing if the
  fence can, a question for the pull request that builds this), and ecosystems beyond Python and Node.
