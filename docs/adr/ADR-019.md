# ADR-019: `sv` runs the app in a container on a network with no way out

**Status:** accepted. Decided with `sv run`'s design (DESIGN, "Running the code" and "`sv run`", from 22 to
24 September 2026) and written down here on 27 September 2026, because the ADR analysis found that no record
named it (BACKLOG, "Records that disagree with what was built", item 8).

**Governs:** `crates/sv-run/src/docker.rs`, `crates/sv-run/tests/fence.rs`. A pull request that changes any of these
changes this record too, or says in its description why it does not (`docs/adr/README.md`).

**Replaces, for `sv`:** v1's ADR-010 (on the `v1` branch), which ran generated code as a Node process under
Node's permission model and rejected containers because "Docker is not available on the target machine". That
record describes v1 and stays as it was.

## Context

The strongest evidence about an app comes from running it: signing in as a test user and asking what that user
can reach. v1 could run the apps it wrote because it knew they were Node: it started them under Node's
permission model, which limits the file system, and two days later fenced their network with `sandbox-exec` on
macOS and a network namespace on Linux (`pipeline/net-fence.ts`). ADR-010 was not updated for the second step.

`sv` checks apps it did not write, in any language, so it can neither assume Node nor rely on Node's
permission model. It also runs somebody else's code, which may be careless or hostile, on the owner's own
computer. A container backend became available on the owner's machine on 22 September 2026 (Colima 0.10.3 with
Docker 29.8.1), which removed ADR-010's reason for rejecting one.

## Decision

`sv run`, and `sv report --run`, start the app in a container, fenced as follows:

- **The network is created with `--internal`**, so nothing on it can reach anything outside it. The runner
  then asks Docker whether the network really is internal, and refuses to start the app if the answer is
  anything but yes. Passing the flag and checking it are different claims, and only the second survives an
  edit that drops the flag.
- **Nothing is published to the owner's computer.** The probes run from a small helper container on the same
  internal network, not from the host.
- **The app's folder is mounted read-only**, the only writable place is a small in-memory folder for a test
  report, and the app is given none of the owner's environment: no keys and no home folder.
- **The helper containers get less still.** The helper that sends the probes, and the stand-in mail server,
  sign-in provider, AI model, and browser, have a read-only file system, no capabilities, and no way to gain
  privileges.
- **No container backend means "not assessed".** Everything that needs the app running is reported as not
  assessed, never as passed or failed, and the reports say which applied.

## Alternatives considered

- **Keep v1's approach**, a process under a language's own permission model with an OS network fence. It
  works only for languages that have such a model, and `sv` checks apps in any language.
- **A container on Docker's default network, probed through a published port.** This was measured, not
  assumed: on the default network the app reached `1.1.1.1:53`, so the fence was gone. On an `--internal`
  network it did not, and the host could not reach a published port either, which is why the probes moved
  into a helper container.
- **Run nothing, and check only files.** This loses every requirement that only a running app can answer:
  sign-in, sessions, access control, and uploads.

## Consequences

- The owner needs Docker, or a compatible backend such as Colima, for anything that runs the app. Without it,
  those requirements say *not assessed*, and the report says why.
- Docker downloads the images `sv run` starts the first time each is needed: the image the manifest names for
  the app (`image` under `[stack.run]`), and `busybox`, `axllent/mailpit`, `node:22-alpine`, and
  `chromedp/headless-shell` for the helpers. That is Docker's connection, not `sv`'s, and the README says so.
- The `sv` container image cannot run apps itself, because starting containers from inside a container means
  handing it the Docker socket, which is control of the owner's computer (DESIGN, "`sv` in a container").
- An app that needs to reach an outside service to start or work cannot be fully checked this way. The fence
  is the point, so `sv` supplies stand-ins on the fenced network instead: a mail server, a sign-in provider,
  and an AI model.

## Later, 30 September 2026

The weekly review of the records found one sentence above that is not true of the code. "The only writable place
is a small in-memory folder for a test report" holds for the app's folder, which is mounted read-only, and for every
helper container, which runs with `--read-only`. It does not hold for the app's own container: `sv-run` starts it
without `--read-only` (`crates/sv-run/src/docker.rs`, the `run` arguments for the app), so the app can write
anywhere in its container's own file system outside `/app`, such as `/tmp`. That space is Docker's storage, not the
owner's folder, and it is removed with the container. The in-memory folder for the test report is given no size
limit either, so "small" is not enforced. The comment beside that code said the same as this record and is
corrected. Whether the app should run read-only too, with an in-memory `/tmp`, is a choice with a cost (an app or a
build step that writes elsewhere would fail) and is in the backlog.

## Later, 3 October 2026

The owner chose read-only. The app's container now runs like every helper: `--read-only`, `--cap-drop ALL` and
`no-new-privileges`, with two in-memory folders as its only writable places, `/tmp` (256 MB) and the test-report
folder (16 MB). The arguments are built by `app_args` in `crates/sv-run/src/docker.rs`, so a test reads them, and
`the_app_is_hardened_like_every_helper` turned red when each flag or size was removed in turn.

Measured before and after, with `sv run` on every example app and on a small app that refuses to start unless it is
contained:

- That app, under the old arguments, could write to `/etc` and held Docker's default capabilities
  (`CapEff 00000000a80425fb`). Under the new ones it could write only to `/tmp`, held none, and started.
- The four example apps that start gave the same results before and after, check for check, including the
  signed-in checks, the headless browser, and the app's own test suite writing to the report folder.
- `examples/flask-booking` did not start before or after: its build step, `pip install`, cannot download anything
  behind the fence. What it last printed changed, from the network refusal to "site-packages is not writeable",
  and neither line names the cause, so the report now says that a build step runs inside the fence, where nothing
  can be downloaded and nothing outside `/tmp` written, and that packages belong in the image.

The cost is the one recorded above: an app that writes outside `/tmp` while it runs now fails to start, and the
report says where it may write.


## Later, 4 October 2026: the network's gateway

The deep review of `sv` at `eff3f17` found a way out that this record's title denies (S2, high): `docker network create
--internal` stops traffic to the internet but still gives the network a gateway address, and that address is the host
(this computer on Linux, or the virtual machine Docker runs in on Docker Desktop and Colima). The review's fenced
container reached the Colima machine's SSH server. Fixed the same day (#558): the network is made with no gateway
address where Docker allows it, and before the app starts a throwaway container knocks on every address a gateway could
have; an answer, or a refusal, stops the run. The fence test now needs a plain `--internal` network to be refused, so a
pass proves something. DESIGN, "The fence's gateway".

## Later, 4 October 2026: the release build must keep unwinding

The containers and network a run starts are removed by `Teardown`'s `Drop` (`crates/sv-run/src/docker.rs`), and a
`Drop` runs when a check panics only because the release build unwinds. Switching `[profile.release]` to `panic =
"abort"` to make the binary smaller would leave a run's fenced containers running whenever a check panicked. The reason
was until now only a comment in `Cargo.toml` and a sentence in DESIGN, "A release profile" (#330); nothing tests it,
so it is said here. Ctrl-C and a run killed outright are ADR-025's.

## Later, 4 October 2026: limits on what the app may use

The deep review found that the app ran with no limit on memory, processes, or processors, and that `sv` kept
everything a command printed (S9, medium). An app that leaks memory, starts processes without end, or answers with
gigabytes could take the owner's computer down with it, and the app is code `sv` was asked to check, not code it
trusts. Every container a run starts now gets the same limits, added in the one place every `docker run` passes
through (`DockerBackend::prepared`), so a helper written later cannot be missed: 2 GB of memory and no swap beyond
it, 512 processes, and two processors, or all of them when Docker has fewer. The browser's and the mail server's
in-memory folders now have a size, as the app's already did. `sv` keeps at most 32 MB of what any command prints on
each stream; the rest is read and thrown away, so the command never waits on a full pipe. A Docker call whose output
was cut is never handed to a check as an answer, and a test suite's output says where it was cut. DESIGN, "Limits on
what the app may use".

The review also asked for `--user`, so the app does not run as root inside its container. That was weighed and left
out. Every capability is already dropped, so root inside the container cannot read another user's files, change
ownership, or bind a privileged port, and `no-new-privileges` stops it gaining any. Many images install their
packages under root's home folder or with root-only permissions, so a fixed other user would make apps fail to start
for a reason that has nothing to do with their security. If that changes, it is a record of its own.

## Later, 4 October 2026: each run removes only its own

The deep review found that a run was named from the process id alone and torn down by name (S10, medium). Two copies
of `sv` in two containers sharing one Docker daemon, as on a CI runner, are often the same process number in their
own containers, so they gave their runs the same names and each run's teardown could remove the other's containers.
A run's name now ends in four random bytes, and everything it creates, containers and its network alike, carries
the label `org.securevibe.run` with that name. Its teardown removes what Docker lists under that label, by id, and
falls back to the run's own names only if Docker will not list them. The owner label that the next run's cleanup
reads after a crash is unchanged. DESIGN, "Each run removes only its own".

## Later, 5 October 2026: the browser's DevTools on loopback, and the driver in a world of its own

The deep review's S11. The browser image's own start script forwards port 9222 on every address to Chromium's
DevTools, so the app, on the same fenced network, could reach the browser by its address and drive it: read what
it reads, and change what it sees. Reproduced with `chromedp/headless-shell:151.0.7922.109` on an internal network:
another container got DevTools' version answer from the browser's address. Built by session securevibe-e9 at the
owner's asking, in branch `claude/securevibe-e9-s11`.

- **Chromium is started directly** (`--entrypoint /headless-shell/headless-shell`), with DevTools on 127.0.0.1
  alone. The driver shares the browser's network, so it still reaches DevTools there, and nothing else does. The
  image's forwarder is not started.
- **The driver runs every expression in a world of its own** in the page (`Page.createIsolatedWorld`), the same
  page and storage with none of the page's scripts, so the app cannot redefine what the sign-out check reads
  with. When that world cannot be made, the action fails rather than reading through the page's world.
- Storage is still read with the page's interfaces in that world, not through DevTools' storage domains, which the
  review also named; the world of its own already keeps the page's scripts out of the reading.

Held by `the_app_cannot_reach_the_browser_s_devtools_or_hide_its_storage_from_the_driver`, against a real browser
and an app that redefines `Storage.prototype.getItem` and `Object.keys`, and by
`the_browser_and_its_driver_are_fenced_and_hardened_like_the_sidecar`, which needs no container backend.
