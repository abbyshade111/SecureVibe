# ADR-037: A Python project with no lockfile does not pin, `setup.py` and `setup.cfg` included

**Status:** accepted. Built on 5 October 2026 by session securevibe-e10 as the rest of the deep review's H9
(#766, DESIGN, "What a `requirements.txt` leaves out is named, and a `setup.py` with no lockfile does not pin"), and
recorded the same day after the owner, asked whether it should be, said to record it. The record came after the
decision's pull request, not with it; the session judged no record was owed and said so in #766, and the owner
decided otherwise.

**Governs:** `crates/sv-scan/src/ecosystems.rs`. A pull request that changes it changes this record too, or says in
its description why it does not (`docs/adr/README.md`).

## Context

The pinning check (`config.versions-pinned`, V15.1.2) asks whether the versions an app installs are fixed, so that
its list of third-party libraries is what is installed and not what was asked for. An ecosystem that pins with a
lockfile and has none is reported as not pinning, whatever its manifest says: a `requirements.txt` of exact
versions still lets each of those packages pull in whatever versions of its own dependencies are newest on the day
(`ecosystems::pinning`). Maven, and Gradle without its lockfile, are read for their versions instead, since neither
needs a lockfile to install the same thing every time.

A Python project can declare what it installs in `setup.py` or `setup.cfg` (`install_requires`) and nowhere else.
Neither was one of the manifests the check looked at, so an app declared there alone was told it had no package
manifest ("not assessed"), and one beside a locked npm app had its pinning credited on npm's lockfile alone.

## Decision

- **A `setup.py` or `setup.cfg` that names packages to install, with no Python lockfile in the same folder, is a
  project that pins with a lockfile and has none,** and is reported as not pinning, by the pinning check and in the
  scan's own list of unpinned projects (`ecosystems::setup_only_in`, used by `unpinned_in` and by
  `config::versions_pinned`). `pip install .` resolves `install_requires` afresh each time, as
  `pip install -r requirements.txt` does without a lockfile.
- **A Python lockfile in the same folder stands for it** (`pipenv install -e .`, `pip-compile setup.py`, `uv lock`
  are made from it), and a `setup.py` that names no packages declares nothing.
- **The rule is not new, only its reach.** No lockfile, no pinning, as for every other ecosystem that uses one.
- **One folder is named once.** A `requirements.txt` and a `setup.py` side by side are both "Python".

## Considered

- **Reading `install_requires` for exact versions, as Maven's are read.** Set aside: exact versions in
  `install_requires` still leave every dependency of theirs to float, which is why a `requirements.txt` of exact
  versions without a lockfile is not counted as pinned either; and `setup.py` is a program, whose list `sv` would have
  to guess at without running it.
- **Leaving such an app "not assessed".** Set aside: that is a true statement only when nothing is known, and here
  something is: there is no lockfile, and that is the whole of what the check asks.

## Consequences

- A Python app or library declared in `setup.py` without a lockfile now gets a medium finding, "Python does not pin
  the versions it installs", where it had "not assessed" or a pass. For a library meant to be installed by others,
  that is the check working as written; such a project can set the folder apart (`not-the-app`) or record the finding
  as an accepted risk.
- A requirements file under another name (`requirements-dev.txt`) without hashes is still not judged by the pinning
  check, though the bill of materials names it as not read (BACKLOG, H9).
- Tested by `config::tests::a_python_app_declared_only_in_setup_py_does_not_pin` (`crates/sv-check/src/config.rs`).

## Later, 6 October 2026: requirements files under other names, and a lone `Pipfile.lock`

The two gaps H9's last done note left open are closed by session securevibe-e2, in the same shape as the decision
above (DESIGN, "A lone `Pipfile.lock`, and requirements files under other names").

- **A requirements file under another name** (`requirements-dev.txt`, `requirements/prod.txt`) is judged by the
  pinning check too. It is its own lockfile when it pins and hashes every package (`fully_hash_pinned`, the test
  `requirements.txt` already meets), and otherwise pins nothing, **whatever lockfile is beside it**, which is where
  this differs from `setup.py`: a lockfile is made from what `setup.py` asks for, while a requirements file under
  another name is usually the very list a lockfile beside it leaves out. The bill of materials already named it as
  unread on the same reasoning. A Conda `environment.yml` is still not judged.
  `ecosystems::setup_only_in` is renamed `declared_elsewhere_in`, since it is no longer only `setup.py`.
- **A `Pipfile.lock` with no `Pipfile` beside it** is a Python project of its own, since `pipenv sync` installs from
  it alone, and is read like any lockfile. It is skipped wherever another manifest in its folder already lists it as
  a lockfile (`read_as_lockfile_beside`), so beside a `Pipfile` or a `requirements.txt` it is read once, as before.
