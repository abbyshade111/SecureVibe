# ADR-061: One file per backlog item, with a status line

**Status:** accepted, 8 October 2026, in the pull request that builds it; proposed the same day with the backlog claim.
Asked for by the owner that day ("can you please go ahead with the one file per backlog item when you're ready?"),
from the proposal in the backlog item "One file per backlog item, with a status line", after the end-of-day write-up
and the owner's question about managing the backlog. Written by session securevibe-review.

**Governs:** `docs/BACKLOG.md`, `tools/backlog.py`, `crates/sv-cli/tests/backlog_board.rs`. Not the items
themselves: every claim adds or edits one, and none of them changes how they are kept. A pull request that changes
one of these changes this record too, or says in its description why it does not (`docs/adr/README.md`).

## Context

`docs/BACKLOG.md` is where work is claimed before it starts and marked when it is done, and it has never had a
"Done" section: on 8 October 2026 its "Next" section held 149 items, 82 of them finished and never moved, 31 with
parts in more than one state, and 237 open parts in all. What is open is a reading of each item's prose markers
(`**Claimed`, `**Done`, "Not done"), which the status board of that day (`tools/backlog.py`) makes, and which errs
toward open when a marker is written another way. Every claim and every done note is an addition to the one file,
so any two open pull requests meet there; `tools/merge_main.py` settles the both-added case, and ADR-060 took the
same conflict out of the design record by making each entry a file. The owner's words: "it's hard for me to parse
what's done and not done".

## Decision

Each backlog item becomes a file of its own under `docs/backlog/`, named by a four-digit number and its title made
into a file name, as design entries are (ADR-060). Its first line is `# ` and the title, unchanged from the bold
lead sentence it had, since the code and the documents cite items by title (`BACKLOG, "title"`, some 300 times) and
a search of `docs/backlog/` finds one. Its third line is the status, in one of four forms:

    **Status:** open
    **Status:** claimed by <session>, <date>
    **Status:** done, <date>
    **Status:** partly done: <what remains>

The rest is the item's text as it was, its numbered parts included. Parts are not files: a part claimed or done on
its own is marked in the part's text as today, the item's status line says `partly done` with what remains, and the
board counts the parts' markers beside the item's line. The numbers keep the order the items stood in the old file
at the split and are an identity, not a date; a new item takes the number one past the highest, and two pull
requests open at once may take the same number, which harms nothing.

`docs/BACKLOG.md` keeps the rules and the roadmap, and holds no item and no list of items: a list every item adds a
line to would bring the conflicts back. A test fails when it holds one.

`tools/backlog.py` reads the status lines rather than the prose: `list` and `summary` as before, `new` to write an
item, `claim` and `done` to set its status line, `--check` for the layout (every file named `NNNN-title.md`, a title
on its first line, a status in one of the four forms, no two files with one title, no item in `BACKLOG.md`), and
`move` for a branch written before the split, which makes an item of each entry in its old-layout file that is not
one yet and names, for a person, any whose text differs.

A claim is still a commit of its own, merged before building: `python3 tools/backlog.py claim <number> --by
<session>`, then the pull request. Two sessions claiming the same item now conflict with each other on that one
file, which is the right outcome; a claim and an unrelated done note no longer conflict at all.

## Considered

- **Moving done items to a "Done" section or a second file** (gap item 33's first form). Fewer lines to read, but
  the claims and done notes of the open items still meet on the same lines, and "done" would still be a reading.
- **GitHub issues with assignees** (gap item 33's second form). The record would leave the repository the paper
  cites at commit hashes, and the owner reads the backlog as a document, not a tracker.
- **A generated index committed beside the items.** Every item would add a line to it; the conflicts would move
  there, as ADR-060 found for the design record.
- **A status line in the one file**, item by item, without the split. The reading becomes data, but the file stays
  8,600 lines, and two claims still meet.

## Costs

- Every open branch that edited `docs/BACKLOG.md` conflicts once with the split. A branch that added an item mends
  it with `python3 tools/backlog.py move`, as the script's opening says; a branch that added a claim or a done note
  inside an item carries that note into the item's file by hand, since the note's place is now a status line.
- The roadmap and the documents name items by title, and a title is now also a file name: renaming a title means
  renaming its file, which nobody should do.
- The 31 items with parts in more than one state are given `partly done` by the split with the counts read from
  their markers, and what remains is for a person to write in each when they next touch it.
- The paper and older documents name `docs/BACKLOG.md` at commits before the split, and are left as they are.

## As built

As planned, with four things the plan did not say:

- **Struck-through items.** 47 entries of the old file were written `- ~~**title**~~`, finished or withdrawn and
  struck rather than marked; the split reads them as items too, and one whose markers do not say done is given
  `done, struck through in the old file`, dated.
- **The one duplicate.** Two entries shared the title "AISVS, beyond applicability", the first a self-declared
  duplicate of the second; it is renamed "AISVS, beyond applicability (a duplicate entry)" so that both are files
  and no title is shared. Titles must be unique, since the documents cite by them, and `--check` holds that.
- **The second section's introduction.** The old "Decided, not yet written down as ADRs" section opened with prose
  (the three records written on 27 September 2026) before its first item; the split keeps it as an item titled after
  the section, so nothing is lost.
- **The status at the split is a dated reading, not a person's word**: `done, as its markers read on 8 October 2026`,
  `claimed by <session>, as its markers read on ...`, and for the 37 items with parts in more than one state `partly
  done: <d> of <n> parts done, <c> claimed, <o> open, as the markers read on ...`. Whoever next touches one writes
  what remains in its own words.

- **Batch notes.** Three items whose done notes name several parts at once ("Items 1 to 3 done the same day") read
  as open at the split, since no part carried a marker of its own: the two reviews of the code merged 1 to 6 October
  and the MCP hardening list. A reviewer's comment on the pull request named them, and their status lines say
  `done` by hand, dated with the reason. The reading at the split is dated for exactly this: it is what the markers
  said, not what a person knew.

The split was checked by putting the items back together: in their order, with their titles made bold leads again,
they give the old file's two sections exactly, but for line wrapping inside titles, the strike marks, and the period
each title ended with. The guard: `--check` fails on a file not named `NNNN-title.md`, on one with no title or no
status line or a status in none of the four forms, on two files with one title, and on an item left in
`docs/BACKLOG.md`; each was broken in turn in the self-test and caught, and an item left in the real `BACKLOG.md`
was caught by the check on the real folder.

## Later, 9 October 2026: urgent work gets a claim too, as a draft pull request

A claim is made on a backlog item, and urgent work has none: a red `main`, a check every pull request fails, an outside
service breaking CI. That evening two sessions built CI's Docker Hub sign-in at once, and then two built the fence
check saying what Docker said; each second one was closed unused. The owner asked that all sessions follow one rule
for it, now in `CLAUDE.md` beside the claim rule: before starting, read the open pull requests and the branches pushed
in the last few hours with the files each changes, and join or leave one that touches the same files; when none does,
open a draft pull request from one empty commit at once, so the claim is visible within a minute, and make it the real
pull request when the fix is in. It is a claim by pull request rather than by item file, because there is no item to
put it in and no time to merge a claim first. The rest of this record stands.

## Later, 9 October 2026: a status line for each numbered part

The owner's decision that evening, after the board was found counting parts wrongly: "yes, please add that change when it
fits into your workflow. And this can be part of the dashboard work whenever we get to that." This record gave each item
a status line and left its numbered parts to be read from their prose (`part_counts` in `tools/backlog.py`), on the
words `Done`, `Claimed`, and `not done`. On `main` that evening the board read 0226 as twenty parts open when two were
done and six claimed, because the claims and done notes were written at the item's end, under no part; 0085 as seventeen
parts partly done, because their prose described what had not been; and 0187 as done with four parts open.

Each numbered part gets a status line of its own, in the item's one form, set and read by `tools/backlog.py` alone;
`--check` holds every part to one, and an item's status to its parts; existing items are converted once, with an unclear
part marked as needing a look rather than guessed. How the board shows it moves to the observability dashboard (backlog
0227). Built under backlog 0228 and accepted the same evening, in the pull request that builds it.

**As built.** A part is a line `N. **Its title.**` and the indented lines under it; its line reads `**Part status:**`,
distinct from the `` `Status: proposed` `` some parts carry for a decision record. `claim 0226.3` and `done 0226.3` set
it; an item whose lists number afresh (two parts numbered 1) is set part by part in order by the conversion, and a
claim by number there is refused as ambiguous. The conversion gave 49 items' parts their lines: from a note naming the
part, or the part's own markers, with the note's date; a part of an item already done and with nothing said, done with
the item; a claimed item's, claimed by the same session; mixed words, "unclear, needs a look", 40 parts at first. Of
those, 0085's seventeen were read and settled as done: each "Not done:" there is the template's list of a built check's
limits, not work left. Twenty-three remain for a look, in eight items. An item that read `done` or `open` against its
parts (0187, 0191) became `partly done`, naming the parts. Real parts written without a bold title (in 0091, 0119, and
0170) were given one, from their opening words, so they are counted; the old reader had also counted "183." and
"2026." in mid-sentence as parts, which the new one does not.

**And the owner's yes to three more, the same evening** ("yes, I agree with all those fixes, thank you"): a `done`
folder that a finished item's file moves to, each finding of a future review written as an item of its own, and a
warning for an item past about 300 lines. As 0228's parts 6 to 8, accepted on 10 October 2026 in the pull request that builds them.

**As built, 10 October 2026.** A done item's file is in `docs/backlog/done/`, and everything that reads items reads
both folders. `done` moves an item there and rewrites any path to it in the repository's text; an item given what
remains moves back; `--check` names a file in the wrong folder, and `tidy` puts each where its status says. `tidy` moved
179 done items that day, leaving 50 live ones beside them, and rewrote the two paths to them that the design record
held. Done items have a section of their own in the private pages (ADR-058). The rule that a review writes each finding
as an item of its own is in `CLAUDE.md` and `docs/BACKLOG.md`; the size warning names a live item past 300 lines and
fails nothing, and named eight that day, 0006 the longest at 924. The rest of this record stands.
