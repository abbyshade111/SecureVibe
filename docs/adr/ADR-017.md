# ADR-017: `sv` never writes the app's code

**Status:** accepted. Decided with `sv`'s design ("No wizard": the person builds the app in their own AI
coding tool), and written down here on 27 September 2026.

**Governs:** `crates/sv-check/src/notes.rs`, `crates/sv-check/src/coding_rules.rs`, `crates/sv-cli/src/bundle.rs`. A
pull request that changes any of these changes this record too, or says in its description why it does not
(`docs/adr/README.md`).

## Context

v1 wrote the app. An AI generation agent extended a hardened template, and because that agent could write and
run files, it worked inside a fence of its own: allow-listed paths, validated tool inputs, and screened tool
output (v1's `CLAUDE.md`).

`sv` does not build the app. The person builds it in whatever AI coding tool they choose, and `sv` checks the
result afterwards.

## Decision

`sv` writes no code the app runs. It has no generation agent, so v1's fence around that agent has no
successor here, and none is needed.

What `sv` does write, each only when asked, by the owner's command or through its MCP server:

- `security-notes.md` (`sv notes`): the questions only the owner can answer, kept with their answers.
- A section of `AGENTS.md` between `sv`'s markers (`sv rules`): security rules for the AI coding tool to
  follow while it writes. The rest of the file is left as it was.
- The reports (`sv report`, into `securevibe-report/` unless told otherwise), in a folder marked so that the
  next check does not read it as the app's code, and a zip of the app with its report (`sv bundle`).

`sv init` writes nothing: it prints the `securevibe.toml` specification, and the owner's AI tool writes the
file. Everything in the list is read by a person or by the AI tool, and none of it is part of the running app.

Two other limits stand on their own, and this decision does not touch them:

- **Running the app is still fenced** (`sv-run`): the app runs in a container with no network beyond
  loopback and `sv`'s own stand-in services, and nothing published to the owner's computer.
- **`sv` opens no network connection of its own** (`CLAUDE.md`), with one exception the owner asks for by
  name: `sv probe <address>` makes at most four read-only requests to that address, through `curl`, and
  one DNS query to this computer's resolver.

## Alternatives considered

- **Offer fixes as code.** `sv` knows where a finding is and could write the change. That would make `sv` a
  second author of the app, beside the person's own tool, and would bring back everything the fence existed
  for. A finding carries a plain-language fix for the person, or their tool, to make instead.

## Consequences

- A fix is always made by whoever wrote the app, and the next `sv` check is what shows it worked.
- `sv` needs no guard against its own output breaking the app, and none against a model writing where it
  should not.
- A future feature that writes into the app's folder should be checked against this record. `AGENTS.md`
  is the nearest case so far: it steers the AI tool that writes the code, and writes no code itself.

## Later, 5 October 2026: a bundle replaces only a zip `sv` made

The deep review's improvement 7. `sv bundle` writes its zip outside the app, beside it by default, and wrote over
whatever file already had that name. A file of the owner's there, or given with `--out` by mistake, was lost. Built
by session securevibe-e9 at the owner's asking, in branch `claude/securevibe-e9-cli-guards`.

- **Every bundle ends with a comment of its own** in the zip's comment field, "Made by SecureVibe (sv bundle). See
  README.txt inside." (`bundle::MADE_BY_SV`), which any zip program shows.
- **A file already at the bundle's name is replaced only when it ends that way** (`bundle::made_by_sv`); anything
  else is refused, with the file named and left as it was. A bundle made before this, without the comment, is
  refused once, and the owner moves it.

Held by `a_bundle_replaces_only_a_zip_sv_made` (`crates/sv-cli/tests/bundle.rs`).


## Later, 5 October 2026: `sv review` adds seal lines, now in `design-decisions.md` too

The list above leaves out one thing `sv` has written into the app's folder since 4 October (ADR-026): `sv review`
puts a `Sealed by sv review:` line under a section of `security-notes.md` the owner records as theirs, and seals into
`securevibe.toml`. From today it does the same in `design-decisions.md`, under the two sections that count toward a
checklist control (ADR-022, "Later, 5 October 2026: the decisions file's sections, read as the notes are"). Each is one
line, written only when the owner types at their own terminal, and nothing else in the file changes. Neither file is
code the app runs, so the decision stands.

## Later, 8 October 2026: `sv init` redirected into a file prints only the starter

"`sv init` writes nothing" still holds: the shell writes, when the owner types `sv init > securevibe.toml`. The gap
analysis (`docs/GAP-ANALYSIS.md`, 5.3) found that what landed in the file then was the starter `securevibe.toml`
followed by many pages of instructions for the AI coding tool, which made it a file every later command refused. Since
backlog item 25(f), when standard output is a file rather than a terminal or a pipe, `sv init` prints only the
starter, which `sv` reads, and says on the screen that the instructions were left out and how to read them. Through a
pipe, as an AI coding tool reads it, nothing changes. What `sv init` can put in the folder is now only ever a starter
`securevibe.toml`, which is not code the app runs, so the decision stands. The check is in `crates/sv-cli/src/main.rs`
(`stdout_is_a_file`), governed by ADR-056 for other reasons; this record does not add it to its Governs list, because
`main.rs` holds most of `sv`'s commands.

## Later, 8 October 2026: `AGENTS.md` tells the tool to stop when SecureVibe is not connected

The rules `sv rules` writes into the app's `AGENTS.md` now open with one more instruction, right under their heading:
if the `securevibe_` tools are not among the tools the AI coding tool can call, it stops and tells the person
before writing any code, and never says the app was checked (`coding_rules::WHEN_NOT_CONNECTED`). The gap analysis
(`docs/GAP-ANALYSIS.md`, 5.3) found that a tool with SecureVibe not connected simply built on, and `AGENTS.md` is the
one file `sv` writes that a tool reads whether or not SecureVibe is connected. The line goes only into `AGENTS.md`
(and `sv rules --print`); `securevibe_guidance` gives the rules without it, since a tool calling it is plainly
connected. It is an instruction to the AI coding tool, like the rest of the section, not code the app runs, so the
decision stands. Backlog item 25(a).
