How sv works

The owner builds the app with their own AI coding tool, in any language. sv reads what was built, runs it behind a network fence to ask it questions, and writes a report that ranks every piece of evidence and names what nothing examined. Every stage below is a command of its own; sv report runs them together.

What goes in

The owner

Decides what the app is for, answers the questions no tool can, and downloads the vulnerability data.

Their AI coding tool

Writes the app, and fills in securevibe.toml from the spec sv init gives it. Before it codes, sv gives it rules to follow and prompts, each marked tested or not.

sv rules · sv prompts

The app's folder

Code in any language, lockfiles, and the app's own tests.

securevibe.toml

What the app is: its stack, how to start it, its test users, AI and sign-in settings, and answers to design questions.

security-notes.md

The owner's written answers, one question per requirement (sv notes). An answer the AI tool records is marked as its own.

Advisory data

OSV exports the owner downloaded. sv never fetches them itself.

What sv does

Scope

OWASP ASVS 5.0, AISVS 1.0, and the Secure by Design checklist, narrowed by what the manifest and the code say the app has: which requirements apply, and why.

sv scope

Read the code

One walk of the folder: credentials, configuration and start commands, a bill of materials held to each manifest, 19 tree-sitter rules in 15 languages, and the app's own tests that name a requirement.

sv check · sv sbom

Outside tools

Semgrep (or Opengrep in its place), Bandit, CodeQL, gosec, and Brakeman, when installed, each rule mapped to the requirements it can speak to.

--tools

Known vulnerabilities

Every package compared against the downloaded advisories, offline. A comparison that did not cover the whole app says so.

sv audit · --advisories

The live site

The one network exception: at most four read-only requests to an address the owner types, for the certificate and its revocation status, HTTPS, cookies, and old TLS versions.

sv probe <address>

The running app, behind the fence

A Docker network made with --internal for each run, and confirmed internal before anything starts: nothing inside can reach the internet. The app runs read-only, with no capabilities. A rate limiter's answer is waited out, and a crash is never read as the app refusing.

What comes out

Evidence, ranked

Each requirement gets the strongest thing behind it. A finding outranks everything.

The report

HTML, Markdown, SARIF, and JSON. It opens with what was not examined, names the sv that made it, and adds a threat model, the tests worth writing, and what only the owner can check. Nothing in it says a requirement passed.

sv report

The bundle

The app, its report, and a SHA-256 for every file, in one zip.

sv bundle

The MCP server

The same checks, served to the AI coding tool in ten tools, with the reports as resources, progress as it goes, and a 50-second limit, kept inside one folder.

sv mcp --root

The loop closes through the AI coding tool: it reads the findings over MCP or from the report, changes the app, and runs the checks again. The owner decides when it is done.

the owner and their tool sv's own stages inside the network fence

A stage that cannot run, such as no container backend, no advisory data, or a language no rule reads, marks what depended on it not assessed: never a pass and never a failure.
