# If you suspect a security incident

A short, concrete plan for the moment something looks wrong — a leaked password, unexpected admin activity, or a report from a user.

**Contact:** Not configured yet. Set ADMIN_EMAIL in .env (or the owner contact in your SecureVibe design) so this file names a real contact.

## 1. Check what actually happened

- Run `npm run audit:verify` to confirm the security event log has not been tampered with.
- Look at recent events for the account or IP address in question (the `audit_log` table, or the log file at `DATA_DIR/app.log`).
- In test/staging, the same data is available at `GET /__securevibe/events` — never in production.

## 2. Contain it

- Sign the affected account out everywhere: **Administration → Users → (the account) → Sign out everywhere**.
- If a password may be known to someone else, force a reset: the same page can disable the account or remove its one-time codes so it cannot be used until the owner resets their password.
- If the API key feature is enabled, revoke the key in question.

## 3. Fix the cause

Patch the vulnerability or misconfiguration, redeploy, and confirm with `npm test` and `npm run typecheck` before bringing the app back if it was taken offline.

## 4. Tell the people affected

If personal data may have been exposed, tell the people affected in plain language: what happened, what data, what you have done about it, and what they should do (for example, changing a re-used password elsewhere). Rules on when you must notify people or a regulator vary by where your users live — check docs/data-protection.md and, if unsure, a professional.

## 5. Write it down

Keep a short record of what happened and what changed as a result — even a few lines. It is the fastest way to improve the plan above next time.
