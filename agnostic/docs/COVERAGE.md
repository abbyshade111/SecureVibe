# Coverage: what the checks can speak to

Generated by `tools/coverage.py` from the checks' own citations. Do not edit by hand; run
`python3 tools/coverage.py` after changing a check, and the build fails until you do.

## How to read this

- **Can settle**: at least one check can mark the requirement *checked* or *needs attention*.
  A check is almost always about part of a requirement: a clean result is one automated check
  that was satisfied, not a pass.
- **Supporting only**: a check speaks to it, but the requirement asks something no check can
  answer, such as a documented policy or a design decision. The check is shown beside it and
  a person still has to answer it. The whole Secure by Design checklist is this by design.
- **Nothing**: no check in `sv` names it. It can still be credited by the app's own tests that
  name the requirement id and pass, which is how `sv init` asks for tests to be written, and
  otherwise stays *not verified*.
- Which requirements apply to a given app is decided separately; this counts every requirement.

What each kind of check needs before it can run:

| Kind | Needs |
|---|---|
| Reads the code | nothing: plain `sv check` |
| Known vulnerabilities | a local copy of the OSV database (`--advisories DIR`) |
| The running app | a container backend and a `run` section (`--run`) |
| Signed in | the above, and a `users` section with test accounts, or an `oidc` section for a sign-in through another service |
| Outside tools | the tool installed (`--tools`) |
| Your own live site | the address your app is served from, typed at the terminal (`sv probe https://…`) |
